# 10. Vault: секреты и жизненный цикл доступа

[Программа](../../README.md) · [Практика](practice.md) · [Подсказки](hints.md)

## Цель и вход

Выдать приложению минимально необходимый доступ и наблюдать его прекращение. Нужны HTTP, переменные окружения и основы контейнеров. Практика использует локальный dev Vault с публично известным учебным root token; он существует только внутри изолированного занятия на loopback.

## Откуда берётся доверие

Пароль в Git, image или открытом конфиге трудно отозвать и легко скопировать. Vault централизует хранение секретов и проверяет права клиента. Но приложению всё равно нужно впервые доказать свою личность. Это secret zero: статический root token в env не решает задачу, а лишь перемещает её.

В production обычно используют identity окружения: Kubernetes auth, workload identity или другой согласованный auth method. После аутентификации клиент получает token с ограниченной policy и временем жизни. Различай аутентификацию (кто ты) и авторизацию (что разрешено).

## Policy и KV v2

Policy разрешает capabilities на определённые пути. В KV v2 путь HTTP API для значения содержит `/data/`, а для списка метаданных — `/metadata/`. Команда CLI скрывает часть этой структуры; policy должна учитывать реальный API path.

```hcl
path "secret/data/example" {
  capabilities = ["read"]
}
```

Это право чтения только одного секрета. Разрешение на `secret/*` гораздо шире и не требуется обычному inference-сервису. Проверяй отрицательные случаи: чтение соседнего пути и запись должны завершаться отказом.

KV хранит статические значения с версиями. Dynamic secrets создаются по запросу для поддерживаемых систем и могут иметь lease с отзывом. Не называй любое значение KV «динамическим паролем»: жизненный цикл принципиально различается.

## TTL, renewal и отзыв

TTL задаёт срок действия token. Renew продлевает его только в рамках разрешённых политик и максимальных сроков. Приложение должно обновлять доступ до истечения или корректно останавливаться/переходить в неготовность при недоступной зависимости. Бесконечный retry с 403 может перегружать систему и скрывать реальную причину.

Кеширование секрета снижает число запросов к Vault, но увеличивает период использования старого значения. Реши, что делать после ротации и после revoke. Если секрет нужен лишь при старте для скачивания модели, его жизненный цикл отличается от доступа к базе на каждом запросе.

## Dev mode и production

Учебный dev server хранит состояние в памяти, автоматически unseal и не представляет полноценную HA-инсталляцию. Остановка контейнера теряет секреты. Настоящий Vault требует TLS, устойчивого storage, процедур seal/unseal или auto-unseal, audit и резервирования. Эти темы нужно понимать концептуально, но кластер Vault не добавляется к ноутбучному проекту ради количества сервисов.

Vault не удаляет секрет из логов, если приложение само его напечатало. Выводи только статус доступа, имя поля и путь; не печатай токены и secrets. В starter HTTP-клиент оставлен для подключения обработки отказов; root используется лишь для настройки лабораторной.
