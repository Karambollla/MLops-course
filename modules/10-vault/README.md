# 10. Vault: секреты и жизненный цикл доступа

[Программа](../../README.md) · [Задания](#задания) · [Подготовка](#подготовка-к-заданиям)

## Какую задачу решает этот модуль

Housing API из предыдущих модулей читает публичный локальный bundle и не нуждается в пароле к нему. Представим другой способ поставки: модель лежит в закрытом хранилище и приложению нужен ключ для скачивания. Если встроить ключ в Docker image или положить его в values Helm, копии распространятся вместе с выпуском, а отзыв доступа потребует искать каждую копию. Vault предоставляет отдельный сервис хранения секретов и проверки доступа к ним.

**Секрет** — значение, владение которым даёт доступ: пароль, токен или закрытый ключ. Имя bucket или MODEL_PATH обычно является конфигурацией, а ключ чтения bucket — секретом. В модуле изучается не реальное закрытое хранилище, а учебное поле `artifact_key` в Vault 1.19.0. Результат — ограниченный клиент, который подтверждает наличие нужного поля без раскрытия значения, и различение отказа прав от сетевой ошибки.

## Подготовка к заданиям

Все команды выполняются из корня курса.

Основное Python-окружение подготовь по [SETUP](../../SETUP.md#основная-среда). Базовые тесты чистых функций и вызовов через test double не требуют Vault. Для SDK-проверок установи hvac, для чтения реального секрета подготовь dev Vault ниже. Нужен Docker daemon, но housing bundle и kind не требуются.

### SDK

После основного SETUP установи необязательную зависимость:

```bash
python -m pip install -r labs/vault/requirements.txt
MLOPS_RUN_SDK=1 make task TASK=10-vault/01-policy
```

Импорт не открывает соединений. SDK-тест использует настоящий hvac KV2 и transport double. Доступ/права проверяются отдельно на живом dev Vault. Незавершённые `read_secret`, `inspect_payload`, `renew_token`, `revoke_token`, `classify_error` остаются student-заготовками.

### Подготовка dev Vault

```bash
docker compose -f labs/vault/compose.yaml up -d
```

Лимит контейнера — 1 ГиБ с учётом пускового расхода памяти на ARM64. Низкое потребление после старта не доказывает достаточность лимита для запуска.

Команды настройки выполняй внутри контейнера с root только на этом стенде:

```bash
docker compose -f labs/vault/compose.yaml exec -e VAULT_TOKEN=course-root vault vault kv put secret/housing artifact_key=local-demo-value
```

Скопируй policy в контейнер и создай ограниченный token:

```bash
docker compose -f labs/vault/compose.yaml cp modules/10-vault/tasks/01-policy/policy.hcl vault:/tmp/policy.hcl
docker compose -f labs/vault/compose.yaml exec -e VAULT_TOKEN=course-root vault vault policy write housing /tmp/policy.hcl
docker compose -f labs/vault/compose.yaml exec -e VAULT_TOKEN=course-root vault vault token create -policy=housing -ttl=60s -renewable=false
```

Сначала реализуй policy из задания 01, затем копируй и загружай её командами выше. `token create` показывает временный token: используй его только в текущем shell и не сохраняй полный вывод в проект.

Для SDK-чтения задай `VAULT_ADDR=http://127.0.0.1:8200` и ограниченный token в `VAULT_TOKEN` в текущем shell. Не вставляй token в командную строку/файл. Введи полученный ограниченный token без эха:

```bash
read -s VAULT_TOKEN
export VAULT_TOKEN
```

Token с TTL60s может истечь пока ты реализуешь функции. Подготовь код заранее, а для нового опыта выпусти новый временный token.

```bash
export VAULT_ADDR=http://127.0.0.1:8200
python scripts/run_task.py run 10-vault/01-policy
MLOPS_RUN_INTEGRATION=1 make task TASK=10-vault/01-policy
```

Поле artifact_key остаётся внутри клиента, stdout содержит только факт наличия. Соседний path запрещён. Для ручного renewal создай **новый** token командой подготовки с `-renewable=true`, используй его в `VAULT_TOKEN` и выполни CLI задания 02. Для автоматического lifecycle live-теста администратор передаётся отдельно через `VAULT_ADMIN_TOKEN`, application token не используется для создания дочерних:

В отдельном вводе передай token администратора только своего dev-стенда:

```bash
read -s VAULT_ADMIN_TOKEN
export VAULT_ADMIN_TOKEN
MLOPS_RUN_INTEGRATION=1 MLOPS_RUN_WRITES=1 make task TASK=10-vault/02-expiry
```

Тест создаёт свой child TTL60s, вызывает student SDK renew/revoke, проверяет 403 и очищает child в finally. Он не создаёт policy/секреты и не отзывает переданный admin token. Без обоих opt-in флагов writes пропущены.

`unset VAULT_TOKEN VAULT_ADMIN_TOKEN`, затем `docker compose -f labs/vault/compose.yaml down`. Dev-секреты исчезнут. Не сохраняй root/token в файлы проекта.

## Что приходит из проекта и что добавляет стенд

Из [сервисного модуля](../03-service-ci/README.md) нужны понимание HTTP-кодов, переменных окружения и готовности API. Из [Kubernetes](../07-kubernetes/README.md) — различие конфигурации Pod и процесса, из [Helm](../08-helm/README.md) — понимание, почему values и сохранённый рендер не подходят для секретов. Bundle остаётся прежним: этот модуль его не переобучает и не добавляет обязательную зависимость Vault в публичный housing API.

`labs/vault/compose.yaml` запускает локальный dev server на `127.0.0.1:8200`. Привязка порта к loopback означает доступ с этого компьютера. Внутри контейнера Vault слушает другой адрес — `0.0.0.0:8200`. Учебный root token `course-root` нужен для создания данных и политики. Клиент упражнений должен использовать отдельный application token с меньшими правами.

`tasks/01-policy/solution.py` создаёт настоящий `hvac.Client` из `VAULT_ADDR`/`VAULT_TOKEN` с timeout 5 секунд. Ты реализуешь `read_secret(client,path,mount_point)` через SDK KV v2 и `inspect_payload`, возвращающую только наличие поля. Во втором задании сохраняется чистая `classify_error` и добавлены SDK-заготовки `renew_token`/`revoke_token` для собственного временного token. Все student-функции оставлены с `NotImplementedError`: CLI-обвязка сама по себе ещё не является работающей интеграцией. Необязательная зависимость `hvac==2.3.0` устанавливается из `labs/vault/requirements.txt`.

## Кто удостоверяет клиента и кто разрешает чтение

**Аутентификация** — проверка личности, **авторизация** — проверка разрешённого действия. **Auth method** — способ доказать Vault свою личность, например предъявить удостоверение Kubernetes. После успешной проверки Vault выдаёт **token**, строку доступа, связанную с политиками и временем жизни. HTTP-клиент предъявляет его в заголовке `X-Vault-Token`.

**Policy** — набор правил доступа. **Capability** — разрешённая операция на конкретном пути, например `read`. Администратор настраивает policy и auth role, клиент читает только необходимые значения. Root token имеет слишком широкие права для приложения: удачное чтение с root не проверяет, что policy составлена правильно.

Это похоже на middleware авторизации Go-сервиса: удостоверение устанавливает субъект, правило допускает метод и ресурс. Граница аналогии: Vault ещё хранит данные и управляет сроком доступа, а приложение обязано обработать его истечение. Перенос неизменного root token из Git в env не решает проблему начального доверия. Её называют **secret zero**: откуда приложение берёт первое удостоверение для получения остальных секретов.

В production обычно используют identity среды исполнения, то есть подтверждаемую принадлежность Pod или workload определённому окружению. В локальной лабораторной ограниченный token выдаёт администратор вручную. Это способ изучить права и срок жизни, а не готовая схема автоматической доставки удостоверений.

## KV v2: путь, политика и форма ответа

**Secrets engine** — подключаемый механизм Vault для хранения или выдачи секретов. **KV v2**, key-value версии 2, хранит произвольные поля и версии их значений. Mount `secret/` — префикс, под которым он доступен. Логическое имя `secret/housing` в CLI преобразуется в HTTP API `/v1/secret/data/housing` при чтении данных.

Ниже отдельный пример для условного `example`, чтобы показать смысл полей policy без готового решения задания:

```hcl
path "secret/data/example" {
  capabilities = ["read"]
}
```

`path` относится к пути Vault API без `/v1/`. Сегмент `data` обязателен для данных KV v2. `read` допускает GET значения, но не его запись. Для списка метаданных KV v2 используется путь с `metadata`, и разрешение чтения данных не превращается в разрешение перечислять все секреты. Широкое `secret/*` увеличило бы доступ далеко за пределы одного файла модели.

Путь чтения учебного значения:

1. Клиент отправляет GET `/v1/secret/data/housing` с token.
2. Vault проверяет срок и действительность token, затем разрешения на API path.
3. KV v2 возвращает JSON: внешний `data` содержит результат операции, внутренний `data` — собственные поля секрета, `metadata` — сведения о версии.
4. Функция проверяет наличие `artifact_key` и отдаёт только `{"field_present": true}`. Значение дальше не требуется и не должно попадать в вывод.

Форма с вымышленным значением выглядит так:

```json
{
  "data": {
    "data": {"artifact_key": "example-not-a-real-key"},
    "metadata": {"version": 1}
  }
}
```

Два уровня `data` — часть контракта API, а не опечатка. Наличие `metadata.version` не подтверждает наличие `artifact_key`. Ответ с отсутствующим внутренним словарём или полем должен стать ошибкой контракта, а не успешным `false`, которое скроет неправильную структуру. Формат описан в [KV v2 API](https://developer.hashicorp.com/vault/api-docs/v1.19.x/secret/kv/kv-v2).

Права проверяют и положительно, и отрицательно: разрешённое чтение даёт 200, соседний путь при ограниченной policy — 403. Не печатай тело curl для доказательства чтения. Достаточно кода ответа и безопасного результата функции. Секрет нельзя вернуть из функции «для удобства отладки» и затем надеяться, что логгер его отфильтрует.

## TTL, продление, отзыв и ротация

**TTL**, time to live, — оставшееся время действия. Token с TTL 60 секунд разрешает обращение до истечения, если его раньше не отозвали. **Renewal** — запрос продления. Он возможен только для renewable token и в пределах ограничений Vault. **Revoke** — явный отзыв до естественного истечения. Смотри фактически возвращённый TTL: запрос продления не обещает бесконечное время жизни.

Для опыта nonrenewable token сначала даёт 200, после истечения — 403. Для отдельного renewable token продление выполняют до истечения. После `vault token revoke -self` следующее чтение тоже даёт отказ. При этом значение KV продолжает существовать. [Жизненный цикл leases в Vault 1.19](https://developer.hashicorp.com/vault/docs/v1.19.x/concepts/lease) помогает различить срок удостоверения и срок выдаваемого секрета.

**Lease** — запись о времени действия выданного доступа или динамического секрета. **Dynamic secret** создаётся по запросу для поддерживаемой внешней системы, например учётная запись БД, и может отзываться через эту систему. Значение KV является статически сохранённым: истечение token не удаляет пароль из KV, из памяти клиента или из другой системы. **Ротация** — замена секретного значения. Версия KV хранит новое значение, но приложение не перечитывает его автоматически.

Если ключ нужен только для загрузки модели на старте, после истечения token уже загруженная модель может продолжать прогнозы. Но новое скачивание без доступа невозможно. Если секрет нужен для каждой операции с БД, политика готовности будет другой. Решение о readiness принимает приложение на основе реально нужной зависимости. Vault не выбирает его автоматически. Кеш уменьшает обращения, но позволяет дольше использовать старое значение. Продумай reload, удаление старого значения и ротацию доступа в самой внешней системе.

## Интеграция с Pod и ответственность приложения

В руководстве рассматривается поток без развёртывания нового auth-стенда: Pod с **service account**, именованной идентичностью Kubernetes, получает JWT — подписанное удостоверение. Он предъявляет JWT Kubernetes auth method Vault и указывает **role**, правило сопоставления service account/namespace с политиками token. После проверки Vault выдаёт короткий application token. Клиент читает ключ, скачивает конкретную версию артефакта, проверяет bundle и только затем становится готовым.

**Vault Agent** — отдельный процесс, который может аутентифицироваться, продлевать token и рендерить секрет в файл. Приложение всё равно отвечает за перечитывание файла и переход к нужному состоянию при ошибке. Запись нового файла не меняет автоматически уже созданное HTTP-соединение или значение в памяти.

Время ожидания запроса, timeout, не говорит, принял ли сервер запрос: сеть не дала получить исход вовремя. Для чтения допустим ограниченный retry с backoff, увеличением задержек между попытками. 403 означает полученный отказ доступа: проверь token, TTL, path и policy, а не запускай бесконечный retry. 404 может означать неверный путь или отсутствующие данные и отличается от 403. В учебной классификации прочие HTTP-коды попадают в `http_error`. Углублённая диагностика остаётся за вызывающим кодом.

## Границы dev mode и диагностика

Dev server хранит состояние в памяти, автоматически готов к работе и не использует полноценную production-схему хранения и защиты. После остановки его секреты исчезают. Устойчивый Vault требует TLS, постоянного storage, процедуры unseal/auto-unseal, аудита и восстановления. **Seal** означает состояние, когда Vault не может расшифровывать защищённые данные. Dev mode скрывает эту эксплуатационную процедуру, чтобы сосредоточиться на API.

Если curl не соединяется, сначала проверь адрес, порт и работающий контейнер. Если вернулся 403, соединение уже было: исследуй права и время жизни. Если 200 есть, а функция отклоняет payload, проверь вложенность KV v2 и имя поля. Если после перезапуска исчезло значение, это ожидаемое свойство dev storage, а не проблема Python. В логи допускаются тип ошибки, путь и статус. Token, тело секрета и полный вывод token create не сохраняются в проект.
