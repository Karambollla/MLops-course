# 10. Vault: выдать доступ к закрытой модели

[Программа](../../README.md) · [Задания](#задания) · [Подготовка](#подготовка-к-заданиям)

## Какую проблему решаем

Housing API читает локальный bundle. Представим, что следующую версию модели нужно скачать из закрытого хранилища. Для этого загрузчику нужен ключ. Если положить его в Docker image, каждая копия образа получит тот же доступ. При смене ключа придётся искать эти копии и выпускать образ заново.

Вместо этого загрузчик обращается к отдельному сервису: предъявляет удостоверение и получает только разрешённое значение. Администратор может ограничить путь и срок доступа независимо от выпуска приложения. Такой сервис предоставляет Vault. В заданиях ты прочитаешь учебный ключ через Python SDK, проверишь отказ на соседнем пути, затем продлишь и отзовёшь временный доступ.

Скачивания из закрытого хранилища здесь нет. Используется поле `artifact_key` с вымышленным значением. Публичный Housing API остаётся прежним. Для классификатора изображений можно было бы хранить ключ доступа к весам, а для batch-inference — пароль к источнику входной таблицы. Во всех случаях нужно различать значение секрета, разрешение получить его и дальнейшее использование приложением.

## Подготовка к заданиям

Все команды выполняются из корня курса. Подготовь [основную Python-среду](../../SETUP.md#основная-среда). Базовые тесты функций используют фиксированные ответы и подменяют границу SDK. Для настоящего клиента установи закреплённый `hvac==2.3.0`:

```bash
python -m pip install -r labs/vault/requirements.txt
```

`hvac` — Python SDK Vault: библиотека формирует HTTP-запросы и разбирает ответы. Создание клиента не запускает сервер и не выдаёт ему права. Чтение настоящего значения потребует работающего Vault и отдельного удостоверения клиента.

В локальном стенде Vault запускается в **dev mode**: хранит состояние в памяти и сразу готов к настройке. Это позволяет изучить API без отдельной настройки хранилища. Docker daemon нужен только для этой части. Housing bundle и kind не используются.

```bash
docker compose -f labs/vault/compose.yaml up -d
export VAULT_ADDR=http://127.0.0.1:8200
```

Compose публикует сервер на `127.0.0.1:8200`. В контейнере задан учебный root token `course-root`. Он разрешает административную настройку стенда. Успешный запрос с ним ещё не проверяет ограничения приложения. Создание учебного значения, политики и ограниченного token выполняется в [задании 01](tasks/01-policy/README.md#подготовить-данные-и-ограниченный-token), после реализации функций.

## Кто получает ключ и кто разрешает чтение

Чтобы выдать загрузчику доступ, сначала надо установить, кто обращается, а затем решить, что ему разрешено. Первую проверку называют **аутентификацией**, вторую — **авторизацией**. В лабораторной администратор вручную выдаёт клиенту строку доступа — **token**. Клиент предъявляет её Vault в заголовке `X-Vault-Token`.

У token есть список правил доступа — **policies** — и срок действия. Правило связывает конкретный путь с разрешёнными операциями, или **capabilities**. Для загрузки ключа достаточно `read`. Право записать новый ключ или перечислить все секреты этой операции не требуется. Поэтому проверяются оба исхода: чтение нужного пути успешно, соседний путь запрещён.

Сам ключ хранилища и token Vault — два разных секрета. **Секретом** здесь называется значение, владение которым даёт доступ. `MODEL_PATH` описывает, где искать файл, а `artifact_key` должен давать право его получить. Перенос root token из Git в env не решает вопрос первого удостоверения приложения. Этот вопрос называют **secret zero**. В последнем задании вместо ручной выдачи рассматривается удостоверение среды Kubernetes.

## KV v2: путь, политика и форма ответа

Загрузчик хочет прочитать набор полей по имени `housing`. Vault должен знать, каким механизмом обслуживать это имя. Подключаемый механизм хранения или выдачи секретов называется **secrets engine**. Здесь используется **KV v2** — хранилище key-value с версиями значений. Оно подключено под префиксом `secret`, который называют **mount**.

У одного значения есть несколько представлений пути. Они относятся к одной операции, но передаются разным интерфейсам:

| Где используется | Что передать | Почему именно так |
|---|---|---|
| Команда `vault kv put/get` | `secret/housing` | CLI получает mount и логическое имя вместе |
| Python `read_secret_version` | `path="housing", mount_point="secret"` | SDK сам добавляет служебные сегменты KV v2 |
| Policy | `secret/data/housing` | Правило проверяет путь API без префикса `/v1/` |
| HTTP GET | `/v1/secret/data/housing` | `data` выбирает чтение данных KV v2 |

Для другого условного значения `example` правило чтения выглядело бы так:

```hcl
path "secret/data/example" {
  capabilities = ["read"]
}
```

`path` ограничивает объект, `capabilities` — действия. Путь с `metadata` обслуживает другие операции KV v2, включая работу с метаданными. Разрешение прочитать данные не даёт автоматически права перечислять все значения. В задании policy ограничивается одним путём.

После проверки token и policy сервер возвращает ответ. Внешний `data` содержит результат операции KV v2, внутренний `data` — пользовательские поля, `metadata` — сведения о версии:

```json
{
  "data": {
    "data": {"artifact_key": "example-not-a-real-key"},
    "metadata": {"version": 1}
  }
}
```

Два уровня `data` — часть [API KV v2](https://developer.hashicorp.com/vault/api-docs/v1.19.x/secret/kv/kv-v2). Наличие версии не подтверждает наличие нужного поля. В задании `inspect_payload` проверяет структуру и ключ `artifact_key`, после чего возвращает только `{"field_present": true}`. Секрет не нужен дальнейшему учебному расчёту и не должен попадать в stdout, исключение или результат функции.

## TTL, продление, отзыв и ротация

Допустим, ключ удалось прочитать, но через некоторое время повторное чтение получает отказ. Это может произойти без изменения policy: истёк срок token. Оставшееся время действия называют **TTL**, time to live. В опытах доступ выдаётся на `60s`, чтобы наблюдать истечение на одном локальном запуске.

Если token допускает продление, клиент может заранее запросить **renewal**. Vault возвращает фактически разрешённый срок: запрошенные `60s` не обещают бесконечного доступа. Для немедленного прекращения доступа используют **revoke**, отзыв. Во втором задании функции обращаются только к `renew_self` и `revoke_self`: они управляют token текущего клиента.

| Действие | Что меняется | Что проверить следующим чтением |
|---|---|---|
| Истечение nonrenewable token | Удостоверение больше не действует | Отказ 403 |
| Продление renewable token | Vault выдаёт новый допустимый срок | Чтение ещё доступно, TTL берётся из ответа |
| Отзыв token | Доступ прекращается до естественного истечения | Отказ 403 |
| Замена значения KV | Появляется новая версия данных | Клиент должен заново прочитать значение |

Последнее действие называют **ротацией** секрета. Отзыв token не удаляет статическое значение KV и уже прочитанную копию из памяти. Замена ключа в KV также сама по себе не меняет ключ во внешнем хранилище. Эти действия нужно согласовать с системой, к которой он открывает доступ.

Vault умеет и выдавать **dynamic secrets**: например, создавать временную учётную запись БД. У выданного доступа может быть **lease**, запись о сроке и отзыве. В этой практике KV хранит статическое значение. Истечение удостоверения клиента не превращается в удаление этого значения.

## Интеграция с Pod и ответственность приложения

Ручной ввод token удобен для опыта, но Pod должен запускаться автоматически. Kubernetes может предоставить ему удостоверение именованного **service account**. Pod предъявляет подписанный JWT и имя согласованной **role** механизму Kubernetes auth в Vault. Role задаёт связь service account/namespace с политиками выдаваемого token. После проверки клиент получает ограниченный token, читает ключ, скачивает выбранный bundle и проверяет его перед готовностью API.

**Vault Agent** — отдельный процесс, который может выполнить аутентификацию, продлевать token и записывать секрет в файл. Приложение всё равно должно перечитать изменившийся файл и применить значение. Новый файл не обновляет уже открытое соединение или переменную в памяти.

Поведение при отказе определяется нужной операцией. Если ключ нужен только для стартового скачивания, загруженная модель может продолжать отвечать после истечения token. Для новой загрузки доступ придётся восстановить. Если batch-задача читает закрытую таблицу во время работы, потеря доступа мешает следующему чтению. Readiness HTTP-сервиса и успешность batch-запуска описывают разные условия. Vault не выбирает их за приложение.

При **timeout** клиент не получил исход запроса за отведённое время. Ограниченный повтор чтения с растущей задержкой, **backoff**, может помочь при временной сетевой проблеме. Полученный 403 требует проверки token, TTL и policy. Повтор того же запроса прав не добавляет. Учебная `classify_error` сохраняет это различие, но сама не выполняет сеть и не повторяет запросы.

## Проверки и завершение

В задачах явно разделены три проверки. Базовые тесты проверяют функции и один вызов нужного метода на подменённом клиенте. `MLOPS_RUN_SDK=1` включает настоящий `hvac` с подменённым транспортом, без сервера. `MLOPS_RUN_INTEGRATION=1` включает чтение подготовленного dev Vault. Жизненный цикл нового token дополнительно требует `MLOPS_RUN_WRITES=1`.

Пропуск live-теста не подтверждает права на сервере. При 403 соединение уже установлено: проверь ограниченный token и путь. При ошибке соединения проверь адрес и контейнер. При ошибке структуры после успешного чтения проверь вложенность `data.data`. После пересоздания dev server данные придётся подготовить заново: они хранятся в памяти.

После обоих SDK-заданий очисти переменные и останови стенд:

```bash
unset VAULT_TOKEN VAULT_ADMIN_TOKEN
docker compose -f labs/vault/compose.yaml down
```

Production Vault требует устойчивого хранения и отдельной настройки защиты. Dev server не предназначен для настоящих ключей. В проекте сохраняются policy и код, а значения token и полный вывод административных команд в файлы проекта не записываются.
