# От удостоверения Pod до готовой модели

[Модуль](../../README.md) · [Подготовка](../../README.md#подготовка-к-заданиям) · [Все задания](../../README.md#задания)

## Что разбираем

В первых заданиях администратор вручную передавал token клиенту. При автоматическом запуске Pod такой шаг недоступен. Нужно определить, откуда берётся первое удостоверение, кто выдаёт права и кто реагирует на потерю доступа.

Это разбор архитектуры на прежнем Housing API. Новый auth-стенд, Python-функция и файл с ответами не требуются. Подготовка опирается на [готовность API в Kubernetes](../../../07-kubernetes/README.md) и на [policy/TTL предыдущих заданий](../../README.md#кто-получает-ключ-и-кто-разрешает-чтение).

## Сначала определить необходимую зависимость

Если bundle публичен и уже лежит в локальном volume, чтение Vault не нужно для прогнозов. Рассматриваем другой случай: загрузчик должен получить ключ и скачать закрытую версию. Вход операции — удостоверение Pod и выбранная версия артефакта. Успешный выход — скачанный и проверенный bundle, который API смог загрузить. Сам факт чтения ключа ещё не означает готовность модели.

Для batch-inference тем же выходом могла бы быть доступность входной таблицы перед расчётом. У batch-задачи нет обязательного HTTP `/ready`, но есть условие успешного запуска. Поэтому реакцию на недоступность секрета выбирают по конкретной работе приложения.

## Проследить одно получение доступа

1. Pod запускается с выделенным Kubernetes service account. Среда даёт ему JWT — подписанное удостоверение.
2. Клиент отправляет JWT в Kubernetes auth method Vault и указывает согласованную role. Role связывает допустимые service account/namespace с policy. Механизм описан в [главе](../../README.md#интеграция-с-pod-и-ответственность-приложения).
3. Vault проверяет удостоверение и выдаёт application token с policy и сроком. Например, policy разрешает только чтение `secret/data/housing`, как в задании 01.
4. Загрузчик читает KV v2 через SDK, получает `artifact_key`, скачивает выбранную версию модели и проверяет bundle.
5. API становится готовым после успешной загрузки модели. Ключ, JWT и token в обычный вывод не попадают.

Здесь service account отвечает на вопрос «кто обращается», role — «какие права выдать этой личности», policy — «какое действие разрешено», TTL — «как долго действует выданный доступ». Root token из dev-стенда в эту цепочку приложения не входит.

## Разобрать изменение условий

| Событие | Что проверить или изменить | Наблюдаемый результат |
|---|---|---|
| Timeout при чтении | Ограниченный retry с backoff, доступность Vault | Новый запрос либо контролируемая ошибка загрузки |
| 403 | Token/TTL, policy, соответствие role личности | Восстановленная авторизация. Повторы без изменения доступа не помогают |
| Приближается истечение renewable token | Запросить renewal заранее и прочитать фактический TTL | Доступ продлён в пределах разрешений Vault |
| Ключ заменён в KV | Перечитать и применить новое значение | Новые операции используют новый ключ |
| Модель уже загружена, token истёк | Определить, нужен ли ключ для текущего predict | Прогнозы могут продолжаться. Новое скачивание требует доступа |

Vault Agent может взять на себя аутентификацию, renewal и запись секрета в файл. Приложение отвечает за чтение этого файла и применение значения. Запись файла сама не обновит соединение с закрытым хранилищем. Доступ к статическому KV также не равен выдаче динамической учётной записи БД.

Разбор завершён, когда для каждого перехода понятно, кто выполняет действие, какой вход предъявляет и чем проверяется результат. Упражнение не требует развёртывания Kubernetes auth или изменения публичного Housing API. Если dev Vault ещё работает, используй [очистку модуля](../../README.md#проверки-и-завершение).
