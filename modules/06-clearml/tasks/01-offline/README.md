# ClearML: связать локальное обучение с его результатами

[Модуль и подготовка](../../README.md#подготовка-к-заданиям) · [Все задания модуля](../../README.md#задания) · [SETUP](../../../../SETUP.md)

## Что предстоит сделать

В модуле 01 ты получил программу, которая обучает модель и сохраняет файлы. Теперь нужно уметь ответить на вопрос: «Какие данные и настройки дали именно этот результат?» Реализуй `train_and_log` в соседнем [solution.py](solution.py): вызови прежнее обучение и сохрани в одной Task параметры, ошибки модели и выбранные файлы. Проверяй функцию тестом, затем настоящую локальную сессию и созданный Housing output.

Здесь обучение продолжает выполняться на твоей машине. Offline-режим записывает сведения локально, поэтому сервер и Agent для задания не нужны. Смысл Task и её методов разобран в [описании SDK](../../README.md#sdk-и-task-запись-из-python-программы).

## Что должно быть готово

- Собственная реализация `housing.train.train` из [задания кандидата](../../../01-ml/housing.ipynb).
- CSV `work/housing.csv`, подготовленный по [SETUP](../../../../SETUP.md).
- Формат `metrics.json` и `manifest.json` из [контракта проекта](../../../../labs/housing/README.md). В частности, метрики выбранной модели находятся в `candidate.test.mae` и `candidate.test.rmse`.

У обучения два входа: данные и настройки запуска. На выходе появляются модель, метрики, манифест и split. Твоя функция должна передать в SDK фактически полученные результаты. Запись постоянного `mae=0.5` проверила бы доступность метода SDK, но потеряла бы связь с обучением.

## Что уже сделано и что реализовать

В `solution.py` готова CLI-обвязка: она разбирает `--data`, `--output`, `--seed`, открывает Task и закрывает её в `finally`. Поэтому рабочая часть задания сосредоточена в одной функции:

```python
def train_and_log(task, data_path: Path, output_dir: Path, seed: int = 42):
    ...
```

В заготовке нет аннотации возвращаемого типа. Реализуй функцию в [solution.py](solution.py), опираясь на [test_task.py](test_task.py).

| Параметр | Тип | Формат и смысл | Откуда берётся | Пример |
|---|---|---|---|---|
| `task` | Созданный ClearML `Task` или совместимый объект | Методы `connect`, `get_logger`, `upload_artifact`. Функция использует существующую Task | Создаётся CLI-обвязкой через `Task.init`. В unit-тесте подменяется | Offline Task проекта `mlops-course` |
| `data_path` | `Path` | Путь к существующему housing CSV | CLI `--data`, данные из SETUP | `Path("work/housing.csv")` |
| `output_dir` | `Path` | Каталог результатов именно этого обучения | CLI `--output` | `Path("work/clearml-run-1")` |
| `seed` | `int`, по умолчанию `42` | Передаётся существующему train без подмены | CLI `--seed` | `17` |

CLI создаёт проект `mlops-course` и Task с именем `housing-student`. Путь `work/clearml-run-1` в таблице — пример отдельного каталога одного обучения. Seed `17` ниже выбран только для демонстрации передачи аргумента, стандартный seed CLI остаётся `42`.

Реализуй последовательность действий по следующему контракту:

| Действие | Требуемое поведение |
|---|---|
| Запуск обучения | Вызвать `housing.train.train(data_path, output_dir, seed)` |
| Происхождение | Прочитать `seed` и `data_sha256` из manifest.json. Передать их в `task.connect` под ключами `seed` и `data_sha256` |
| Качество | Прочитать `candidate.test.mae` и `candidate.test.rmse` из созданного metrics.json |
| Числовые ряды | Записать эти значения через logger: title=`quality`, series=`mae`/`rmse`, iteration=0 |
| Файлы | Добавить через `task.upload_artifact` существующие model.joblib и manifest.json под такими же именами |
| Ошибка | Пропустить исключение обучения вызывающему коду. Не выдавать сбой за успешный результат |

Возвращаемое значение функции не оценивается. Файлы `metrics.json` и `split.json` также остаются в output, но обязательные загружаемые артефакты этого задания — модель и манифест. Разбор методов SDK есть в [самостоятельном примере](../../README.md#самостоятельный-пример-sdk). Он использует отдельные маленькие данные и не содержит реализацию этой функции.

## Небольшой пример входных файлов и записи

Для иллюстрации формы данных предположим, что после вызова `housing.train.train(data_path, output_dir, 17)` что в каталоге появились такие фрагменты JSON:

```json
{"seed": 17, "data_sha256": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa"}
```

Это условный фрагмент `manifest.json`: повторяющиеся `a` только показывают длину SHA-256. В настоящем файле checksum вычислен по байтам CSV. Условные метрики того же обучения:

```json
{"candidate": {"test": {"mae": 0.31, "rmse": 0.57}}}
```

Тогда в `task.connect` передаются `seed=17` и этот фактический SHA-256. Logger получает события `("quality", "mae", 0.31, 0)` и `("quality", "rmse", 0.57, 0)`, где последний элемент — iteration. Под именами `model.joblib` и `manifest.json` загружаются реальные файлы из `output_dir`. Наблюдаемый результат функции — эти вызовы SDK и созданные train файлы. Конкретное возвращаемое значение контрактом не закреплено.

## Проверка функции без SDK

Из корня курса в основном тестовом окружении:

```bash
make task TASK=06-clearml/01-offline
```

Тесты подставляют маленькую замену функции обучения и объект с методами SDK. Это позволяет проверить твою логику без сервера, установленного ClearML и повторного обучения модели при каждом запуске pytest.

Проверяются пути и seed вызова обучения, чтение разных метрик из его файлов, правильные файлы для загрузки и проброс ошибки. Отдельно проверяется, что обвязка закрывает Task и после успеха, и после исключения.

До реализации `train_and_log` завершается `NotImplementedError`, а тесты готового `finally` могут пройти. Это подтверждает соединение компонентов, но настоящий запуск SDK проверяется следующим шагом.

## Запуск с настоящим ClearML

Подготовь [окружение модуля](../../README.md#подготовка-к-заданиям) с `labs/clearml/requirements.txt` и установленным пакетом housing. Активируй его и запусти из корня:

```bash
CLEARML_OFFLINE_MODE=1 python modules/06-clearml/tasks/01-offline/solution.py --data work/housing.csv --output modules/06-clearml/tasks/01-offline/output --seed 42
find modules/06-clearml/tasks/01-offline/output -maxdepth 1 -type f
```

CLI-параметры и режимы:

| Вход | Формат | Смысл и источник |
|---|---|---|
| `--data` | Путь, обязательный | Входной CSV, например `work/housing.csv` |
| `--output` | Путь, обязательный | Отдельный каталог результатов, например `work/clearml-run-1` |
| `--seed` | Целое, по умолчанию `42` | Передаётся в `train_and_log` |
| `CLEARML_OFFLINE_MODE` | `1` или `0`. Локально по умолчанию `1` | Включает локальную запись до `Task.init`. Для online-запуска из темы 02 задаётся `0` |

Под Agent `Task.running_locally()` ложно, поэтому обвязка не принуждает remote Task к offline-режиму. Если SDK отсутствует, `main()` поднимает `RuntimeError` с командой установки. После создания Task готовый `finally` вызывает `close()` и при успехе, и при исключении. Исключение обучения при этом не скрывается.

Переменная `CLEARML_OFFLINE_MODE=1` выбирает локальную запись. Каталог output принадлежит этому запуску. ClearML использует отдельный cache для своей сессии. Для повторного независимого опыта можно передать другой `--output`.

После успешного обучения в output находятся:

```text
model.joblib
metrics.json
manifest.json
split.json
```

SDK печатает ID и путь offline-сессии. В ней должны присутствовать seed, контрольная сумма CSV, два числовых ряда и два добавленных файла. Метрики совпадают с созданным metrics.json. Значения зависят от твоей реализации и данных, поэтому заранее заданного «правильного MAE» здесь нет.

## Если что-то пошло не так

- `NotImplementedError` из обучения означает, что модуль 01 ещё не завершён. Сначала проверь train отдельно.
- Нет metrics.json — проверь путь output и завершение обучения до вызовов logger.
- Числа в сессии расходятся с файлом — проверь раздел `candidate.test`, единицы и отсутствие захардкоженных значений.
- Локальная сессия есть, в Web UI пусто — это ожидаемо для offline-режима. Чтобы показать её на сервере, нужен импорт. Порядок описан в [официальной инструкции](https://clear.ml/docs/latest/docs/guides/set_offline/).

Сессия с записью исключения не подтверждает успешное обучение. Код CLI должен остаться ненулевым, а частичный output не использоваться как готовая модель. Этот сценарий подробнее разобран в [теме отказов](../03-comparison-failure/README.md).

Сохрани нужные результаты и архив SDK для дальнейшего использования. Серверов в этом задании нет. Остановка окружения — `deactivate`. Локальный запуск не демонстрирует очередь: к ней переходим в [следующем руководстве](../02-agent/README.md).

## Автоматическая проверка настоящего offline SDK

В среде с `labs/clearml/requirements.txt` из корня курса:

```bash
MLOPS_RUN_SDK=1 python -m pytest modules/06-clearml/tasks/01-offline/test_task.py -m sdk -q
```

Тест подставляет два разных результата на границе `housing.train.train`. Создание Task, запись параметров и метрик, загрузку файлов и сохранение сессии выполняет настоящий ClearML 1.18.0. Проверка читает созданные SDK `task.json`, `metrics.jsonl`, output artifact metadata/hash и байты копий файлов. Она обнаруживает постоянные метрики, неверный seed/checksum и отсутствие реального upload. Fake SDK из быстрых тестов здесь не используется. Формат offline-сессии закреплён по [исходнику SDK](https://github.com/clearml/clearml/blob/v1.18.0/clearml/backend_interface/task/task.py).

Subprocess изолирует глобальную Task, cache/config находятся только в pytest временном каталоге и очищаются вместе с ним. Сетевых записей нет. Флаги integration и writes этому локальному тесту не нужны. Тест проверяет SDK-обвязку и не заменяет запуск твоего настоящего housing.train на CSV, описанный выше, либо опыт очереди/Agent из следующей темы. Заготовка ожидаемо падает с `NotImplementedError` даже с установленным SDK.
