# ClearML: сравнить результаты и проверить отказ

[Модуль и подготовка](../../README.md#подготовка-к-заданиям) · [Все задания модуля](../../README.md#задания) · [SETUP](../../../../SETUP.md)

## Что предстоит сделать

MLflow и ClearML позволяют сохранять сведения об обучении, а Airflow помогает организовать зависимые шаги. В этом руководстве используй уже реализованные CLI: выполни одну конфигурацию Housing через обе системы, сравни выходные файлы, затем временно добавь исключение в свою `train` в [ML-notebook](../../../01-ml/housing.ipynb). После сохранения notebook проверь ненулевой код CLI и успешный повтор после удаления исключения. Новых функций и сервисов сравнения не требуется.

Если в MLflow запустить Ridge, а в ClearML — RandomForest на другом split, результаты будут различаться по причинам, не связанным с системой учёта. Поэтому здесь фиксируем данные, код обучения, конфигурацию и split, а затем смотрим, как каждый инструмент представляет полученную работу. Объяснение их ролей — в [теории модуля](../../README.md#clearml-mlflow-и-airflow-на-одном-сценарии).

Отдельно проверим ошибку. Для эксплуатации важно различать «сведения о запуске сохранились» и «модель успешно обучилась». Сессия, в которой записано исключение, может быть полезна для разбора сбоя, но её нельзя публиковать как готовый результат.

## Что нужно подготовить

- Завершённую [offline-интеграцию](../01-offline/README.md).
- MLflow из [модуля 04](../../../04-mlflow/README.md) с запуском той же конфигурации обучения.
- Один CSV, одинаковые seed, split, настройки модели и версии библиотек.
- Для сценария с Agent — выполненное [руководство по очереди](../02-agent/README.md) на совместимой машине.

Это руководство с проверкой результатов существующих программ. Письменную сравнительную таблицу, JSON-подтверждение и отдельную Python-реализацию здесь создавать не требуется.

## Сопоставить входы и результаты

Проверь доступность MLflow и выполни локальный ClearML-запуск из корня курса в соответствующем окружении:

```bash
curl --fail --max-time 10 http://127.0.0.1:5001/health
CLEARML_OFFLINE_MODE=1 python modules/06-clearml/tasks/01-offline/solution.py --data work/housing.csv --output modules/06-clearml/tasks/03-comparison-failure/output --seed 42
```

Проверка health отвечает только на вопрос о доступности MLflow. Сам запуск MLflow выполняется по модулю 04. Эта команда ClearML не записывает данные одновременно в обе системы.

Открой результаты MLflow и offline-сессию ClearML либо её импортированную копию на Server. Импорт нужен только для просмотра offline-записи в Web UI. Его порядок приведён в [официальном руководстве](https://clear.ml/docs/latest/docs/guides/set_offline/).

| Что сравнить | Корректный результат |
|---|---|
| SHA-256 CSV и split | Совпадают. Одинаковое имя файла само по себе недостаточно |
| Настройки модели и seed | Соответствуют одной конфигурации обучения |
| MAE/RMSE | Численно совпадают в пределах принятого допуска |
| Прогнозы на фиксированных строках | Совпадают с допусками проекта: rtol=1e-6, atol=1e-8 |
| Файлы | У обоих запусков доступны собственная модель и сведения о её происхождении |

ID Task и run принадлежат разным системам и не обязаны совпадать. Манифесты могут содержать разные идентификаторы, а pickle/joblib — различаться байтами при эквивалентных прогнозах. Поэтому сравнение размеров или хешей двух модельных файлов не заменяет сравнение их поведения.

Дальше посмотри на один процесс с трёх сторон: где видны метрики, как определяется версия модели, кто запускает код и где видно повтор шага после ошибки. В локальном опыте без Agent исполнителем остаётся твой Python-процесс. Очередь этим опытом не проверяется.

## Контролируемая ошибка обучения

Для опыта используй отдельный output, чтобы не затронуть рабочую модель. В своей функции обучения временно введи:

```python
raise RuntimeError("injected training failure")
```

Размести исключение до сохранения готовой модели и сохрани notebook на диск, чтобы адаптер загрузил изменённое определение `train`. Это искусственный сбой, а не постоянная часть реализации. Запусти:

```bash
CLEARML_OFFLINE_MODE=1 python modules/06-clearml/tasks/01-offline/solution.py --data work/housing.csv --output modules/06-clearml/tasks/03-comparison-failure/failed-output --seed 42
echo $?
```

`echo $?` нужно выполнить непосредственно после Python-команды в том же shell: он показывает её код завершения. Ожидается ненулевое число и сообщение `injected training failure` в диагностике Python. Точное значение кода здесь не закрепляется.

Проверь три независимых результата:

1. Ошибка дошла до вызывающего процесса, а не была скрыта обработчиком исключений.
2. Обвязка выполнила `task.close()` в finally. offline-сессия сохраняется для просмотра, если SDK завершил её запись.
3. В новом output нет модели, ошибочно представленной как успешно обученная. Содержимое такого каталога не используется для выкладки.

Закрытая Task и существующий архив не являются проверкой успешности обучения. Итог оценивается по коду завершения и действительным результатам. Не предполагается, что ручной вызов close сам выберет нужный бизнес-статус для любого варианта ошибки.

Убери инъекцию и повтори запуск с новым output. Теперь ожидаются код 0, созданные файлы и реальные метрики. Это и есть восстановление: программа снова выполняет работу и даёт проверяемый результат, а не просто перестаёт печатать исключение.

## Если проверяешь отказ Agent

Этот опыт выполняется только со своим исполнителем и отдельным клоном Task. Сначала дождись фактического старта процесса обучения. Если маленькая модель уже обучилась, воздействия на работающую задачу не было и результат ничего не говорит об отказоустойчивости.

Останови своего Agent и проверь, что произошло с исполняемым процессом и записью Task. Завершение процесса управления может обрабатываться по-разному. Нельзя заранее обещать один статус или немедленный повтор. Учитываются способ остановки, версия компонентов и настройки обнаружения недоступного исполнителя.

После восстановления проверь, возобновляется ли работа или создаётся новое выполнение. У них могут быть разные Task IDs. Для последующей публикации важны устойчивый ключ запуска и проверка качества из модулей 04–05: два выполнения не должны незаметно создать два выпуска одной модели.

Посмотреть число Task полезно, но окончательная проверка касается результата: какой файл создан, какие данные использованы и какая версия разрешена к выкладке. Если Agent был остановлен, а обучение продолжило работать, зафиксирован именно такой сценарий, а не предполагаемый «упавший запуск».

## Завершение

Верни свой код обучения в рабочее состояние и останови запущенные для опыта сервисы по инструкциям их модулей. Данные в отдельных output можно удалить после проверки. Готовую модель и необходимые сессии сохрани. Сравнение проверяется по файлам и выполнению программ. Отдельный отчёт не требуется.
