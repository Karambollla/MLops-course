# ClearML: передать обучение исполнителю через очередь

[Теория](../../README.md) · [Практика модуля](../../practice.md) · [Подсказки](../../hints.md)

## Какую задачу решаем

Локальная программа уже умеет обучать модель и сохранять сведения в offline-сессии. Теперь представим выделенную машину, на которой нужно выполнять такие запуски. Вместо ручного входа и запуска каждого обучения разместим подготовленную Task в очереди, а Agent получит её и запустит код.

В этой схеме Server предоставляет общее место хранения задач и результатов. Очередь хранит ожидание работы, Agent предоставляет исполнение на своей машине. Разбор компонентов и схема взаимодействия находятся в [теории](../../README.md#очередь-и-agent-исполнение-подготовленной-задачи).

Это руководство с командами и проверяемыми признаками. Автоматического теста удалённого исполнения у темы нет. Проверка HTTP-страницы Server и успешный локальный online-запуск — полезные этапы, но очередь считается проверенной, когда задачу действительно получил Agent.

## Среда и исходное состояние

Для серверного Compose-стенда курса нужна совместимая Linux x86_64-машина. Само housing-обучение выполняется на CPU, NVIDIA здесь не требуется. Без такой среды можно выполнить локальную тему SDK и изучить руководство без заявления об удалённом запуске.

Ниже Server, первый online-запуск и Agent находятся на одной Linux-машине. Поэтому `localhost` во всех трёх случаях указывает на неё. Команды выполняются из корня копии репозитория на этой машине. На ней должны быть:

- Завершённая [offline-интеграция](../01-offline/README.md) и обучение модуля 01.
- Docker Compose и ресурсы для серверного стенда из [SETUP](../../../../SETUP.md).
- Python 3.12 и отдельное окружение обучения с `labs/clearml/requirements.txt`.
- Доступные CSV и версия исходников. Нужные файлы и их происхождение должны быть известны до отправки работы.

## Запуск Server и настройка адресов

```bash
docker compose -f labs/clearml/compose.yaml up -d
curl --fail --max-time 10 http://localhost:8088/
clearml-init
```

Compose запускает серверные компоненты и их хранилища. Успех curl означает доступность Web UI. В `clearml-init` настрой адреса API `http://localhost:8008`, Web UI `http://localhost:8088` и файлового сервиса `http://localhost:8081`, затем введи ключи доступа, созданные в интерфейсе Server.

SDK сохраняет конфигурацию подключения вне исходников. Ключи доступа не добавляй в Git и не записывай как параметры обучения. Если Agent запускается под другим пользователем или с другой конфигурацией, ему потребуется собственная настройка подключения.

Для просмотра UI с другого компьютера можно настроить SSH-перенаправление трёх портов. Например, `USER` — имя SSH-пользователя, `HOST` — адрес Linux-машины:

```bash
ssh -N -L 8088:127.0.0.1:8088 -L 8008:127.0.0.1:8008 -L 8081:127.0.0.1:8081 USER@HOST
```

Браузер обращается к локальным портам туннеля, а SDK и Agent на Linux — к Server на той же машине. Открывать серверные порты в интернет для этой лабораторной не требуется.

## Подготовка точки входа

Точка входа — Python-файл, с которого Agent начинает исполнение. SDK импортируется в начале модуля задания, до `argparse.parse_args()`, чтобы учитывать и переопределять CLI-параметры. Дополнительно исполнителю нужно найти локальный пакет `course_tasks`, через который подключаются учебные функции.

Создай в корне своей реализации `clearml_entry.py`. Он вызывает существующую учебную функцию main, не дублируя обучение:

```python
from pathlib import Path
import sys

# Локальный пакет доступен из checkout, даже если не установлен из PyPI.
sys.path.insert(0, str(Path(__file__).resolve().parent / "labs" / "housing" / "src"))
from course_tasks import load_task

if __name__ == "__main__":
    load_task("06-clearml/01-offline").main()
```

Строка с `sys.path` добавляет исходники локального пакета в путь поиска Python. `load_task` загружает модуль задания вместе с его импортами, после чего вызывается `main()`. Поэтому SDK подключается до разбора аргументов. Это подготовка исполнения: функция `train_and_log` и её контракт остаются прежними.

Файл точки входа и твоя реализация должны быть сохранены в доступном Agent Git-репозитории. Проверь версию кода, которую показывает ClearML. Git не переносит исключённый из него `work/housing.csv`: данные нужно сделать доступными на машине исполнения отдельно.

## Первый online-запуск и подготовка клона

В окружении обучения выполни:

```bash
CLEARML_OFFLINE_MODE=0 python clearml_entry.py --data work/housing.csv --output modules/06-clearml/tasks/02-agent/output --seed 42
```

Теперь SDK отправляет сведения на Server. Открой Task в UI: проверь параметры, реальные MAE/RMSE и артефакты. Этот запуск выполнен вручную; он нужен как исходная запись с кодом, зависимостями и параметрами для повтора.

Проверь в конфигурации Task раздел CLI-параметров `Args`: должны быть data, output и seed. Если их нет, проверь порядок импорта в точке входа. Не считай поля `General`, добавленные через task.connect, автоматической заменой аргументам командной строки.

Клонируй Task в UI. Клон получает отдельный ID и может быть подготовлен к исполнению. Перед отправкой:

1. Проверь в Execution репозиторий, версию кода и точку входа `clearml_entry.py`.
2. Проверь Installed Packages — список Python-зависимостей. Используй закреплённые зависимости обучения из `labs/housing/requirements.txt` и SDK `clearml==1.18.0`. Локальный `housing-course` доступен через launcher; если SDK добавил его как пакет для PyPI, убери эту строку из зависимостей клона. Библиотеки самого ClearML Agent в окружение обучения переносить не нужно.
3. В `Args/data` задай абсолютный путь к тому же CSV на Linux, в `Args/output` — новый доступный для записи каталог. Оставь seed=42 для сравнения с исходным запуском.
4. Проверь совпадение SHA-256 данных. Не подменяй checksum в General вместо предоставления нужного файла. Путь меняется под среду исполнения, содержимое данных остаётся тем же.

Параметры подключённого словаря могут переопределяться при удалённом исполнении. Для этого опыта используй те же данные и seed; переопределение наблюдаемых метаданных не должно скрывать смену входных данных.

## Запуск Agent и очереди

Agent устанавливается отдельно от библиотек модели. Он создаёт среду для задачи, поэтому смешивать его зависимости с окружением обучения не нужно:

```bash
python3.12 -m venv .venv-clearml-agent
source .venv-clearml-agent/bin/activate
python -m pip install setuptools==80.9.0 clearml-agent==1.9.3
clearml-agent init
unset CLEARML_OFFLINE_MODE
clearml-agent daemon --queue default --foreground
```

В выбранном Agent 1.9.3 используется модуль pkg_resources; совместимый setuptools в этой команде предоставляет его. Это зависимость окружения исполнителя. `clearml-agent init` настраивает подключение Agent; укажи те же серверные адреса. `unset` убирает принудительный offline-режим из окружения, если он был установлен.

`daemon` запускает процесс прослушивания очереди, `--queue default` выбирает её имя, `--foreground` выводит журнал в текущий терминал. Убедись, что очередь default существует в UI и появился подключённый исполнитель. Затем отправь подготовленный клон в эту очередь.

## Как выглядит корректное исполнение

Наблюдай отдельные признаки, а не только итоговый зелёный статус:

| Этап | Ожидаемый признак |
|---|---|
| Отправка | Клон находится в очереди default |
| Получение | У Task указан исполнитель; в журнале Agent есть подготовка её кода и среды |
| Работа | Статус выполнения in_progress и сообщения настоящего обучения |
| Завершение | Completed при успешном исполнении, реальные метрики и файлы результата |
| Происхождение | Нужная версия кода, исходный SHA-256 и выбранный seed |

Сравни метрики и прогнозы исходного запуска и клона с допусками проекта. Идентификаторы Task и сериализованные файлы могут различаться; это не отменяет численной эквивалентности модели.

Если Task ждёт, сначала проверь совпадение очереди и доступность Agent. Если процесс уже стартовал, но упал, читай его исключение: отсутствие CSV, недоступная версия Python и ошибка установки пакетов требуют разных исправлений. Как устроена эта граница, поясняется в [теории](../../README.md#от-локального-запуска-к-повтору-на-другой-машине).

## Завершение

Agent останови через Ctrl+C. Сохрани необходимые результаты перед остановкой Server:

```bash
docker compose -f labs/clearml/compose.yaml down
```

Команда сохраняет именованные volumes с данными. Удаление volumes не является частью этого задания. При проверке отказа исполнителя не предполагается заранее фиксированный статус: это разбирается в [следующей теме](../03-comparison-failure/README.md).

## Обязательное подтверждение очереди и результата

Offline SDK-тест из темы 01 доказывает локальную запись SDK. Он не отправляет Task
в очередь. Для этого руководства нужен настоящий Server и поддерживаемый Linux
исполнитель (на macOS/Apple Silicon локальная offline-запись не является заменой
совместимому Agent; при отсутствии Linux выполни этот этап на отдельной машине).

В UI отправь **свой отдельный клон** в созданную очередь через Enqueue. Дождись
записи получения Task именно твоим Agent и запуска Python, затем проверь
созданные им Task metrics/artifacts: seed/SHA-256, реальные MAE/RMSE из metrics.json,
скачанные model.joblib и manifest.json. Сопоставь исходный и Agent Task ID, commit,
queue/worker и результат. Статус queued, подключённый worker или один Completed
без файлов обучения не засчитываются. Если платформа не позволяет выполнить
Agent, этап остаётся невыполненным: не подменяй его offline Task, fake queue или
ожидаемым «success». Официальный путь очереди:
[Task.enqueue SDK](https://clear.ml/docs/latest/docs/references/sdk/task/#enqueue)
и [ClearML Agent](https://clear.ml/docs/latest/docs/clearml_agent/).

Останови только своего Agent; архивируй/удаляй только созданный для опыта клон и
его результаты после проверки. Не очищай общую очередь и не удаляй чужие Tasks.
