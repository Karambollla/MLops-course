## Зачем считать метрики отдельно от поиска

HTTP 200 и два документа в ответе не говорят, подходят ли они пользователю. Нужна функция, которая сравнивает ранжированные IDs с независимыми qrels. [Разбор метрик](../../README.md#качество-выдачи-и-разобранные-метрики) показывает, откуда берутся числители, знаменатели и позиции.

Реализуй одну функцию в соседнем [solution.py](solution.py). Подготовлены фиксированные тесты и `labs/search/queries.json`. Для функции не нужны Qdrant и embedding-модель: вход — два списка IDs и k, выход — три числа. Это CPU-задача в [основном окружении](../../../../SETUP.md). Полученную функцию затем можно использовать для выдачи первого задания.

## Вход и ожидаемый результат

Разберём сбой поиска по вопросу о credentials: разметчик выбрал IDs 7 (Vault) и 8 (срок жизни credentials), а поиск поставил на первое место документ 5 (Prometheus), затем 8. Поэтому `retrieved=[5,8]`, `relevant=[7,8]`, `k=2`. Это пример ошибки ранжирования на существующих IDs корпуса.

```python
def ranking_metrics(retrieved: list, relevant: list, k: int) -> dict[str, float]:
    ...
```

| Параметр | Тип | Формат и смысл | Откуда взять | Пример |
|---|---|---|---|---|
| `retrieved` | `list` | IDs в порядке ранжирования, включая возможные повторы | `[hit["id"] for hit in query_documents(...)]` или тестовый список | `[5,8]` |
| `relevant` | `list` | IDs подходящих документов для этого запроса. Это не scores | Поле `relevant` из `labs/search/queries.json` | `[7,8]` |
| `k` | `int` | Число первых позиций для оценки, положительное, без `bool` | Выбранная глубина сравнения | `2` |

Для этих входов результат равен `{"recall":0.5,"precision":0.5,"mrr":0.5}`. Типы IDs должны совпадать: строка `"2"` и целое `2` не являются одним ID. Сетевые выдачи соседних модулей приводятся к `int` при разборе ответа.

## Технический контракт

Реализуй `ranking_metrics(retrieved, relevant, k) -> dict[str,float]` с ключами `recall`, `precision`, `mrr`.

Рассматриваются первые k позиций исходной выдачи. Один ID увеличивает число попаданий только один раз. Recall делится на число уникальных relevant IDs, precision — на k даже при короткой выдаче. `mrr` здесь означает reciprocal rank одного запроса: обратную исходную позицию первого релевантного результата в top-k. Среднее по нескольким запросам вычисляется уже снаружи. Для пустой разметки или отсутствия попаданий соответствующие значения нулевые. k — положительное целое без bool. Неверное k вызывает ValueError.

Сначала возьми первые k позиций, затем посчитай уникальные попадания и исходную позицию первого ответа. Для `[7,7,8]`, relevant `[7,8]`, k=2 третья позиция не рассматривается: recall=0.5, precision=0.5, mrr=1.0. Для `[5,8]` с той же разметкой — recall=0.5, precision=0.5, mrr=0.5. Пустая выдача даёт три нуля. Это примеры контракта, не готовый алгоритм.

## Проверка и применение

```bash
make task TASK=13-qdrant/02-evaluation
```

Тесты вызывают функцию напрямую. Отдельного CLI нет. Они проверяют ручные расчёты, дубликаты, короткую выдачу и неверный k. До реализации функция даёт `NotImplementedError`. После unit-проверки подай выдачи первого задания и relevant из `queries.json`. На четырёх ручных запросах ожидается Recall@2=1 по построению данных. Это проверка соединения компонентов. [ANN recall и смысловая релевантность](../../README.md#exact-и-approximate-search) проверяют разные свойства.

Для эксперимента усредняй метрики по одним и тем же запросам и сохраняй исходные IDs, k и qrels. Не меняй разметку ради улучшения числа. Функция не управляет стендом: если Qdrant был запущен отдельно, останови его по [инструкции остановки](../../README.md#остановка-стенда).

Integration/writes тест первого задания уже соединяет эти шаги: он создаёт уникальную коллекцию через твою index_documents, получает query_documents по всем queries и передаёт фактические IDs в твою ranking_metrics. Для запуска нужны оба флага MLOPS_RUN_INTEGRATION=1/MLOPS_RUN_WRITES=1 и завершённое первое задание. Команда находится в его README. Локальные unit-тесты метрик не требуют SDK.
