# Потоковый JSONL и командная строка

[Подготовка](../../README.md#подготовка-к-заданиям) · [Все задания](../../README.md#задания) · [Теория JSONL](../../README.md#построчное-чтение-и-контракт-cli)

## Зачем отделять формат от расчёта

В [предыдущей теме](../01-records/README.md) функция работала со словарями в памяти. Теперь записи приходят из файла, который может быть большим или повреждённым. Нужно сохранить одно правило расчёта и добавить границу чтения: корректный JSON-объект передаётся агрегатору, повреждённая строка останавливает обработку с понятным номером. Механика описана в [разделе про JSONL и CLI](../../README.md#построчное-чтение-и-контракт-cli).

## Что уже есть и что добавить

Нужна реализованная `summarize` первой темы. Здесь предоставлены сигнатуры итератора, обработки пути и `main`, а также два файла в `fixtures/`. Реализуй ленивое декодирование, повторное использование агрегатора и перевод ожидаемой ошибки в stderr/exit code. Накопление всех строк через `read`, `readlines` или `list` нарушит цель потоковой обработки даже при правильном среднем.

Вход из строк `{"duration": 2}`, `{"duration": "bad"}`, `{"duration": 4}` синтаксически целиком корректен: среднее 3.0 по двум значениям. Если заменить вторую строку на `broken`, сводки быть не должно: итератор выдаёт первую запись, на втором запросе поднимает `ValueError` с номером 2, CLI завершает работу ненулевым кодом. Третью строку после ошибки читать не нужно. Так проверяется граница между плохим полем и плохим форматом, а не только итоговый JSON.

## Подготовка

Активируй основное окружение по [инструкции модуля](../../README.md#подготовка-к-заданиям) и сначала реализуй `summarize` из первого задания. Для чтения JSONL используются стандартные `json`, `argparse` и `Path`. Docker и внешние серверы не нужны.

## Что реализовать

Редактируй [solution.py](solution.py). Предоставлены импорты, три заготовки и вызов `main()` под `if __name__ == "__main__"`. Функции отвечают за разные границы: чтение строк, обработку файла и интерфейс командной строки.

### `iter_records`: декодировать поток строк

```python
def iter_records(stream: Iterable[str]) -> Iterator[dict]:
    ...
```

| Аргумент | Тип и формат | Откуда берётся и зачем нужен | Пример |
|---|---|---|---|
| `stream` | Итерируемый источник строк `Iterable[str]` | Открытый текстовый файл или небольшой список строк из теста. Нужно читать его последовательно, без загрузки целиком | `['{"duration": 2}\n', '{"duration": 4}\n']` |

Возвращается ленивый итератор словарей. Одна строка JSONL должна содержать ровно один JSON-объект. Пустая строка, повреждённый JSON или JSON-значение другого типа вызывают `ValueError` с номером строки, начиная с 1. Массив `[]`, число `7`, строка `"text"`, `true` и `null` сами по себе допустимы в JSON, но не соответствуют формату записи этого задания.

Ошибка должна возникать при чтении соответствующей строки из итератора. После неё следующие строки не читаются. Например, после одной корректной строки и строки `broken` потребитель получит первый словарь, а на следующем шаге — исключение с номером 2.

### `summarize_file`: связать файл с агрегатором

```python
def summarize_file(path: Path) -> dict:
    ...
```

| Аргумент | Тип и формат | Откуда берётся и зачем нужен | Пример |
|---|---|---|---|
| `path` | `pathlib.Path` к JSONL-файлу | В CLI получается из позиционного аргумента. Функция открывает этот файл как текст UTF-8 | `Path("modules/00-python/tasks/02-jsonl-cli/fixtures/valid.jsonl")` |

Открой файл и передай поток в `iter_records`. Полученные словари направь в `summarize` первого задания через подготовленный `load_task`. Функция возвращает его сводку `{"count": ..., "mean": ...}`. Не дублируй правила фильтрации `duration` во втором задании.

Не используй `read`, `readlines` или `list` для накопления всего файла. Если реализация `summarize` пока требует список, сделай её пригодной для однопроходного итератора. Договорённости о допустимых значениях и результате остаются прежними.

Повреждённая строка прерывает расчёт с `ValueError`. Корректный JSON-объект с неверным `duration` продолжает обработку и отфильтровывается агрегатором.

### `main`: разобрать команду и вывести результат

```python
def main() -> None:
    ...
```

`main() -> None` — точка входа программы. Её не вызывают как `main(path)`: при запуске Python путь уже находится в `sys.argv`. Например, команда ниже передаст один позиционный аргумент — строку пути к JSONL:

```bash
python modules/00-python/tasks/02-jsonl-cli/solution.py modules/00-python/tasks/02-jsonl-cli/fixtures/valid.jsonl
```

Внутри `main` настрой `argparse`: обязательный позиционный `path` преобразуется в `Path`. В `summarize_file` передаётся этот `Path`, а не весь `sys.argv` и не содержимое файла. Относительный путь разрешается от текущей рабочей директории. Если путь содержит пробелы, заключи его в кавычки.

Цепочка обработки:

1. `main()` разбирает аргументы CLI и вызывает `summarize_file(path)`.
2. `summarize_file` открывает файл в UTF-8, передаёт поток строк в `iter_records`, а полученный итератор — в `summarize` первого задания.
3. `iter_records` выдаёт словари по одному и останавливается при ошибке формата. `summarize` фильтрует значения `duration` и вычисляет сводку.
4. `main` сериализует готовый словарь в JSON и печатает его в stdout. Функция возвращает `None`. Результат вычисления передаётся пользователю через stdout, а не через `return`.

## Формат вывода

В `fixtures/valid.jsonl` находятся:

```jsonl
{"duration":2}
{"duration":4}
{"duration":false}
```

После реализации команда выше выводит **один JSON-объект**, без приветствий, пояснений и Python-представления словаря:

```json
{"count": 2, "mean": 3.0}
```

`count` — количество пригодных значений, а не число строк. Здесь `false` исключается по контракту предыдущего задания. `mean` — среднее этих значений: `(2 + 4) / 2`. Пробелы между JSON-полями несущественны. Python-строка с одинарными кавычками не является JSON. Для пустого файла или отсутствия пригодных значений вывод — `{"count": 0, "mean": null}`: Python `None` сериализуется как JSON `null`.

| Ситуация | stdout | stderr | Код завершения |
|---|---|---|---|
| Корректный JSONL | Единственный JSON со сводкой | Пусто | `0` |
| Пустой файл | `{"count": 0, "mean": null}` | Пусто | `0` |
| Некорректное поле `duration` | Сводка без этого значения | Пусто | `0` |
| Повреждённая JSON-строка или JSON не-object | Без сводки | Сообщение с номером строки, без traceback | Ненулевой |

Для `fixtures/broken.jsonl` допустимый пример сообщения — `Ошибка в строке 2: некорректный JSON`. Точная формулировка свободная, но номер строки должен быть понятен. Не печатай частичную успешную сводку и не продолжай чтение после повреждённой строки. Обычный `return 1` из `main()` сам по себе не задаст код завершения процесса: используй механизм завершения с ненулевым кодом.

## Проверка функций

Из корня репозитория:

```bash
make task TASK=00-python/02-jsonl-cli
```

Тесты функций работают offline на маленьких входах и временных файлах. До реализации ожидается `NotImplementedError`. Ошибка импорта означает проблему подготовки среды. Проверка функций не заменяет описанный опыт на данных или стенде.

Пример запуска через runner из корня курса. Аргумент после `--` указывает путь к JSONL-файлу:

```bash
python scripts/run_task.py run 00-python/02-jsonl-cli -- modules/00-python/tasks/02-jsonl-cli/fixtures/valid.jsonl
```

Здесь `run` и `00-python/02-jsonl-cli` относятся к runner, а разделитель `--` обозначает начало аргументов твоего CLI. Сам `--` не попадает в `argparse` задания. Runner выполняет задание из корня курса. При прямом запуске относительные пути отсчитываются от текущей директории терминала.

## Пример корректного результата

Для fixtures/valid.jsonl CLI печатает JSON `{"count": 2, "mean": 3.0}` и завершается с кодом 0. Для broken.jsonl — ненулевой код, сообщение о строке 2 в stderr, без успешной JSON-сводки в stdout.
