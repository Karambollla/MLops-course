# Первый полезный текст: TTFT и TPOT

[Модуль и подготовка](../../README.md#подготовка-к-заданиям) · [Все задания модуля](../../README.md#задания) · [Окружение курса](../../../../SETUP.md)

## Зачем измерять первый полезный content

Streaming может передать role сразу, а текст — значительно позже. Если поставить TTFT по первой сетевой активности, сравнение engines будет неверным. Определения и численный пример находятся в [TTFT/TPOT](../../README.md#ttft-tpot-и-throughput), параметры стенда — в [разборе Compose](../../README.md#что-означают-параметры-compose).

В соседнем [solution.py](solution.py) реализуй только `request_metrics`. Подготовлены числовые тесты. `benchmark.json` — пустой технический шаблон, Compose в `labs/llm/` — материал для чтения. Функцию метрик можно проверить на локальном CPU в [основном окружении](../../../../SETUP.md). В этой теме выполняются только локальные расчёты. API-бенчмарки исключены из практики.

## Шаг 1. Прочитать временную шкалу

Пусть отсчёт начался в 0.9 секунды. В 1.0 пришло служебное событие без текста, в 1.15 — полезный content, в 1.5 — окончание. По условию ответ содержит 4 tokens. Эти подготовленные значения нужны для расчёта метрики. Сетевого запроса за ними нет.

```python
def request_metrics(started: float, events: list[dict], ended: float, output_tokens: int) -> dict:
    ...
```

| Параметр | Тип | Формат и смысл | Откуда взять | Пример |
|---|---|---|---|---|
| `started` | `float` | Время начала в секундах единой монотонной шкалы | Подготовленный числовой пример из теста | `0.9` |
| `events` | `list[dict]` | Упорядоченные события с `time` в секундах и `content`-строкой | Подготовленный список, без LLM endpoint | `[{"time":1.0,"content":""},{"time":1.15,"content":"hello"}]` |
| `ended` | `float` | Время завершения на той же шкале | Подготовленный числовой пример | `1.5` |
| `output_tokens` | `int` | Положительное число сгенерированных tokens, не число событий | Условие примера. В теории источник — usage или тот же tokenizer | `4` |

Результат для примера:

```python
{"ttft_ms": 250.0, "total_ms": 600.0, "output_tokens": 4, "tpot_ms": 116.66666666666667}
```

Сравнивай дробные значения с допуском. Единицы результата — миллисекунды, исходных timestamps — секунды. Если content только один и output_tokens=1, `tpot_ms` равен `None`.

## Шаг 2. Рассчитать интервалы и проверить порядок

Реализуй `request_metrics(started,events,ended,output_tokens) -> dict`. Времена — секунды одного monotonic clock, events — упорядоченные `{time,content}` внутри интервала started..ended. Результат содержит `ttft_ms`, `total_ms`, `output_tokens`, `tpot_ms`. Первый полезный event имеет непустой content. Служебное пустое поле не подходит.

TTFT — интервал от started до первого content. Total — started..ended. TPOT=`(total_ms-ttft_ms)/(output_tokens-1)`. При одном token TPOT=None. Нет полезного content, времена несогласованы или output_tokens неположительно — `ValueError`. Все события, включая пустые content, должны попадать в интервал started..ended и идти в неубывающем порядке. Завершение не может предшествовать началу. Не подменяй число output tokens количеством событий.

Для started=0.9, пустого content в 1.0, текста в 1.15, ended=1.5 и output_tokens=4 ожидаются TTFT=250 ms, total=600 ms, TPOT≈116.67 ms. Это пример определения, а не скорость Qwen.

## Связать метрику с устройством serving

В теории длинная очередь до prefill увеличивает ожидание первого текста, а длинный decode — оставшуюся длительность. Одно число total эти причины не разделяет. Прочитай [планирование cache](../../README.md#планирование-и-управление-cache) и [условия сравнения](../../README.md#протокол-честного-сравнения).

В практике используются только локальные числовые события тестов. Вызовы и имитации generation, streaming и benchmark к любым LLM endpoints исключены. Файлы Compose здесь не запускаются.
