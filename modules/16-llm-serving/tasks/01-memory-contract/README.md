# Память, SSE и корпус запросов

[Модуль и подготовка](../../README.md#подготовка-к-заданиям) · [Все задания модуля](../../README.md#задания) · [Окружение курса](../../../../SETUP.md)

## Что предстоит сделать

Нужно заранее отличить объём весов от растущего cache и полезный текст от служебных событий потока. Для этого достаточно CPU-расчётов и фиксированных строк протокола: скачивание модели и платные API не нужны. Прочитай [память](../../README.md#веса-и-kv-cache-в-байтах), [SSE-контракт](../../README.md#streaming-и-sse-контракт) и [определения tokens](../../README.md#tokens-prefill-и-decode).

В соседнем [solution.py](solution.py) реализуй три локальные функции. Подготовлены тесты и `prompts.json` с 20 текстами разной длины для разбора входного корпуса. Здесь вход — числа и строки, выход — числа байтов и content chunks. Нужны только [основное окружение](../../../../SETUP.md) и локальный CPU.

## Шаг 1. Отделить веса от памяти активных запросов

Для арифметики возьмём условную модель с 500 миллионами параметров в формате 2 байта на параметр. Отдельно зададим архитектуру attention: 24 слоя, 8 KV heads ширины 64. Один активный запрос хранит 2048 tokens. Эти условия дают входы функций ниже. Они не описывают Qwen из справочного Compose.

### `weights_bytes(parameters: int, bytes_per_parameter: int = 2) -> int`

| Параметр | Тип | Формат и смысл | Откуда взять | Пример |
|---|---|---|---|---|
| `parameters` | `int` | Количество обученных параметров модели, положительное, без `bool` | Конфигурация архитектуры или условие локального расчёта | `500_000_000` |
| `bytes_per_parameter` | `int` | Байт на один параметр, положительное, без `bool` | Выбранный формат хранения весов | `2` для FP16/BF16 |

Результат — целое число байтов весов, без cache и runtime. Для примера это `1_000_000_000`. Чтобы получить GiB, дели результат на `2**30`. GB используют делитель `10**9`, это другая единица. Ноль, отрицательное, дробное число и `bool` в любом аргументе вызывают `ValueError`.

### `kv_cache_bytes(layers: int, kv_heads: int, head_dim: int, context: int, concurrency: int, bytes_per_element: int = 2) -> int`

| Параметр | Тип | Формат и смысл | Откуда взять | Пример |
|---|---|---|---|---|
| `layers` | `int` | Число attention-слоёв | Архитектура модели или условие примера | `24` |
| `kv_heads` | `int` | Число key/value heads. При GQA это не число query heads | Конфигурация attention | `8` |
| `head_dim` | `int` | Число элементов в одной голове | Архитектура attention | `64` |
| `context` | `int` | Число сохранённых tokens на одну последовательность | Условие оценки длины контекста | `2048` |
| `concurrency` | `int` | Число одновременно живущих последовательностей этой длины | Условие оценки нагрузки | `1` |
| `bytes_per_element` | `int` | Байт на один элемент key/value | Формат хранения cache | `2` |

Все шесть аргументов — положительные целые без `bool`. Неверное значение любого аргумента вызывает `ValueError`. Формула и смысл множителя key/value разобраны в [теории памяти](../../README.md#веса-и-kv-cache-в-байтах).

Для примера результат `100_663_296` байт, при concurrency=8 — `805_306_368`. Формула предполагает полные одинаковые контексты и не включает buffers, allocator overhead или особенности scheduler. Это часть оценки памяти, а не подтверждение вместимости VRAM.

## Шаг 2. Извлечь текст из готовых SSE-строк

### `sse_contents(lines: list[str]) -> list[str]`

| Параметр | Тип | Формат и смысл | Откуда взять | Пример |
|---|---|---|---|---|
| `lines` | `list[str]` | Уже собранные полные строки. Каждая data-строка содержит один полный JSON event или `[DONE]` | Фиксированные тестовые данные, без сетевого запроса | `['data: {"choices":[{"delta":{"content":"Hi"}}]}', "data: [DONE]"]` |

Верни все непустые `choices[].delta.content` в порядке событий и choices. Для примера — `["Hi"]`. Один event может содержать несколько choices, а chunk может включать несколько слов. Количество chunks нельзя считать количеством tokens.

Пропускай пустые строки, heartbeat и role-only metadata. `[DONE]` немедленно завершает обработку: повреждённый JSON или error после него не читаются. Event с `error` и повреждённый JSON до DONE вызывают `ValueError`.

Допустим, в файле сохранены служебный heartbeat, роль сообщения, два текстовых фрагмента и признак окончания. Разбери такой локальный текст:

```text
: heartbeat
data: {"choices":[{"delta":{"role":"assistant"}}]}
data: {"choices":[{"delta":{"content":"Hel"}}]}
data: {"choices":[{"delta":{"content":"lo"}}]}
data: [DONE]
data: {broken
```

Результат — `["Hel","lo"]`. Parser не собирает сетевые фрагменты и не реализует весь стандарт многострочных SSE events. Это локальная обработка готового текста без обращения к LLM API.

## Проверка и использование результата

```bash
make task TASK=16-llm-serving/01-memory-contract
```

Тесты вызывают функции, CLI нет. `prompts.json` содержит объекты с `id` и `text`, а не SSE-строки. Он не передаётся в эти функции. Длина text в символах не равна числу tokens с chat template. Корпус остаётся материалом для теоретического разбора, API-запросы с ним не выполняются.

Сверь результаты памяти с 100663296 байт на один контекст и 805306368 байт на восемь, а parser — с `["Hel","lo"]`. Это локальные проверки формул и текста. Сервисов в задании нет, остановка не нужна.
