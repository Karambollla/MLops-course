# 16. vLLM, SGLang и TensorRT-LLM

[Программа](../../README.md) · [Практика](practice.md) · [Подсказки](hints.md)

## Инженерная задача и доступные маршруты

Обычная housing-модель выдаёт одно число на строку. Языковая модель выдаёт ответ постепенно: одни пользователи ждут короткую инструкцию, другие отправляют длинный документ. Нужно оценить, поместится ли модель в память, отличить сетевую активность от появления текста и сравнить serving engines на одной нагрузке.

**LLM** — языковая модель с большим числом обученных параметров. **Serving engine** загружает веса, планирует вычисления и управляет памятью генерации. vLLM и SGLang предоставляют HTTP-serving; TensorRT-LLM — стек исполнения/оптимизации для NVIDIA, который может работать через Triton backend. Результат этого модуля — понятный контракт запроса и проверяемые измерения, а не универсальный рейтинг движков.

Нужны HTTP/JSON, [tensor shapes и serving](../15-triton/README.md), базовое представление о матричных вычислениях. Вход CPU-части — числа размеров модели и строки SSE; выход — оценки памяти и метрики. Для неё не нужны веса, платные API или симуляция GPU. Реальные vLLM/SGLang и TensorRT-LLM запускаются дополнительно на совместимом Linux/NVIDIA стенде. Изучение конфигурации и unit-тесты не подтверждают практику GPU-serving.

## Tokens, prefill и decode

**Tokenizer** разбивает текст на tokens и сопоставляет им числовые IDs. Token не равен слову или сетевому chunk: слово может занимать несколько tokens, а chunk — содержать несколько tokens. Chat template добавляет служебное оформление сообщений user/assistant; оно тоже занимает контекст.

**Prompt** — вход модели вместе с таким оформлением. **Context** — последовательность tokens, которую модель учитывает; лимит обычно должен вместить вход и планируемый выход. **Prefill** обрабатывает prompt и формирует состояния attention. **Decode** последовательно генерирует новые tokens с использованием уже вычисленных состояний. Длинный prompt увеличивает prefill, длинный ответ — число decode steps.

Путь данных: `messages JSON → chat template/tokenizer → очередь → prefill → повторяющийся decode → detokenization → SSE content → клиент`. HTTP gateway может ограничить размер запроса и timeout, но управление tensors и cache остаётся у engine. По аналогии с Go API у сервера есть очередь и admission control; в отличие от простого stateless handler, память активного запроса растёт вместе с контекстом.

## Веса и KV cache в байтах

**Веса** — обученные параметры модели. Для грубой оценки: `parameters × bytes_per_parameter`. В FP16/BF16 элемент занимает 2 байта: 500000000 параметров требуют примерно 1000000000 байт, то есть 0.931 GiB. Для 7 млрд — 14000000000 байт, около 13.04 GiB. GB=10^9 байт, GiB=2^30 байт; различие единиц заметно при планировании VRAM.

**KV cache** хранит key/value tensors attention для уже обработанных tokens, чтобы decode не вычислял их заново. Для одинаковых полных последовательностей упрощённая оценка:

`2 × layers × kv_heads × head_dim × context × concurrency × bytes_per_element`

Множитель 2 означает key и value; layers — число слоёв; kv_heads — число голов key/value; head_dim — ширина головы; context — число сохранённых tokens на последовательность; concurrency — число таких одновременно живущих последовательностей. **GQA**, grouped-query attention, позволяет нескольким query heads использовать общие KV heads. Поэтому подмена kv_heads числом query heads завысит оценку.

Для layers=24, kv_heads=8, head_dim=64, context=2048, concurrency=1 и 2 байт: на token требуется `2×24×8×64×2=49152` байт, на последовательность — 100663296 байт, ровно 96 MiB. Восемь таких последовательностей требуют 805306368 байт, 768 MiB. Эти числа описывают условную архитектуру упражнения, а не паспорт Qwen из Compose.

Формула не включает временные tensors, allocator overhead, CUDA graphs, metadata квантования и особенности распределения cache. **Квантование** уменьшает точность представления весов или cache; выигрыш памяти нельзя переносить на весь процесс простым делением. VRAM — память GPU. Веса, едва помещающиеся в VRAM, не оставляют достаточного места для контекста. CPU-формула оценивает нижние составляющие, а реальный запуск проверяет вместимость и ошибки выделения памяти.

## Планирование и управление cache

**Continuous batching** позволяет добавлять новый запрос в набор активных последовательностей, когда другой закончил генерацию. Это отличается от ожидания завершения всего статического batch. **Paged KV storage** хранит cache блоками и уменьшает проблемы размещения разной длины последовательностей; не создаёт дополнительную физическую память. **Prefix caching** переиспользует состояния одинакового начала запросов. Если префиксы различаются, пользы может почти не быть.

Большая concurrency может повысить общий throughput, но увеличить очередь и TTFT. При перегрузке нужны лимиты активных запросов, очередь, timeout и отмена. Отмена HTTP-клиентом и фактическое освобождение cache — разные события; поведение проверяется у выбранного engine. Настройки двух engines не обязаны означать одинаковый объём свободной памяти.

## Streaming и SSE-контракт

**SSE**, Server-Sent Events, — поток текстовых событий поверх HTTP. В учебном контракте каждая строка `data:` содержит один полный JSON event. Настоящий SSE также допускает многострочные events и разбиение сетевых чтений посередине строки: перед вызовом учебного parser клиент должен собрать строки/events. Это не общий parser произвольного сетевого потока.

```text
: heartbeat

data: {"choices":[{"delta":{"role":"assistant"}}]}

data: {"choices":[{"delta":{"content":"Hel"}}]}

data: {"choices":[{"delta":{"content":"lo"}}]}

data: [DONE]
```

Heartbeat и role — служебная активность, полезного текста ещё нет. Parser упражнения возвращает `["Hel","lo"]`, завершение `[DONE]` останавливает чтение. Ошибка JSON до завершения или event с `error` — ошибка, а не успешный пустой ответ. После DONE данные не обрабатываются. `curl -N` отключает клиентское буферизование вывода, но само по себе не измеряет время tokens.

## TTFT, TPOT и throughput

**TTFT**, time to first token, на клиенте этого курса — время от отправки запроса до первого непустого content. Строго говоря, это первый полезный текстовый chunk: его границы не обязаны совпасть с одним token. **End-to-end latency** — время до завершения потока. Используй monotonic clock: его показания измеряют интервалы и не меняются при коррекции календарного времени.

Пусть started=0.9 s, служебное событие пришло в 1.0 s, первый content — в 1.15 s, ended=1.5 s, реально сгенерировано 4 tokens. TTFT=`(1.15-0.9)×1000=250 ms`, total=`(1.5-0.9)×1000=600 ms`. В упражнении **TPOT**, time per output token после первого, равен `(total_ms-ttft_ms)/(output_tokens-1)=350/3≈116.67 ms`. Для одного token знаменатель нулевой: возвращается None. Конец потока включает клиентские и сетевые расходы, поэтому такая TPOT — клиентская оценка, а не чистое время GPU decode.

**Inter-token latency** описывает интервалы между tokens; её нельзя точно восстановить, если один content chunk содержит несколько tokens. Число chunks не равно output_tokens. Бери фактический usage или tokenizer той же revision и явно указывай способ подсчёта.

**Throughput** требует общего wall time, а не усреднения `tokens/latency` отдельных запросов. Если за 2 s завершилось 4 запроса по 10 output tokens, получено 2 requests/s и 20 output tokens/s. Если входы суммарно содержали 80 tokens, total throughput=(80+40)/2=60 tokens/s. Эти арифметические примеры не являются GPU-измерениями. В отчётных данных всегда подписывай, какие tokens, завершения и ошибки входят в счётчик.

## Что означают параметры Compose

В `labs/llm/` закреплены vLLM v0.10.2 и SGLang v0.4.10.post2-cu126. Оба загружают публичную `Qwen/Qwen2.5-0.5B-Instruct` и публикуют имя `course-llm`. Последнее — alias API, а не model revision.

| Настройка | vLLM | SGLang | Смысл |
|---|---|---|---|
| Модель | `--model` | `--model-path` | Источник весов/tokenizer |
| Имя API | `--served-model-name course-llm` | То же | Значение `model` в request.json |
| Контекст | `--max-model-len 2048` | `--context-length 2048` | Лимит последовательности, который нужно согласовать с запросами |
| Память | `--gpu-memory-utilization 0.70` | `--mem-fraction-static 0.70` | Настройки планирования памяти конкретного engine; численно одинаковые значения не означают идентичные алгоритмы |
| Host port | `8000:8000` | `8000:30000` | Клиент использует 8000, внутренний SGLang — 30000 |

`gpus: all` передаёт доступные GPU контейнеру; оно не устанавливает драйвер или NVIDIA runtime. `model-cache` сохраняет скачанные файлы, `shm_size:2g` задаёт shared memory контейнера и не добавляет VRAM. SGLang слушает `0.0.0.0` внутри контейнера, host port ограничен loopback. Запускай движки по очереди.

Compose удобен для первого знакомства, но model revision в командах не закреплена. Перед итоговым сравнением используй одну immutable revision через поддерживаемый в этих версиях `--revision` и согласуй tokenizer. Разбор аргументов — в [vLLM 0.10.2 CLI](https://docs.vllm.ai/en/v0.10.2/cli/serve.html) и [ServerArgs SGLang выбранного тега](https://github.com/sgl-project/sglang/blob/v0.4.10.post2/python/sglang/srt/server_args.py). Cache сам по себе не доказывает, какая revision загружена.

В `request.json` `messages` — prompt, `max_tokens:64` — верхняя граница выхода, temperature=0 выбирает режим без температурной случайной выборки, `stream:true` включает поток. Модель может закончить раньше 64 tokens. Температура 0 не гарантирует одинаковый текст на разных kernels, hardware и engines. Совместимость endpoint не гарантирует поддержку всех параметров чужого API.

## Протокол честного сравнения

Используй 20 prompts из первого задания или фиксированный собственный корпус. Сначала отдельно выполни минимум 20 warmup-запросов, затем 100 измеряемых при concurrency 1 и 4 для каждого engine. Зафиксируй model/revision/tokenizer, dtype, quantization, context, входные/выходные длины, параметры генерации, hardware и runtime. Повторяющиеся префиксы и состояние cache должны быть сопоставимы: иначе проверяется ещё и преимущество прогретого cache.

Сохраняй timestamps/content events, фактические tokens, статусы и общую длительность серии. Сравни распределения TTFT/total, throughput и ошибки. Быстрый ответ с context error не является успешно сгенерированным ответом. Отдельно проверь oversized context, неизвестное имя модели и отмену. Контракт ошибок может различаться; наблюдаемые результаты важнее предположения об одном HTTP-коде.

## TensorRT-LLM и Triton

TensorRT-LLM может требовать преобразования checkpoint и сборки engine под выбранную модель и GPU. **Engine** — подготовленный исполняемый артефакт с настройками точности, shapes и других оптимизаций. **Checkpoint** — сохранённые веса/состояния модели; он ещё не engine. Triton backend загружает подготовленный комплект и предоставляет serving-контракт, иногда с preprocessing/postprocessing и ensemble — цепочкой связанных моделей.

В курсе используется образ `25.06-trtllm-python-py3` и [архивный guide 25.06](https://docs.nvidia.com/deeplearning/triton-inference-server/archives/triton-inference-server-2560/user-guide/docs/tensorrtllm_backend/README.html). `tensorrt-llm.sh` открывает shell в контейнере; build и server там не выполняются автоматически. В архивном quickstart встречаются иллюстративные команды с тегом 24.07: не переноси этот тег и связанные команды сборки в образ 25.06. Сначала сопоставь встроенные версии Triton/TensorRT-LLM с support matrix и используй соответствующие им примеры. Поддержку Qwen из предыдущего упражнения нельзя предполагать: выбирай модель и conversion path из этого релиза. Engine из другого релиза/GPU не считается совместимым без проверки; сохраняй build flags, версии и hash результата.

## Диагностика и границы доказательства

| Симптом | Что разделить |
|---|---|
| `nvidia-smi` работает, контейнер не видит GPU | Драйвер хоста, Docker GPU runtime и доступность устройств — разные уровни |
| OOM при длинном prompt | Веса уже загружены, но выросли KV cache/временные tensors; проверить длины и concurrency |
| `/v1/models` отвечает, генерация падает | Список моделей не проверяет конкретный prompt, context и decode |
| Первый chunk ранний, текста долго нет | Role/heartbeat не являются полезным content, TTFT ещё не наступил |
| throughput вырос, TTFT ухудшился | Больше запросов обрабатывается вместе; смотреть очередь и распределение latency |
| TensorRT container открыл shell | Это проверка среды, не сборка engine и не inference |

CPU-тесты проверяют формулы и обработку потока, а не реальные ресурсы или скорость. GPU-сравнение требует фактического стенда; без него сохраняется честная граница между пониманием механизма и измеренным поведением.
