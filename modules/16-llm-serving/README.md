# 16. vLLM, SGLang и TensorRT-LLM

[Программа](../../README.md) · [Задания](#задания) · [Подготовка](#подготовка-к-заданиям)

## Инженерная задача и доступные маршруты

После табличного сервиса Housing рассмотрим другую инженерную ситуацию — приложение, которое постепенно показывает текст ответа. Обычная housing-модель выдаёт одно число на строку. Языковая модель выдаёт ответ постепенно: одни пользователи ждут короткую инструкцию, другие отправляют длинный документ. Нужно понять, почему длинный документ требует больше памяти, когда пользователь увидит первый текст и какие условия сделали бы сравнение serving engines осмысленным.

**LLM** — языковая модель с большим числом обученных параметров. **Serving engine** загружает веса, планирует вычисления и управляет памятью генерации. vLLM и SGLang предоставляют HTTP-serving. TensorRT-LLM — стек исполнения/оптимизации для NVIDIA, который может работать через Triton backend. Результат этого модуля — понимание устройства serving и проверяемые локальные расчёты.

Практика ограничена теорией, локальными формулами памяти и разбором готовых SSE-строк/времён. Любые вызовы и имитации generation, streaming и benchmark к LLM endpoints исключены. Нужны HTTP/JSON, [tensor shapes и serving](../15-triton/README.md), базовое представление о матричных вычислениях. Вход CPU-части — числа размеров модели и строки SSE. Выход — оценки памяти и метрики. Файлы `labs/llm/` читаются как примеры устройства runtime. Запуск стенда, скачивание весов и доступ к GPU для заданий не требуются.

## Tokens, prefill и decode

Пользователь передаёт длинную инструкцию и просит краткое объяснение. Перед вычислением текст нужно представить входными числами. **Tokenizer** разбивает текст на tokens и сопоставляет им числовые IDs. Token не равен слову или сетевому chunk: слово может занимать несколько tokens, а chunk — содержать несколько tokens. Chat template добавляет служебное оформление сообщений user/assistant. Оно тоже занимает контекст.

После оформления получается **prompt**, полный вход модели. Учитываемая моделью последовательность tokens называется **контекстом**. Проверяя его лимит, нужно оставить место и для входа, и для планируемого ответа.

Чтобы начать отвечать, модель сначала обрабатывает весь prompt. Этот этап называется **prefill**: он формирует состояния attention, используемые при продолжении. Затем начинается **decode**, последовательная генерация новых tokens с использованием уже вычисленных состояний. Поэтому длинный документ увеличивает начальную работу, а длинный ответ — число шагов продолжения.

Путь данных: `messages JSON → chat template/tokenizer → очередь → prefill → повторяющийся decode → detokenization → SSE content → клиент`. HTTP gateway может ограничить размер запроса и timeout, но управление tensors и cache остаётся у engine. Admission control решает, какой запрос можно допустить к вычислению при текущей занятой памяти. Пока ответ растёт, активный запрос продолжает занимать состояния предыдущих tokens.

## Веса и KV cache в байтах

Сначала отделим постоянную часть памяти от зависящей от нагрузки. **Веса** — обученные параметры модели. Если в условной модели 500 миллионов параметров, размер её весов грубо оценивается как `parameters × bytes_per_parameter`. В FP16/BF16 элемент занимает 2 байта: 500000000 параметров требуют примерно 1000000000 байт, то есть 0.931 GiB. Для 7 млрд — 14000000000 байт, около 13.04 GiB. GB=10^9 байт, GiB=2^30 байт. Различие единиц заметно при планировании VRAM.

**KV cache** хранит key/value tensors attention для уже обработанных tokens, чтобы decode не вычислял их заново. Для одинаковых полных последовательностей упрощённая оценка:

`2 × layers × kv_heads × head_dim × context × concurrency × bytes_per_element`

Множитель 2 означает key и value. Layers — число слоёв. Kv_heads — число голов key/value. Head_dim — ширина головы. Context — число сохранённых tokens на последовательность. Concurrency — число таких одновременно живущих последовательностей. **GQA**, grouped-query attention, позволяет нескольким query heads использовать общие KV heads. Поэтому подмена kv_heads числом query heads завысит оценку.

Для расчёта упражнения возьмём условную архитектуру: 24 слоя, 8 KV heads ширины 64. Один активный запрос хранит 2048 tokens, каждый элемент key/value занимает 2 байта. Это входы `layers=24`, `kv_heads=8`, `head_dim=64`, `context=2048`, `concurrency=1`, `bytes_per_element=2`. Тогда на token требуется `2×24×8×64×2=49152` байт, на последовательность — 100663296 байт, ровно 96 MiB. Восемь таких последовательностей требуют 805306368 байт, 768 MiB. Эти числа описывают условную архитектуру упражнения, а не паспорт Qwen из Compose.

Формула не включает временные tensors, allocator overhead, CUDA graphs, metadata квантования и особенности распределения cache. **Квантование** уменьшает точность представления весов или cache. Выигрыш памяти нельзя переносить на весь процесс простым делением. VRAM — память GPU. Веса, едва помещающиеся в VRAM, не оставляют достаточного места для контекста. CPU-формула оценивает нижние составляющие, а реальный запуск проверяет вместимость и ошибки выделения памяти.

## Планирование и управление cache

Пока один пользователь ждёт длинный ответ, другой может уже закончить короткий. **Continuous batching** позволяет scheduler менять набор активных последовательностей между шагами генерации, добавляя новые запросы по мере доступности ресурсов. Это отличается от ожидания завершения всего статического batch. **Paged KV storage** хранит cache блоками и уменьшает проблемы размещения разной длины последовательностей. Не создаёт дополнительную физическую память. **Prefix caching** переиспользует состояния одинакового начала запросов. Если префиксы различаются, пользы может почти не быть.

Большая concurrency может повысить общий throughput, но увеличить очередь и TTFT. При перегрузке нужны лимиты активных запросов, очередь, timeout и отмена. Отмена HTTP-клиентом и фактическое освобождение cache — разные события. Поведение проверяется у выбранного engine. Настройки двух engines не обязаны означать одинаковый объём свободной памяти.

## Streaming и SSE-контракт

Интерфейс хочет показывать ответ по мере появления текста. **SSE**, Server-Sent Events, — поток текстовых событий поверх HTTP. В учебном контракте каждая строка `data:` содержит один полный JSON event. Настоящий SSE также допускает многострочные events и разбиение сетевых чтений посередине строки: перед вызовом учебного parser клиент должен собрать строки/events. Это не общий parser произвольного сетевого потока.

```text
: heartbeat

data: {"choices":[{"delta":{"role":"assistant"}}]}

data: {"choices":[{"delta":{"content":"Hel"}}]}

data: {"choices":[{"delta":{"content":"lo"}}]}

data: [DONE]
```

Heartbeat и role — служебная активность, полезного текста ещё нет. Parser упражнения возвращает `["Hel","lo"]`, завершение `[DONE]` останавливает чтение. Ошибка JSON до завершения или event с `error` — ошибка, а не успешный пустой ответ. После DONE данные не обрабатываются. Буферизация клиента может дополнительно задерживать показ текста. Подготовленные строки позволяют изучить формат без сетевого подключения.

## TTFT, TPOT и throughput

Пользователь может увидеть начало ответа быстро, но долго ждать его окончания. Одного времени завершения недостаточно, чтобы описать эти два впечатления. Поэтому отдельно отмечают отправку запроса, появление первого полезного текста и конец потока.

Интервал до первого полезного текста здесь называется **TTFT**, time to first token. На клиенте мы фактически видим первый непустой content chunk: его границы не обязаны совпасть с одним token. Полное время до завершения потока называется **end-to-end latency**. Для таких интервалов используют monotonic clock: его показания не меняются при коррекции календарного времени.

Разберём условную временную шкалу, подготовленную для арифметики функции. Начало запроса `started=0.9 s`, служебное событие — `1.0 s`, первый content — `1.15 s`, завершение `ended=1.5 s`. По условию ответ содержит 4 tokens. Это числа примера, а не запуск какого-либо engine. TTFT=`(1.15-0.9)×1000=250 ms`, total=`(1.5-0.9)×1000=600 ms`. В упражнении **TPOT**, time per output token после первого, равен `(total_ms-ttft_ms)/(output_tokens-1)=350/3≈116.67 ms`. Для одного token знаменатель нулевой: возвращается None. Конец потока включает клиентские и сетевые расходы, поэтому такая TPOT — клиентская оценка, а не чистое время GPU decode.

**Inter-token latency** описывает интервалы между tokens. Её нельзя точно восстановить, если один content chunk содержит несколько tokens. Число chunks не равно output_tokens. В реальном протоколе источником числа tokens служат usage или tokenizer той же revision. Способ подсчёта влияет на результат.

**Throughput** требует общего wall time, а не усреднения `tokens/latency` отдельных запросов. Если за 2 s завершилось 4 запроса по 10 output tokens, получено 2 requests/s и 20 output tokens/s. Если входы суммарно содержали 80 tokens, total throughput=(80+40)/2=60 tokens/s. Эти арифметические примеры не являются GPU-измерениями. В определении метрики нужно указать, какие tokens, завершения и ошибки входят в счётчик.

## Что означают параметры Compose

Прочитай два Compose-файла как описание решений оператора: какие веса выбрать, какое имя показать клиенту, какой контекст и часть памяти разрешить runtime. В `labs/llm/` закреплены vLLM v0.10.2 и SGLang v0.4.10.post2-cu126. Оба загружают публичную `Qwen/Qwen2.5-0.5B-Instruct` и публикуют имя `course-llm`. Последнее — alias API, а не model revision.

| Настройка | vLLM | SGLang | Смысл |
|---|---|---|---|
| Модель | `--model` | `--model-path` | Источник весов/tokenizer |
| Имя API | `--served-model-name course-llm` | То же | Значение `model` в request.json |
| Контекст | `--max-model-len 2048` | `--context-length 2048` | Лимит последовательности, который нужно согласовать с запросами |
| Память | `--gpu-memory-utilization 0.70` | `--mem-fraction-static 0.70` | Настройки планирования памяти конкретного engine. Численно одинаковые значения не означают идентичные алгоритмы |
| Host port | `8000:8000` | `8000:30000` | Клиент использует 8000, внутренний SGLang — 30000 |

`gpus: all` передаёт доступные GPU контейнеру. Оно не устанавливает драйвер или NVIDIA runtime. `model-cache` сохраняет скачанные файлы, `shm_size:2g` задаёт shared memory контейнера и не добавляет VRAM. SGLang слушает `0.0.0.0` внутри контейнера, host port ограничен loopback. Одинаковый host port означает, что в реальном стенде эти конфигурации рассчитаны на последовательное использование. В практике запуск исключён.

Compose удобен для первого знакомства, но model revision в командах не закреплена. Для теоретически сопоставимого эксперимента нужна одна immutable revision через поддерживаемый в этих версиях `--revision` и одинаковый tokenizer. Разбор аргументов — в [vLLM 0.10.2 CLI](https://docs.vllm.ai/en/v0.10.2/cli/serve.html) и [ServerArgs SGLang выбранного тега](https://github.com/sgl-project/sglang/blob/v0.4.10.post2/python/sglang/srt/server_args.py). Cache сам по себе не доказывает, какая revision загружена.

В `request.json` `messages` — prompt, `max_tokens:64` — верхняя граница выхода, temperature=0 выбирает режим без температурной случайной выборки, `stream:true` включает поток. Модель может закончить раньше 64 tokens. Температура 0 не гарантирует одинаковый текст на разных kernels, hardware и engines. Совместимость endpoint не гарантирует поддержку всех параметров чужого API.

## Протокол честного сравнения

Сравнение engines имеет смысл при одинаковых model/revision/tokenizer, dtype, quantization, context, входных и выходных длинах, параметрах генерации, hardware и runtime. Входным корпусом могли бы служить 20 prompts первого задания. Состояние prefix cache должно быть сопоставимым, иначе один engine получает преимущество от уже обработанного префикса.

Warmup — серия до измерений, её события не входят в статистику. Число измерений и concurrency задаются заранее. Например, если сравниваются короткая инструкция и длинный документ, эти группы оцениваются отдельно: среднее по разной смеси входов может отражать состав корпуса, а не свойства engine.

Для расчётов нужны timestamps полезного content, фактическое число tokens, статусы и общая длительность серии. Корректное сравнение показывает распределения TTFT/total, throughput и ошибки. Наличие context error не считается успешным ответом. Ошибки oversized context, неизвестного имени модели и отмены различают отдельно. Подготовленные события тестов не дают сведений о том, как какой-либо engine обрабатывает такие ситуации.

## TensorRT-LLM и Triton

TensorRT-LLM может требовать преобразования checkpoint и сборки engine под выбранную модель и GPU. **Engine** — подготовленный исполняемый артефакт с настройками точности, shapes и других оптимизаций. **Checkpoint** — сохранённые веса/состояния модели. Он ещё не engine. Triton backend загружает подготовленный комплект и предоставляет serving-контракт, иногда с preprocessing/postprocessing и ensemble — цепочкой связанных моделей.

В справочном shell-скрипте указан образ `25.06-trtllm-python-py3` и [архивный guide 25.06](https://docs.nvidia.com/deeplearning/triton-inference-server/archives/triton-inference-server-2560/user-guide/docs/tensorrtllm_backend/README.html). `tensorrt-llm.sh` открывает shell в контейнере. Build и server там не выполняются автоматически. В архивном quickstart встречаются иллюстративные команды с тегом 24.07: не переноси этот тег и связанные команды сборки в образ 25.06. Для понимания совместимости сопоставь встроенные версии Triton/TensorRT-LLM с support matrix и примерами этого релиза. Использование Qwen в конфигурации другого engine не доказывает её поддержку этим backend. Нужен conversion path, поддерживаемый конкретным релизом. Engine из другого релиза/GPU не считается совместимым без проверки. Сохраняй build flags, версии и hash результата.

## Диагностика и границы доказательства

| Симптом | Что разделить |
|---|---|
| `nvidia-smi` работает, контейнер не видит GPU | Драйвер хоста, Docker GPU runtime и доступность устройств — разные уровни |
| OOM при длинном prompt | Веса уже загружены, но выросли KV cache/временные tensors. Проверить длины и concurrency |
| `/v1/models` отвечает, генерация падает | Список моделей не проверяет конкретный prompt, context и decode |
| Первый chunk ранний, текста долго нет | Role/heartbeat не являются полезным content, TTFT ещё не наступил |
| throughput вырос, TTFT ухудшился | Больше запросов обрабатывается вместе. Смотреть очередь и распределение latency |
| TensorRT container открыл shell | Это проверка среды, не сборка engine и не inference |

CPU-тесты проверяют формулы и обработку потока, а не реальные ресурсы или скорость. Сравнение реальной производительности потребовало бы фактического стенда и находится вне практики этого модуля.
