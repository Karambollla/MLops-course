# Проверка изменений в CI

[Модуль и подготовка](../../README.md#подготовка-к-заданиям) · [Все задания модуля](../../README.md#задания)

## Задача

Проверить, что ошибка в тесте действительно делает автоматическую проверку красной. Ты проследишь цепочку: неверное ожидание → `AssertionError` → ненулевой код команды → неуспешный шаг GitHub Actions. Затем восстановишь правильное ожидание и убедишься, что проверка проходит.

**CI**, или continuous integration, — автоматическая проверка изменений в репозитории. Здесь используются GitHub Actions: workflow описывает команды, job объединяет шаги их выполнения. Успешный статус полезен только тогда, когда нужный тест действительно запускается и его ошибка доходит до статуса job.

Роли команд курса объясняются в [разделе «Что доказывает CI»](../../README.md#что-доказывает-ci).

## Подготовка

Подготовь основное окружение по [SETUP](../../../../SETUP.md#основная-среда). Все команды ниже выполняются из корня курса.

Для просмотра удалённого запуска нужна собственная копия репозитория на GitHub с включёнными Actions. Опыт с намеренной ошибкой выполняй в отдельной рабочей ветке. Локальную часть можно выполнить без GitHub и Docker.

## Исходная проверка

Запусти команды, которые выполняет workflow:

```bash
make check
make test
make tasks-collect
```

| Команда | Что проверяет | Ожидаемый результат |
|---|---|---|
| `make check` | Структуру курса, внутренние ссылки и синтаксис исходников | Код завершения 0 |
| `make test` | Готовые компоненты и обвязку, включая тест контракта API | Тесты проходят, код завершения 0 |
| `make tasks-collect` | Импорт и сбор учебных тестов | Сбор завершается с кодом 0 |

Сбор тестов не выполняет незавершённые учебные функции. Их поведение проверяется отдельно через `make task`. Проверки ML-модуля запускаются внутри notebook.

## Намеренно неверное ожидание

В `test_alive_but_not_ready_without_model` временно замени ожидаемый код GET `/live` с 200 на 201. Меняется только ожидание этого assertion. Реализация API должна продолжать возвращать правильный код 200.

Запусти:

```bash
make test
```

Ожидается падение указанного теста: фактический код 200 не равен ожидаемому 201. В выводе должен быть `AssertionError`, а команда должна завершиться с ненулевым кодом. Номер кода завершения `make` и формулировка вывода могут зависеть от окружения.

Для удалённой проверки отправь эту намеренно неверную версию в отдельную ветку своего GitHub-репозитория. Открой вкладку Actions и выбери запуск для соответствующего commit. Шаг `make test` и job `verify` должны завершиться со статусом failure.

Если job остался зелёным, сравни commit выбранного запуска с отправленным изменением. Затем проверь логи: выполнялась ли команда `make test` и присутствовал ли нужный тест в запуске.

## Восстановление корректного теста

Верни ожидаемый код 200 и повтори `make test`. Тест должен пройти.

Если выполняешь удалённую часть, отправь исправление в ту же рабочую ветку и открой новый запуск Actions. Убедись, что он относится к исправленному commit и завершается успешно.

## Ожидаемое поведение

| Состояние теста | Локальный результат | Результат GitHub Actions |
|---|---|---|
| Ожидается 201, API возвращает 200 | `AssertionError`, ненулевой код `make test` | Шаг `make test` и job `verify` имеют статус failure |
| Ожидание восстановлено до 200 | Тест проходит | Workflow завершается успешно, если остальные проверки тоже проходят |

Это описание ожидаемого поведения. Реальный результат смотри в выводе команд и логах выбранного запуска Actions. Файл с пересказом опыта создавать не требуется.

## Завершение

Оставь в рабочем коде корректное ожидание 200. Для этого опыта не запускаются контейнеры или HTTP-сервер, поэтому останавливать стенд не нужно. Публикация образа и настройка секретов не входят в проверку workflow.
