# CI: пример проверки изменений

[Практика модуля](../../practice.md) · [Теория](../../README.md)

Это руководство по существующему `.github/workflows/check.yml`. Отдельной Python-заготовки и тестов заполненности истории CI нет. Реальный результат виден в GitHub Actions и в локальных командах workflow.

## Команды workflow

После установки зависимостей:

```bash
make check
make test
make tasks-collect
```

Ожидаемый результат: целостность материалов проверена, готовая обвязка проходит тесты, учебные тесты собираются без выполнения незавершённых решений. Незавершённые учебные функции не должны превращать общий CI в бесконечно красный.

## Негативный сценарий

В отдельной ветке своего репозитория намеренно сломай готовый контрактный тест, например замени ожидаемый HTTP status 200 на 201. Выполни make test локально: должен упасть соответствующий assertion. После отправки этой ветки на GitHub шаг make test завершается с ненулевым кодом и job получает failure.

Верни правильное ожидание. Локальный тест и job должны пройти. Не меняй реализацию API под намеренно неверный тест. Публикация image, доступ к registry и секреты для этого опыта не нужны.

## Как выглядит корректный результат

```text
Намеренно неверное ожидание: AssertionError, job failure
Исправленный тест:          тест проходит, job success
```

Это иллюстрация статусов, а не заранее выполненный запуск. Точные run IDs и число тестов зависят от твоей ветки; записывать их в ci-runs.json не нужно. Посмотри логи соответствующего шага в GitHub Actions. Для локального курса GitHub не требуется; удалённый запуск остаётся отдельной проверкой workflow.
