# Сборка и проверка контейнера API

[Модуль и подготовка](../../README.md#подготовка-к-заданиям) · [Все задания модуля](../../README.md#задания) · [Окружение курса](../../../../SETUP.md)

## Задача

В предыдущем задании API проверялся через `TestClient` внутри Python-процесса. Теперь нужно собрать Docker-образ и убедиться, что приложение работает в настоящем контейнере: зависимости доступны, сервер принимает запросы, а модель читается из подключённой папки.

Проверь два состояния поставки. С собственной моделью сервис должен возвращать прогнозы. Без модели процесс должен оставаться живым, но сообщать о неготовности обслуживать прогнозы. Падение контейнера с ошибкой импорта означает проблему поставки.

Роли образа, контейнера, порта и подключённой папки объясняются в [теории модуля](../../README.md#как-образ-получает-модель-и-адрес).

Используй предоставленные файлы:

В этом задании результатом является работающий контейнер с нужными свойствами. Отдельной Python-функции для реализации нет. Ты запускаешь стенд и проверяешь его настройки. Дополнительная конфигурация понадобится для опыта с отсутствующей моделью.

## Подготовка

Нужны доступный Docker daemon, Compose и основное Python-окружение курса для запуска тестов. Проверь доступность Docker:

```bash
docker version
docker compose version
```

В выводе `docker version` должны быть сведения и о клиенте, и о сервере. Если сервер недоступен, запусти свой Docker runtime.

Заверши обучение и сохранение в [ML-notebook](../../../01-ml/housing.ipynb). Его последняя ячейка записывает комплект артефактов прямо в `work/artifacts/`. Для готовности API нужен совместимый `work/artifacts/model.joblib`.

Все команды выполняются из корня курса. Останови локальный Uvicorn или другой процесс, занимающий порт 8000.

## Запуск с моделью

Проверь Compose-конфигурацию, затем собери и запусти сервис:

```bash
docker compose -f labs/housing/compose.yaml config --quiet
docker compose -f labs/housing/compose.yaml up -d --build
docker compose -f labs/housing/compose.yaml logs api
```

Первая команда должна завершиться с кодом 0. В логах приложения дождись успешного startup. Сам факт создания контейнера ещё не означает, что модель загружена.

Папка `work/artifacts/` на компьютере подключена как `/models` внутри контейнера. Приложение читает `/models/model.joblib` через `MODEL_PATH`, заданный в образе. Режим `:ro` разрешает чтение этой папки и запрещает запись через монтирование.

Если в логах появляется `Permission denied`, проверь доступность файла и родительских каталогов для UID 10001. Исправь права чтения и прохода по каталогам для учебного артефакта. Не запускай приложение от root ради обхода ошибки.

## Параметры проверки

Тесты получают настройки из переменных окружения:

| Переменная | Что передать | Значение по умолчанию |
|---|---|---|
| `MLOPS_RUN_INTEGRATION` | `1`, чтобы разрешить обращение к запущенному стенду | Без `1` тесты пропускаются |
| `MLOPS_CONTAINER_ID` | ID контейнера сервиса `api`. Получается командой `docker compose ... ps -q api` | Нет. При включённых проверках ID обязателен |
| `MLOPS_MODEL_STATE` | `ready`, если модель загружена. `absent`, если стенд намеренно запущен с пустой папкой моделей | `ready` |
| `MLOPS_HOUSING_URL` | Базовый HTTP-адрес API, доступный из процесса тестов | `http://127.0.0.1:8000` |

Значение `MLOPS_MODEL_STATE` сообщает тестам ожидаемое состояние. Оно не удаляет модель и не меняет конфигурацию контейнера. Сначала подготовь нужное состояние стенда, затем запускай соответствующую проверку.

## Проверка контейнера с моделью

Убедись, что сервер начал отвечать:

```bash
curl -i http://127.0.0.1:8000/ready
```

При готовой модели ожидается 200. Затем запусти тесты:

```bash
MLOPS_CONTAINER_ID=$(docker compose -f labs/housing/compose.yaml ps -q api) \
  MLOPS_RUN_INTEGRATION=1 make task TASK=03-service-ci/02-container
```

Подстановка `$(...)` получает ID контейнера. Переменные перед `make` действуют для этой команды и её дочерних процессов.

Тесты читают `docker inspect` и `docker image inspect`, выполняют `id -u` внутри контейнера и отправляют HTTP-запросы. Они не запускают и не останавливают стенд. Без включения интеграционных проверок результат `skipped` не подтверждает работу контейнера.

Ожидаемые результаты:

| Проверка | Результат |
|---|---|
| GET `/live` | 200 |
| GET `/ready` | 200 |
| POST `/predict` с [request.json](../../../../labs/housing/request.json) | 200 и один конечный прогноз |
| POST `/predict` с `{"instances": []}` | 422 |
| `id -u` | Числовой UID, отличный от 0 |
| Монтирование `/models` | `RW=false` в `docker inspect` |

Прогноз и версия берутся из твоего bundle. Фиксированного числа для всех моделей нет. При просмотре Dockerfile и `.dockerignore` также проверь, что в образ не копируются CSV, секреты и локальное виртуальное окружение.

## Проверка отсутствующей модели

Для второго опыта нужна пустая папка моделей. Создай `work/empty-models/` и убедись, что в ней нет `model.joblib`. Собственную модель в `work/artifacts/` сохраняй для следующих модулей.

Создай Compose-надстройку отдельным файлом:

```bash
mkdir -p work/empty-models
cat > work/housing-empty.compose.yaml <<'YAML'
services:
  api:
    volumes:
      - ../../work/empty-models:/models:ro
YAML
```

Надстройка заменяет источник монтирования для `/models` пустой папкой. Относительный путь вычисляется от первого Compose-файла — `labs/housing/compose.yaml`.

Останови основной стенд, чтобы освободить порт. Проверь объединённую конфигурацию и запусти отдельный Compose-проект:

```bash
docker compose -f labs/housing/compose.yaml down
docker compose -p housing-empty -f labs/housing/compose.yaml -f work/housing-empty.compose.yaml config --quiet
docker compose -p housing-empty -f labs/housing/compose.yaml -f work/housing-empty.compose.yaml up -d
docker compose -p housing-empty -f labs/housing/compose.yaml -f work/housing-empty.compose.yaml logs api
```

Дождись завершения startup, затем запусти проверки с ожидаемым состоянием `absent`:

```bash
MLOPS_CONTAINER_ID=$(docker compose -p housing-empty -f labs/housing/compose.yaml -f work/housing-empty.compose.yaml ps -q api) \
  MLOPS_MODEL_STATE=absent MLOPS_RUN_INTEGRATION=1 make task TASK=03-service-ci/02-container
```

Теперь `/live` должен отвечать 200. `/ready` и корректный `/predict` должны отвечать 503. Неверный запрос всё ещё должен давать 422, поскольку проверка входа выполняется до обращения к модели.

## Остановка

Останови запущенные учебные проекты:

```bash
docker compose -p housing-empty -f labs/housing/compose.yaml -f work/housing-empty.compose.yaml down
docker compose -f labs/housing/compose.yaml down
```

Собственные артефакты в `work/artifacts/` останутся на компьютере. Временную пустую папку и Compose-надстройку можно удалить после остановки стенда, если они больше не нужны.
