# Проверка контракта API модели

[Модуль и подготовка](../../README.md#подготовка-к-заданиям) · [Все задания модуля](../../README.md#задания) · [Окружение курса](../../../../SETUP.md)

## Задача

Модель уже умеет делать прогноз через `pipeline.predict`. Теперь эти же прогнозы должны получать клиенты HTTP API. Требуется проверить, что сервер использует правильные признаки, возвращает прогноз для каждой входной строки и сообщает версию модели.

Успешный HTTP-код сам по себе этого не доказывает. Например, сервер может перепутать столбцы и вернуть другие числа с кодом 200. Поэтому ты сравнишь два пути вычисления: прямой вызов Pipeline и запрос к API. Такое сравнение называется **паритетом прогнозов**. Оно проверяет одинаковое поведение двух способов запуска модели. Качество модели относительно настоящей стоимости жилья оценивается в модуле 01.

Путь запроса разобран в [теории модуля](../../README.md#какие-файлы-превращаются-в-сервис). Причины ответов 422 и 503 объясняются в [разделе об ошибках API](../../README.md#разобранный-запрос-и-независимые-ошибки).

## Что уже подготовлено

В [housing.api](../../../../labs/housing/src/housing/api.py) находятся приложение FastAPI, функция `create_app` и маршруты `/live`, `/ready`, `/predict`. Приложение загружает собственный доверенный `model.joblib` при запуске, а затем вызывает его `pipeline.predict` для входных строк.

В соседнем [solution.py](solution.py) подготовлены импорты и заготовки двух функций. В [test_task.py](test_task.py) есть проверки этих функций. Для них создаются маленькие обученные модели на синтетических данных и временные файлы bundle. Скачивать датасет или завершать обучение модели California Housing для запуска этих проверок не требуется.

**Bundle** — словарь, сохранённый в `model.joblib`. Он содержит Pipeline, порядок признаков, версию модели и версию схемы файла. В проверках один и тот же Pipeline используется напрямую и загружается приложением из временного bundle.

## Подготовка

Активируй основное окружение курса по [инструкции](../../../../SETUP.md#основная-среда). В нём должны быть установлены зависимости housing и сам пакет. Все команды ниже выполняются из корня репозитория.

Проверки задания используют `TestClient`. Это клиент, который передаёт HTTP-запросы приложению внутри Python-процесса. Отдельный Uvicorn, свободный сетевой порт и Docker для этих проверок не нужны.

## Что реализовать

В `solution.py` реализуй `check_prediction_response` и `exercise_api`. Дополнительные интеграционные тесты API размести в этой же папке в файле с именем `test_*.py`. Они должны использовать предоставленную функцию `housing.api.create_app`.

Здесь интеграционный тест означает совместную проверку FastAPI, загрузки bundle и прогноза настоящей модели. Такой тест может выполняться внутри одного процесса через `TestClient`.

### Проверка тела ответа: `check_prediction_response`

Сигнатура заготовки:

```python
def check_prediction_response(payload: dict, expected, model_version: str) -> None:
    ...
```

| Аргумент | Тип и формат | Откуда берётся и зачем нужен | Пример |
|---|---|---|---|
| `payload` | `dict` с телом ответа API после декодирования JSON | В HTTP-сценарии получается через `response.json()`. Это результат, который нужно проверить | `{"predictions": [1.0, 2.0], "model_version": "v1", "target_unit": "100000 USD"}` |
| `expected` | Одномерная последовательность чисел, например список или массив NumPy | Эталонные прогнозы для тех же строк в том же порядке. В HTTP-сценарии их вычисляет `pipeline.predict(batch)` | `[1.0, 2.0]` |
| `model_version` | `str` | Ожидаемое значение поля `model_version` из bundle, загруженного приложением | `"v1"` |

В `payload` должны быть ровно три поля:

| Поле | Ожидаемое содержимое |
|---|---|
| `predictions` | Одномерный список конечных числовых прогнозов. Количество и порядок соответствуют `expected` |
| `model_version` | Версия модели, равная аргументу `model_version` |
| `target_unit` | Строка `"100000 USD"`, обозначающая единицу целевой переменной California Housing |

Проверь наличие всех трёх полей и отсутствие дополнительных. Прогнозы не должны содержать `NaN`, положительную или отрицательную бесконечность. Вложенный список вида `[[1.0], [2.0]]` не соответствует формату ответа.

Для численного сравнения используй `rtol=1e-6` и `atol=1e-8`. Эти параметры разрешают небольшую погрешность вычислений. Например, прогноз `1.0000001` близок к эталону `1.0` в пределах допуска, а `9.0` вместо `2.0` означает ошибку.

При корректном ответе функция возвращает `None`. При нарушении контракта она выбрасывает `ValueError`. Возвращать `False`, исправлять ответ или молча пропускать неверное поле не нужно.

### Проверка приложения: `exercise_api`

Сигнатура заготовки:

```python
def exercise_api(client, pipeline, batch, model_version: str) -> None:
    ...
```

| Аргумент | Тип и формат | Откуда берётся и зачем нужен | Пример |
|---|---|---|---|
| `client` | `fastapi.testclient.TestClient` внутри активного контекста `with` | Передаётся вызывающим тестом. Приложение уже прошло startup и загрузило модель. Через клиент отправляются запросы к маршрутам API | `client.post("/predict", json=...)` |
| `pipeline` | Обученный sklearn Pipeline с методом `predict` | Тот же Pipeline, который сохранён в bundle приложения. Нужен для вычисления эталонных прогнозов | `pipeline.predict(batch)` |
| `batch` | `pandas.DataFrame` с числовыми признаками. Столбцы расположены в порядке `FEATURES`. В корректном запросе от 1 до 256 строк | Тест создаёт небольшую таблицу. Одна строка описывает район и должна дать один прогноз | Две строки с восемью столбцами из таблицы ниже |
| `model_version` | `str` | Ожидаемая версия bundle приложения. Передаётся дальше в проверку ответа | `"test"` |

Контекст `with TestClient(create_app(path)) as client` открывает жизненный цикл приложения — **lifespan**. Во время входа в него загружается модель. Внутри `exercise_api` клиент уже подготовлен вызывающим тестом. Создавать там второй сервер, заново обучать модель или закрывать переданный клиент не требуется.

Пример содержимого `batch`:

| MedInc | HouseAge | AveRooms | AveBedrms | Population | AveOccup | Latitude | Longitude |
|---|---|---|---|---|---|---|---|
| 3.0 | 20.0 | 5.0 | 1.0 | 1000.0 | 3.0 | 34.0 | -118.0 |
| 4.0 | 15.0 | 6.0 | 1.0 | 800.0 | 2.5 | 37.0 | -122.0 |

`FEATURES` импортирован в заготовке из `housing.features` и содержит именно этот порядок столбцов. Целевую переменную `MedHouseVal` отправлять в API не нужно.

Последовательность проверки:

1. Вычисли эталонные прогнозы через переданный Pipeline для `batch`.
2. Представь строки таблицы как JSON-объекты внутри поля `instances` и отправь POST `/predict`.
3. Проверь код 200 и передай декодированное тело ответа в `check_prediction_response` вместе с эталоном и ожидаемой версией.
4. Переставь порядок ключей в объектах запроса и проверь, что прогнозы сохраняются. Сервер должен восстановить порядок столбцов по `FEATURES`.
5. Отправь некорректные запросы из таблицы ниже и проверь код 422 для каждого.

| Некорректный запрос | Почему API должен его отклонить |
|---|---|
| Пустой список `instances` | Нет ни одной строки для прогноза |
| 257 строк в `instances` | Превышен максимальный размер batch — 256 |
| Отсутствует один из восьми признаков | Модель не получает полный набор входов |
| У строки есть дополнительное поле | Схема признаков запрещает неизвестные поля |
| Вместо числового признака передана строка или `bool` | Строгая схема запрещает такое преобразование типов |
| Один из признаков равен `NaN` или Infinity | Модель не должна получать неконечные значения |

Для последнего случая HTTP-клиент может отклонить значение ещё при сериализации аргумента `json=`. Нужно проверить именно ответ приложения на такие байты. Отправь самостоятельно сериализованное тело через `content=` с заголовком `Content-Type: application/json`. Исключение сериализатора до отправки запроса не подтверждает код 422 от API.

При успешном выполнении всех проверок `exercise_api` возвращает `None`. Ошибку поведения приложения оставляй видимой через assertion. Не перехватывай её ради успешного завершения функции.

### Дополнительные интеграционные тесты

Функция `exercise_api` работает с уже готовым приложением и загруженной моделью. Другие состояния проверь отдельными тестами, создавая приложение с собственным временным путём к bundle:

- При отсутствующем файле `/live` отвечает 200. `/ready` и корректный `/predict` отвечают 503. Некорректный запрос по-прежнему даёт 422.
- Несовместимый bundle, например с `schema_version=2`, прерывает startup. Ошибка должна возникнуть при входе в контекст `TestClient`.
- Проверка ответа обнаруживает неправильное количество прогнозов. Число результатов должно совпадать с числом входных строк.

Для файлов используй временную папку pytest. Загружай только собственные доверенные артефакты. Опыты с отсутствующей или несовместимой моделью не должны изменять `work/artifacts/model.joblib`.

## Запуск проверки

Из корня курса после реализации функций и добавления тестов:

```bash
make task TASK=03-service-ci/01-api-contract
```

Команда выполняет тесты в папке задания, включая добавленные тобой `test_*.py`. До реализации заготовок ожидается `NotImplementedError`. Ошибка импорта библиотеки означает, что сначала нужно подготовить окружение.

## Ожидаемое поведение

Если Pipeline вернул для двух строк `[1.0, 2.0]`, а в bundle указана версия `"test"`, корректное тело HTTP-ответа выглядит так:

```json
{
  "predictions": [1.0, 2.0],
  "model_version": "test",
  "target_unit": "100000 USD"
}
```

Это пример формата. Числа настоящей модели зависят от её обучения. Поле `model_version` берётся из загруженного bundle. Значение прогноза `2.0` соответствует 200000 USD в единицах исторического датасета.

| Состояние | `/live` | `/ready` | Корректный `/predict` | Неверный запрос |
|---|---|---|---|---|
| Совместимая модель загружена | 200 | 200 | 200 и прогнозы | 422 |
| Файла модели нет | 200 | 503 | 503 | 422 |
| Bundle несовместим | Startup завершается ошибкой | Приложение не готово принимать запросы | Приложение не готово принимать запросы | Приложение не готово принимать запросы |

## Ручной запуск со своей моделью

После проверок внутри Python-процесса запусти приложение через настоящий HTTP-сервер. Для этого нужна собственная модель из [ML-notebook](../../../01-ml/housing.ipynb). Последняя ячейка notebook сохраняет её в `work/artifacts/model.joblib`.

В первом терминале из корня курса:

```bash
MODEL_PATH=work/artifacts/model.joblib uvicorn housing.api:app --host 127.0.0.1 --port 8000
```

Во втором терминале отправь запросы:

```bash
curl -i http://127.0.0.1:8000/live
curl -i http://127.0.0.1:8000/ready
curl -i http://127.0.0.1:8000/predict \
  -H 'Content-Type: application/json' \
  --data-binary @labs/housing/request.json
```

При загруженной модели ожидаются коды 200. Если `/ready` отвечает 503, проверь, существует ли указанный `MODEL_PATH` и выполнено ли сохранение из notebook. Замена файла модели требует перезапуска Uvicorn, поскольку приложение читает bundle при startup.

Docker для этого запуска не нужен. Проверка образа и монтирования модели выполняется в [следующем задании](../02-container/README.md).

## Остановка

После ручного опыта останови Uvicorn через `Ctrl+C` в первом терминале. `TestClient` завершается при выходе из контекста, а временными файлами тестов управляет pytest. Собственную модель в `work/artifacts/` сохрани для следующих заданий.
