# Границы Dockerfile, Terraform и Ansible

## Зачем выбирать владельца изменения

Одну настройку можно попытаться записать в Dockerfile, Terraform provisioner и Ansible task одновременно. Тогда следующий запуск любого инструмента способен вернуть своё значение. Полезнее определить, где живёт нужное состояние и какой инструмент отвечает за его жизненный цикл.

Это руководство опирается на образ housing из сервисного модуля, state Terraform 11 и файлы Ansible 12. Новую инфраструктуру поднимать не требуется. Прочти [границы инструментов](../../README.md#граница-dockerfile-terraform-и-ansible) и [передачу результатов Terraform](../../../11-terraform/README.md#файлы-процессы-и-граница-с-предыдущими-модулями).

## Контракт архитектурного примера

Для каждого изменения проследи вход, исполнителя и проверяемый выход. Например, новая библиотека меняет рецепт Docker image и требует сборки; новый контейнер меняет HCL и plan/state; новая настройка существующего узла меняет vars/template и должна дать no-op при повторе. Вернуть прежний env через Ansible означает применить старые vars, а не откатить Terraform state. Сравнение ниже разбирает эти границы на готовых артефактах курса.

## Сопоставление инструментов

| Инструмент | Вход и состояние | Повтор и восстановление |
|---|---|---|
| Dockerfile | Рецепт образа; образ/tag/digest в registry | Пересобрать образ; откат deployment на предыдущий digest |
| Terraform | HCL + привязки address→ID в state | plan сравнивает инфраструктуру; восстановление через reviewed plan/import |
| Ansible | Inventory/playbook + фактические файлы узла | Повтор приводит файлы к нужному виду; откат через прежний template/vars |

Пример изменения: новая Python-зависимость housing API требует образа Docker; новый контейнер/сеть — Terraform; изменение WORKERS на существующем узле — Ansible template+handler. Terraform state не хранится в Git; lock-файл provider хранится. Ansible Vault шифрует файлы, а HashiCorp Vault выдаёт доступ через отдельный сервис: это разные инструменты.

Для локального приложения на одном Compose-хосте достаточно Dockerfile+Compose; добавлять все три инструмента необязательно. Дополнительная практика: выделить SSH managed container и выполнить playbook по inventory вместо локального connection. Это отдельный узел, в отличие от запуска controller-контейнера.
