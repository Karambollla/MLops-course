# Registry

[Модуль и подготовка](../../README.md#подготовка-к-заданиям) · [Все задания модуля](../../README.md#задания) · [SETUP](../../../../SETUP.md)

## Зачем после run нужна версия выпуска

Run из [предыдущей темы](../01-experiments/README.md) описывает обучение. Сервису требуется точный загружаемый объект с понятным интерфейсом, который не изменится при следующем выборе champion. Registry даёт имя семейства и конкретные версии, а release закрепляет выбранную версию. Различия bundle, MLflow Model, flavor, signature и alias разобраны в [теории регистрации](../../README.md#от-pipeline-к-версии-реестра).

## Исходный результат и новые действия

Нужны выбранный по validation run ID, его обученный Pipeline, небольшой batch-пример с FEATURES и результаты финальной проверки качества. Сервер предыдущей темы остаётся тем же: нельзя зарегистрировать модель в другой истории и ожидать прежнюю связь run. В заготовке реализуются регистрация, разрешение alias и проверка численного паритета. Итог сохраняется как `release.json`.

Импорты `mlflow` и `mlflow.sklearn` уже находятся в начале файла. В `register_model` предстоит применить `mlflow.models.infer_signature` и `mlflow.sklearn.log_model`, а через `MlflowClient` — получить версию и назначить alias. Это учебная реализация: до её завершения SDK не регистрирует модель автоматически. Различие файла артефакта и формата MLflow Model объясняется в [разделе о версии реестра](../../README.md#от-pipeline-к-версии-реестра).

Если `champion` указывает на версию 7 исходного `run-1`, `resolve_release(..., expected_run_id="run-1")` возвращает URI `models:/housing/7` и version `"7"`. Если alias теперь ведёт к другому run, нужен `ValueError`, даже при подходящем имени модели. После загрузки модели по закреплённому URI один batch должен дать те же конечные прогнозы, что исходный Pipeline. Проверка версии и проверка чисел независимы: неверный источник иногда может случайно вернуть те же числа на маленьком примере.

## Где работать

Реализуй функции в [solution.py](solution.py). Рядом находятся [тесты](test_task.py). Реальный выпуск сохраняй как `release.json`. Отдельного CLI в заготовке нет.

## `resolve_release`: заменить alias точной версией

```python
def resolve_release(client, model_name: str, alias: str, expected_run_id: str) -> dict:
    ...
```

| Параметр | Тип | Формат и смысл | Откуда берётся | Пример |
|---|---|---|---|---|
| `client` | `MlflowClient` или совместимый объект | Предоставляет `get_model_version_by_alias(name, alias)`. Результат имеет `version` и `run_id` | Клиент выбранного tracking/registry backend. В unit-тесте маленькая замена | `MlflowClient(tracking_uri=uri, registry_uri=uri)` |
| `model_name` | `str` | Имя зарегистрированной модели | Использовано при регистрации Pipeline | `"housing"` |
| `alias` | `str` | Имя изменяемого указателя | Назначено через `set_registered_model_alias` | `"champion"` |
| `expected_run_id` | `str` | ID именно того обучения, которое разрешено выпускать | Выбранный запуск из предыдущего задания | `"run-1"` |

Функция читает alias и проверяет источник. `version` должна обозначать положительное целое и возвращается строкой. Значения `"0"`, `"-1"`, `"1.5"`, `"latest"` и пустая строка отвергаются через `ValueError`. Несовпадение `run_id` тоже даёт `ValueError`.

При ответе клиента `version="7", run_id="run-1"` и аргументах `"housing", "champion", "run-1"` результат имеет точную форму:

```json
{"model_name": "housing", "alias": "champion", "version": "7", "run_id": "run-1", "model_uri": "models:/housing/7"}
```

Финальная ссылка закрепляет номер версии. Плавающий `models:/housing@champion` может позже указывать на другую модель.

## `register_model`: сохранить Pipeline в Registry

```python
def register_model(
    pipeline, example, run_id: str, model_name: str, tracking_uri: str
) -> dict:
    ...
```

| Параметр | Тип | Формат и смысл | Откуда берётся | Пример |
|---|---|---|---|---|
| `pipeline` | Обученный sklearn `Pipeline` | Полная цепочка подготовки и модели с рабочим `predict` | `bundle["pipeline"]` выбранного обучения | Pipeline с scaler и Ridge |
| `example` | Обычно `pandas.DataFrame` | Маленький batch тех же именованных признаков, что при обучении | Несколько строк входного DataFrame | `frame[FEATURES].iloc[:4]` для housing |
| `run_id` | `str` | Существующий исходный run в том же backend | Выбранный по validation запуск | `"run-1"` |
| `model_name` | `str` | Имя семейства моделей Registry | Выбирает вызывающий код | `"housing"` |
| `tracking_uri` | `str` | Адрес MLflow с исходным run | Подготовленный сервер или локальная SDK-среда | `"http://127.0.0.1:5001"` |

Сохрани именно Pipeline через sklearn flavor с input example и signature, полученной по входам и прогнозам. Bundle-словарь и отдельно загруженный joblib — артефакты проекта, но не замена MLflow Model. Свяжи запись с переданным `run_id`, зарегистрируй версию и назначь `candidate` и `champion`. В практическом housing-сценарии это выполняется после quality gate и финальной test-оценки. Сам `register_model` не получает метрик или порога и не может проверить качество по своим аргументам. SDK-тест передаёт уже обученный маленький Pipeline.

Результат — разрешённый release того же формата, что у `resolve_release`. Сохрани его в `release.json` для собственного запуска. Сериализацию файла выполняет вызывающий код: параметра пути в функции нет. После регистрации модель загружается по точному `model_uri`, а численный результат проверяется следующей функцией. При отсутствии SDK заготовка даёт `RuntimeError` с инструкцией установки. Остальные ошибки SDK не должны маскироваться успешным release.

## `assert_parity`: сравнить два пути прогнозирования

```python
def assert_parity(original, registered, batch) -> None:
    ...
```

| Параметр | Тип | Формат и смысл | Откуда берётся | Пример |
|---|---|---|---|---|
| `original` | Объект с `predict(batch)` | Исходный обученный Pipeline | Из выбранного bundle | `bundle["pipeline"]` |
| `registered` | Объект с `predict(batch)` | Загруженная версия той же модели | `mlflow.sklearn.load_model(release["model_uri"])` | Pipeline версии 7 |
| `batch` | Вход, принимаемый обеими моделями | Одинаковые строки и порядок признаков для двух вызовов | Маленький DataFrame исходных данных | `frame[FEATURES].iloc[:2]` |

Оба массива прогнозов должны иметь одинаковую форму и содержать только конечные числа. Сравни их с `rtol=1e-6`, `atol=1e-8`. При успехе возвращается `None`, при расхождении, разной форме, NaN или Infinity — `ValueError`.

Например, прогнозы `[1.0, 2.0]` и `[1.0 + 1e-9, 2.0]` проходят. `[1.0, 3.0]` не проходят. Массивы формы `(2,)` и `(2, 1)` тоже несовместимы, хотя число элементов совпадает. Допуск включает абсолютную и относительную части: `[0.0, 1000.0]` и `[5e-9, 1000.0005]` проходят проверку.

## Среда и зависимости

Базовая среда, numpy. Реальные Registry действия требуют MLflow SDK/Compose предыдущего задания. CPU.

Зависит от 04-mlflow/01-experiments. Офлайн fake client проверяет разрешение версии, а не MLflow сервер. Ожидаемое поведение на стенде: input example/signature доступны, release ссылается на исходный run, прогнозы совпадают, после рестарта метаданные/artifacts остаются.

## Запуск и результат

Из корня репозитория:

```bash
make task TASK=04-mlflow/02-registry
```

Тесты функций работают offline на маленьких входах и временных файлах. До реализации ожидается `NotImplementedError`. Ошибка импорта означает проблему подготовки среды. Проверка функций не заменяет описанный опыт на данных или стенде.

Это задание использует функции. Импортируй заготовку через `course_tasks.load_task("04-mlflow/02-registry")` из Python. CLI не требуется.

## Требования практического опыта

Через `mlflow.sklearn.log_model` зарегистрируй Pipeline с input example и signature. Через MlflowClient назначь `candidate` и `champion`. Разреши champion в конкретный номер версии и сохрани release manifest. Выполни predict через исходный bundle и загруженную зарегистрированную модель на одинаковом batch. Результаты должны совпасть в допуске.

## Приёмка и очистка

Запусти указанную выше команду `make task` после реализации и исправления ошибок. Проверяемые случаи перечислены в соседнем `test_task.py`.

После опыта останови стенд: `docker compose -f labs/mlflow/compose.yaml down`. Не удаляй volume без экспорта истории. Артефакты `work/` сохрани для следующих модулей.

## Пример корректного результата

Разрешённый release хранит конкретную строковую версию и URI вида models:/housing/7, а не плавающий alias. Несовпадение expected_run_id вызывает ValueError. Прогноз зарегистрированной модели совпадает с исходным Pipeline в заданном допуске.

## Локальная проверка SDK

После реализации задания и его предшественников можно проверить MLflow Registry с локальными SQLite и артефактами. Установи зависимости модуля в его окружение, затем выполни из корня курса:

```bash
MLOPS_RUN_SDK=1 python scripts/run_task.py test 04-mlflow/02-registry -- -m sdk
```

Используются только временные данные, внешний сервер не нужен. Без флага проверка пропускается. При включённом флаге отсутствие SDK считается ошибкой подготовки окружения. Этот запуск не заменяет практику работающего стенда. Подробнее — [режимы проверок](../../../../docs/task-structure.md#локальные-проверки-sdk).

## Серверная интеграционная проверка

При работающем стенде и установленном `labs/mlflow/requirements.txt`:

```bash
MLOPS_RUN_INTEGRATION=1 MLOPS_RUN_WRITES=1 MLFLOW_TRACKING_URI=http://127.0.0.1:5001 python -m pytest modules/04-mlflow/tasks/02-registry/test_task.py -m integration -q
```

Тест создаёт собственные уникальные experiment/model, использует маленький
синтетический Pipeline и удаляет только свои записи в finally. Не требуется
существующая обученная housing-модель. Обязательны оба флага записи.
markers — `integration`, `writes`. Ограничение soft delete файлов описано в
[теме экспериментов](../01-experiments/README.md#проверка-настоящего-сервера).
Проверяются исходный run/version/source, закреплённый URI, aliases, signature,
input example и реальные прогнозы загруженного Pipeline с rtol=1e-6, atol=1e-8.
Тест вызывает student `register_model`, `resolve_release`, `assert_parity`.
