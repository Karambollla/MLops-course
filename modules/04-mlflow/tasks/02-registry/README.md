# Зарегистрировать выбранную модель и закрепить выпуск

[Модуль](../../README.md) · [Подготовка среды](../../README.md#подготовка-к-заданиям) · [Все задания](../../README.md#задания)

## Исходная ситуация

В первом задании ты выбрал обучение по validation MAE. Теперь известны его `run_id` и файлы результата. Нужно получить ссылку, по которой приложение сможет загрузить именно эту модель, и проверить, что после сохранения она возвращает прежние прогнозы.

В [теории](../../README.md#от-pipeline-к-версии-реестра) разобран переход от своего joblib к формату MLflow Model и реестру версий. Здесь реализуются конкретные действия через SDK. Работай с тем же сервером, где сохранён исходный run.

Понадобятся выбранный run ID, его обученный `bundle["pipeline"]` и небольшой DataFrame с теми же входными признаками. Качество модели оценивается до вызова регистрации. В аргументах `register_model` нет метрик и порога, поэтому функция не принимает решение о достаточности MAE.

## Где работать и что получится

В [solution.py](solution.py) подготовлены импорты MLflow, sklearn-интеграции, `infer_signature` и `MlflowClient`. Реализуй три функции. [Тесты](test_task.py) проверяют чтение версии, численный паритет и, в отдельных режимах, настоящую регистрацию.

Для первой учебной публикации договоримся: `candidate` обозначает версию, выбранную для проверки, `champion` — версию, выбранную для обслуживания. Такие указатели называются aliases. В этом задании после проверок оба назначаются на одну начальную версию. Их назначение и последующее закрепление разобраны в [разделе о роли версии](../../README.md#как-обозначить-роль-версии).

Результат для собственного проекта — зарегистрированная версия и `release.json` с точными идентификаторами. Сам файл записывает вызывающий код, отдельного CLI в заготовке нет.

## Шаг 1. `register_model`: сохранить Pipeline средствами MLflow

```python
def register_model(
    pipeline, example, run_id: str, model_name: str, tracking_uri: str
) -> dict:
    ...
```

| Аргумент | Тип и формат | Происхождение и назначение | Пример |
|---|---|---|---|
| `pipeline` | Обученный sklearn `Pipeline` | Полная модель выбранного обучения с подготовкой признаков | `bundle["pipeline"]` |
| `example` | `pandas.DataFrame`, принимаемый этим Pipeline | Небольшой пример входа для описания интерфейса и проверки загрузки | `frame[FEATURES].iloc[:4]` |
| `run_id` | `str`, ID существующего run | Связывает зарегистрированную модель с её обучением | ID из результата первого задания |
| `model_name` | `str`, общее имя в реестре | Под ним появится отдельная версия этого результата | `"housing"` |
| `tracking_uri` | `str` | Сервер с исходным run либо URI локального SDK-теста | `"http://127.0.0.1:5001"` |

Сначала выбери tracking URI. Сохрани переданный Pipeline через `mlflow.sklearn.log_model`, связав запись с исходным `run_id`. Пример `example` передаётся как input example. Описание входа и выхода, signature, получается через `infer_signature` по этим строкам и прогнозам Pipeline.

Затем зарегистрируй версию под `model_name`. Загрузи её и проверь прогнозы на том же примере до назначения начальных aliases. Назначь `candidate` и `champion` на проверенную версию через `MlflowClient` и верни закреплённое описание выпуска, разобранное в следующем шаге.

Файл `model.joblib` из первого задания остаётся артефактом происхождения. Для загрузки средствами MLflow здесь сохраняется сам Pipeline в формате MLflow Model. Для текстового классификатора аналогично сохранялась бы цепочка преобразования текста и классификации. Формат входного примера зависел бы от этой цепочки. Другие типы моделей реализовывать не нужно.

При отсутствии SDK заготовка выбрасывает `RuntimeError` с командой установки. Ошибки сохранения и регистрации не должны превращаться в успешный выпуск.

## Шаг 2. `resolve_release`: получить точную версию по alias

```python
def resolve_release(client, model_name: str, alias: str, expected_run_id: str) -> dict:
    ...
```

| Аргумент | Тип и формат | Происхождение и назначение | Пример |
|---|---|---|---|
| `client` | `mlflow.tracking.MlflowClient` | Читает версии с того же сервера. В unit-тесте используется маленький подставной клиент | `MlflowClient(tracking_uri=uri)` |
| `model_name` | `str` | Имя зарегистрированной модели | `"housing"` |
| `alias` | `str` | Назначенный указатель, который нужно разрешить | `"champion"` |
| `expected_run_id` | `str` | Запуск, результат которого разрешено использовать | ID выбранного обучения |

Прочитай версию через `get_model_version_by_alias`. Проверь, что она связана с `expected_run_id`. Номер версии должен быть положительным целым и возвращается строкой. Неверный источник, `"0"`, `"-1"`, `"1.5"`, `"latest"` и пустая версия вызывают `ValueError`.

Допустим, собственный `champion` модели `housing` указывает на версию 7 из `run-1`. Для этих аргументов ожидается:

```json
{
  "model_name": "housing",
  "alias": "champion",
  "version": "7",
  "run_id": "run-1",
  "model_uri": "models:/housing/7"
}
```

Этот же формат возвращает `register_model` после первоначальной публикации. В реальном результате используй настоящий run ID и номер версии. Ссылка с номером остаётся определённой, даже если alias позже перенесут на другую модель.

## Шаг 3. `assert_parity`: сравнить исходную и загруженную модель

```python
def assert_parity(original, registered, batch) -> None:
    ...
```

| Аргумент | Тип и формат | Происхождение и назначение | Пример |
|---|---|---|---|
| `original` | Объект с `predict` | Исходный обученный Pipeline | `bundle["pipeline"]` |
| `registered` | Объект с `predict` | Загруженная точная версия MLflow | `mlflow.sklearn.load_model(release["model_uri"])` |
| `batch` | Вход, принимаемый обеими моделями | Одни и те же строки в том же порядке признаков | `frame[FEATURES].iloc[:20]` |

Полученные массивы должны иметь одинаковую форму и только конечные числа. Сравнивай с `rtol=1e-6`, `atol=1e-8`. При успехе возвращается `None`. Расхождение, другая форма, NaN или Infinity вызывают `ValueError`.

Например, для двух одних и тех же районов прогнозы `[1.0, 2.0]` и `[1.0 + 1e-9, 2.0]` проходят. `[1.0, 3.0]` не проходят. Формы `(2,)` и `(2, 1)` тоже должны различаться: автоматическое расширение массива при сравнении может скрыть неверный интерфейс.

После собственных проверок сохрани возвращённый release в `work/release.json`. Получение одинаковых прогнозов подтверждает сохранение модели. Оно не заменяет оценку MAE относительно настоящих target.

## Проверка функций

```bash
make task TASK=04-mlflow/02-registry
```

Быстрые тесты проверяют разрешение версии и сравнение прогнозов. До реализации ожидается `NotImplementedError`. Они не подтверждают настоящую регистрацию.

Проверка настоящего SDK без Docker:

```bash
MLOPS_RUN_SDK=1 python scripts/run_task.py test 04-mlflow/02-registry -- -m sdk
```

Используются временные SQLite, файлы и небольшой синтетический Pipeline. Проверяются сохранённая signature, input example, связь с run, aliases и прогнозы после загрузки. Собственная Housing-модель для этого теста не нужна, но реализация функций нужна.

## Проверка сервера

При работающем Compose и установленном `labs/mlflow/requirements.txt`:

```bash
MLOPS_RUN_INTEGRATION=1 MLOPS_RUN_WRITES=1 MLFLOW_TRACKING_URI=http://127.0.0.1:5001 python -m pytest modules/04-mlflow/tasks/02-registry/test_task.py -m integration -q
```

Тест создаёт собственные уникальные experiment/model, вызывает твою регистрацию и читает результат через SDK. Удаляются только свои записи. Для собственного Housing-запуска отдельно проверь в UI версию, её исходный run, aliases и возможность загрузки по `model_uri` из `release.json`.
