# Три настройки модели и их записи в MLflow

[Модуль](../../README.md) · [Подготовка среды](../../README.md#подготовка-к-заданиям) · [Все задания](../../README.md#задания)

## Что предстоит сделать

В ML-модуле ты написал `train`, который получает CSV и сохраняет модель с метриками. Теперь нужно сравнить три значения одной настройки Ridge и сохранить каждый результат в MLflow. Для этого сначала доработай само обучение: оно должно принимать конфигурацию извне. Затем реализуй обвязку трекинга и выбор запуска.

Работа выполняется в двух местах. В сохранённом [ML-notebook](../../../01-ml/housing.ipynb) находится твоя `train`. В соседнем [solution.py](solution.py) находятся `track_experiments` и `select_candidate`. Импорты SDK и `from housing.train import train` уже подготовлены. Функция из `housing.train` служит адаптером: читает сохранённые определения notebook и передаёт аргументы твоей `train`. Поэтому после изменений notebook нужно сохранять на диск.

Для ручной практики нужен `work/housing.csv` и сервер из подготовки модуля. Маленькие тесты используют синтетический CSV, но обучение в них тоже настоящее. Значения метрик нельзя подставлять из примеров.

## Шаг 1. Доработать `train`

Сигнатура уже подготовлена в notebook и адаптере. Реализуй поведение нового аргумента в своей функции:

```python
def train(
    data: Path,
    output: Path,
    seed: int,
    *,
    parameters: dict | None = None,
) -> None:
    ...
```

| Аргумент | Формат и назначение | Откуда берётся | Пример |
|---|---|---|---|
| `data` | `Path` к существующему CSV с FEATURES и target | Вход функции трекинга | `Path("work/housing.csv")` |
| `output` | `Path` к каталогу одного обучения | Обвязка выделяет отдельную папку каждой конфигурации | `Path("work/mlflow-runs/ridge-alpha-1")` |
| `seed` | `int`, общий источник случайности разбиения и алгоритма | Для трёх сравнений этого задания зафиксирован 42 | `42` |
| `parameters` | Именованный `dict` с настройками Ridge или `None` | Обвязка перебирает заранее выбранные конфигурации | `{"alpha": 1.0}` |

Ridge штрафует большие коэффициенты линейной модели. Настройка `alpha` управляет силой этого штрафа. В этом задании сравниваются `0.1`, `1.0`, `10.0`. Полезность конкретного значения определят validation-метрики, заранее лучшая настройка неизвестна.

Требуемые режимы:

- При `parameters=None` сохраняется поведение модуля 01: прежнее сравнение кандидатов и четыре файла результата. Существующий CLI, Airflow и ClearML продолжают вызывать обучение с тремя аргументами.
- При словаре обучается один Ridge с указанными настройками. Не выполняй внутри этого режима новый подбор и не заменяй переданную `alpha` собственной настройкой. Подготовку признаков обучай на train и сохраняй в том же Pipeline.
- В обоих режимах рассчитываются baseline и `candidate` на тех же validation/test-строках. `model.joblib`, `metrics.json`, `manifest.json`, `split.json` сохраняют [существующий формат](../../../../labs/housing/README.md#артефакты). В манифесте должны быть фактические параметры обученной модели.

Например, внутри `track_experiments` вызов одного обучения будет выглядеть так:

```python
train(data, output / "ridge-alpha-1", 42, parameters={"alpha": 1.0})
```

`data` и `output` здесь — аргументы обвязки, описанные ниже. После выполнения в этой подпапке должен находиться результат именно Ridge с `alpha=1.0`. Запись другого числа в манифест без применения его к модели не выполняет условие.

Сохрани notebook на диск. Найди его ячейку «Проверка конфигурации обучения для модуля 04», установи `RUN_MLFLOW_CONFIGURATION_CHECKS = True` и выполни её после необходимых определений. Проверки читают текущую функцию ядра. Внешний адаптер читает сохранённую функцию с диска.

Этот режим не является общим интерфейсом любой ML-модели. Для классификатора писем вместо `alpha` могли бы передаваться настройки текстового преобразования и регуляризации классификатора. Принцип сохраняется: конфигурация должна управлять настоящим обучением и отражаться в его результатах. Другую модель в задании реализовывать не требуется.

## Шаг 2. Обучить три конфигурации и записать результаты

```python
def track_experiments(
    data: Path,
    output: Path,
    tracking_uri: str,
    *,
    experiment_name: str = "housing-course",
) -> list[dict]:
    ...
```

| Аргумент | Тип и формат | Откуда берётся и зачем нужен | Пример |
|---|---|---|---|
| `data` | `Path` к CSV | Общий вход всех трёх обучений | `Path("work/housing.csv")` |
| `output` | `Path` к общему каталогу | Внутри будут три подпапки обучения и `comparison.json` | `Path("work/mlflow-runs")` |
| `tracking_uri` | `str` | Адрес записи результатов. Для сервера HTTP, для локального SDK-теста временная SQLite | `"http://127.0.0.1:5001"` |
| `experiment_name` | Именованный `str`, по умолчанию `housing-course` | Группа записей. Серверные тесты передают собственное уникальное имя | `experiment_name="housing-check"` |

Последовательность действий:

1. Выбери tracking URI и Experiment через SDK. Эти методы объясняются в [главе](../../README.md#как-описать-одно-обучение) и [маленьком примере](../../README.md#самостоятельный-пример-учёта).
2. Для каждой `alpha` создай отдельный run и отдельную подпапку результата.
3. Вызови подготовленную `train` с этой настройкой и seed 42. Один CSV и одинаковый seed должны давать одинаковый split.
4. Прочитай созданные файлы. Запиши короткие параметры и версии, четыре измеренные метрики и четыре артефакта по [таблице сохранения](../../README.md#что-сохраняем-после-обучения).
5. После успешного завершения run сформируй запись для сравнения. Её `run_id` берётся из SDK, а метрики и происхождение — из файлов соответствующего обучения.
6. Сохрани `output/comparison.json` и верни список трёх записей. В файле должны находиться ID и validation MAE/RMSE каждого запуска. Конкретная раскладка JSON не закреплена.

Metrics называются `validation_mae`, `validation_rmse`, `test_mae`, `test_rmse` и берутся из `metrics.json`, секции `candidate`. Params содержат SHA-256 данных, seed, настройки и версии среды. Версии можно записать отдельными короткими значениями или JSON-строкой. Полные списки индексов сохраняются в `split.json` и манифесте, дублировать их в params не требуется.

Успех означает три завершённых run с разными ID и фактически разными `alpha`. Статус `FINISHED` описывает завершение выполнения, а не прохождение проверки качества. Ошибка обучения или передачи артефакта должна оставаться видимой. Не создавай фиктивные успешные результаты, если `train` ещё не реализована.

## Шаг 3. Выбрать сравнимый запуск

```python
def select_candidate(runs: list[dict]) -> str:
    ...
```

Функция принимает список ровно из трёх записей. Она не вызывает MLflow и не обучает модели. Её задача — проверить сопоставимость и вернуть ID с наименьшей validation MAE.

| Поле записи | Тип и источник | Пример |
|---|---|---|
| `run_id` | `str`, ID из MLflow | `"example-ridge-1"` — сокращённый учебный ID |
| `status` | `str`, состояние завершённого run | `"FINISHED"` |
| `parameters` | `dict` с фактическими настройками модели | `{"alpha": 1.0}` |
| `data_sha256` | `str`, контрольная сумма CSV из манифеста | Реальный хеш файла |
| `split` | `dict` с позициями `train`, `validation`, `test` из артефактов | `{"train": [0], "validation": [1], "test": [2]}` — только пример формы |
| `validation_mae`, `validation_rmse` | Конечные неотрицательные числа из `candidate.validation` | `0.50`, `0.70` — условные значения |
| Test-метрики, если добавлены в запись | Числа из `candidate.test` | На выбор не влияют |

Допустим, три заранее выбранные настройки Ridge дали validation MAE `0.60`, `0.50`, `0.65`. Функция возвращает ID обучения с `alpha=1.0`. Эти числа иллюстрируют правило, реальные ошибки будут другими.

Сортируй по паре `(validation_mae, run_id)`. При равной MAE это даёт устойчивый выбор независимо от порядка входного списка. Следующие ситуации вызывают `ValueError`: записей не три, один run не завершён, конфигурации совпадают, SHA-256 или любая часть split различаются, validation-метрика отрицательна либо неконечна. Изменение только test-метрики не должно менять выбранный ID.

## Проверка функций и CLI

Из корня курса:

```bash
make task TASK=04-mlflow/01-experiments
```

Тесты выбора используют небольшие словари. Быстрые тесты трекинга подменяют границу MLflow, но запускают настоящее обучение на маленьком CSV. Если не завершены baseline, Pipeline или `train`, ожидается `NotImplementedError`. Ошибка отсутствующей библиотеки означает проблему подготовки среды.

После реализации запусти настоящий сценарий:

```bash
python modules/04-mlflow/tasks/01-experiments/solution.py \
  --data work/housing.csv \
  --output work/mlflow-runs \
  --tracking-uri http://127.0.0.1:5001
```

Предоставленный CLI принимает `--data`, `--output` и `--tracking-uri`. Умолчания — `work/housing.csv`, `work/mlflow-runs` и значение `MLFLOW_TRACKING_URI`, а при его отсутствии `http://127.0.0.1:5001`. Параметр `experiment_name` доступен при вызове функции из Python. Из CLI используется `housing-course`.

В интерфейсе сервера открой эту группу. Проверь три ID, `alpha`, метрики и скачивание файлов. Сопоставь с `comparison.json` и вызови `select_candidate` для возвращённого списка. Одной успешной страницы UI недостаточно для подтверждения результатов обучения.

## Локальная проверка SDK

В среде с `labs/mlflow/requirements.txt`:

```bash
MLOPS_RUN_SDK=1 python scripts/run_task.py test 04-mlflow/01-experiments -- -m sdk
```

Проверка использует настоящий MLflow, временную SQLite и каталог файлов. Сервер не нужен. Проверяется сохранённое состояние, включая скачанные артефакты, параметры настоящего Ridge и соответствие метрик прогнозам. Без флага тест пропускается. Отсутствие SDK при включённом флаге является ошибкой подготовки.

## Проверка настоящего сервера

Сначала запусти Compose, затем:

```bash
MLOPS_RUN_INTEGRATION=1 MLOPS_RUN_WRITES=1 MLFLOW_TRACKING_URI=http://127.0.0.1:5001 python -m pytest modules/04-mlflow/tasks/01-experiments/test_task.py -m integration -q
```

Оба флага обязательны для тестов с записью. Тест создаёт уникальный Experiment, вызывает твою реализацию и новым чтением сервера проверяет три завершённых run, настройки, метрики и скачанные файлы. Рабочий `work/` не используется. Временный CSV устраняет загрузку Housing, но не заменяет реализацию обучения.

Очистка относится только к собственным тестовым записям. Удаление записи MLflow не гарантирует физического удаления всех файлов сервера. Общую очистку `mlflow gc` для задания не запускай.

## Завершение

Сохрани локальные результаты и ID выбранного запуска: они понадобятся во втором задании. При остановке сервера используй `docker compose -f labs/mlflow/compose.yaml down`. Volume с историей сохраняется.
