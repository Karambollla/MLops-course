# Три запуска

[Модуль и подготовка](../../README.md#подготовка-к-заданиям) · [Все задания модуля](../../README.md#задания) · [SETUP](../../../../SETUP.md)

## Зачем объединять три обучения

У тебя уже есть `train`, который создаёт bundle и метрики. Теперь нужно сравнить настройки, сохранив связь каждого числа с его моделью и входами. MLflow хранит эти записи, а твой код определяет, какие запуски сопоставимы и кто победил по validation. Сначала прочти [путь метаданных и файлов](../../README.md#путь-параметров-метрик-и-файлов) и [правила сравнения](../../README.md#сравнимые-запуски-и-выбор).

## Что нужно подготовить

Нужны собственный [train кандидата](../../../01-ml/housing.ipynb), [манифест](../../../02-reproducibility/tasks/02-manifest/README.md), один `work/housing.csv` и один split. В отдельной среде MLflow SDK должен обращаться к поднятому Compose по `http://127.0.0.1:5001`. Заготовка содержит CLI, импорт `mlflow` в начале файла и проверку наличия SDK. Реализуются `track_experiments` и чистая проверка/выбор `select_candidate`. Само наличие импорта ещё не записывает запуск.

Внутри `track_experiments` понадобятся `set_tracking_uri`, `set_experiment`, контекст `start_run`, а затем `log_params`, `log_metrics` и `log_artifacts` с результатами собственного обучения. Их назначение и маленький рабочий пример разобраны в [самостоятельном примере SDK](../../README.md#самостоятельный-пример-учёта). Отсутствие необязательного пакета обрабатывается по [общему стандарту импортов](../../../../docs/task-structure.md#импорты).

Представь три FINISHED run A/B/C с одинаковыми SHA/split, разными `parameters` и validation MAE 0.8/0.5/0.6. Результат выбора — ID B, даже если test A лучше. При смене SHA у B должен возникнуть отказ вместо «победителя»: сравнение стало несопоставимым. Реальный выход `track_experiments` — три записи на сервере, их файлы и `comparison.json`. Маленький offline-тест выбора подтверждает только правило отбора, а не факт обучения и загрузки artifacts.

## Где работать

Редактируй [solution.py](solution.py). Проверяемое поведение описано в [test_task.py](test_task.py). Реализуй две функции. Первая сравнивает готовые записи без SDK. Вторая создаёт эти записи настоящим обучением.

## `select_candidate`: проверить сравнимость и выбрать запуск

```python
def select_candidate(runs: list[dict]) -> str:
    ...
```

| Параметр | Тип | Формат и смысл | Откуда берётся | Пример |
|---|---|---|---|---|
| `runs` | `list[dict]` | Ровно три записи запусков. Поля каждой записи разобраны ниже | Возвращается из `track_experiments`. В unit-тестах составляется вручную | Три записи с ID `A`, `B`, `C` |

| Поле записи | Тип и формат | Происхождение и пример |
|---|---|---|
| `run_id` | `str`, идентификатор запуска | MLflow `run.info.run_id`, например `"B"` в учебном примере |
| `status` | `str`, требуется `"FINISHED"` | Статус завершённого run |
| `parameters` | `dict`, разные значения конфигурации для каждого запуска | Настройки обучения, например `{"alpha": 1.0, "seed": 42}`. Перестановка ключей не делает конфигурацию новой |
| `data_sha256` | `str`, одна и та же SHA-256 CSV у всех трёх | Из манифеста. Обычно 64 шестнадцатеричных символа |
| `split` | `dict` с `train`, `validation`, `test` | Индексы строк CSV из `split.json`, например `{"train": [0], "validation": [1], "test": [2]}`. Все три части совпадают у всех запусков |
| `validation_mae`, `validation_rmse` | Конечные неотрицательные числа | Вычисленные validation-ошибки из `metrics.json`, например `0.5` и `0.6` |
| `test_mae` и другие test-метрики | Числа результатов финальной оценки | Могут присутствовать в записи, но не участвуют в выборе |

Функция возвращает строковый `run_id` с минимальной парой `(validation_mae, run_id)`. Второй ключ делает выбор независимым от порядка списка при равной MAE. Разное число записей, незавершённый run, одинаковые параметры, разные SHA/split или некорректная validation-метрика дают `ValueError`.

Небольшой вход одной записи выглядит так:

```python
{
    "run_id": "B",
    "status": "FINISHED",
    "parameters": {"alpha": 1.0},
    "data_sha256": "a" * 64,
    "split": {"train": [0], "validation": [1], "test": [2]},
    "validation_mae": 0.5,
    "validation_rmse": 0.6,
    "test_mae": 0.7,
}
```

Такой split иллюстрирует форму записи, а не достаточный набор для обучения. Если остальные две записи имеют разные `parameters`, тот же SHA/split и validation MAE `0.8` и `0.6`, результат — `"B"`. Изменение только `test_mae` не меняет выбор. При равной MAE у `"z-run"`, `"a-run"`, `"m-run"` возвращается `"a-run"`.

## `track_experiments`: обучить и сохранить результаты

```python
def track_experiments(
    data: Path,
    output: Path,
    tracking_uri: str,
    *,
    experiment_name: str = "housing-course",
) -> list[dict]:
    ...
```

| Параметр | Тип | Формат и смысл | Откуда берётся | Пример |
|---|---|---|---|---|
| `data` | `Path` | Существующий CSV: восемь FEATURES и target `MedHouseVal` | Данные курса из SETUP. В тестах синтетический CSV | `Path("work/housing.csv")` |
| `output` | `Path` | Общий каталог результатов с отдельной папкой каждого обучения и `comparison.json` | Выбирает вызывающий код | `Path("work/mlflow-runs")` |
| `tracking_uri` | `str` | Адрес backend MLflow. Для Compose HTTP, для SDK-теста локальный SQLite URI | Аргумент CLI или `MLFLOW_TRACKING_URI` | `"http://127.0.0.1:5001"` |
| `experiment_name` | `str`, только именованный аргумент | Имя группы трёх запусков. По умолчанию `housing-course` | Выбирает вызывающий код. Интеграционный тест передаёт уникальное имя | `experiment_name="housing-check"` |

Используй своё обучение кандидата из модуля 01 и манифест из модуля 02. Если ему не хватает выбора настроек модели, расширь конфигурацию обучения. Не заменяй `fit` и вычисленные метрики постоянными числами. Для каждого из трёх разных наборов параметров нужны одинаковые байты CSV и один split. Вложенные run для этого не требуются.

Сначала выбираются tracking URI и experiment. Для каждой конфигурации создаётся свой run, выполняется обучение и загружаются параметры и файлы. MLflow params должны сохранять SHA-256, настройки, split и версии окружения. Проверки допускают плоские поля, вложенные значения и JSON-строки: конкретный способ сериализации не закреплён. В metrics сохраняются измеренные validation/test MAE и RMSE.

Возвращается список трёх записей формата `select_candidate`. В MLflow остаются три `FINISHED` run с разными ID и артефактами `model.joblib`, `metrics.json`, `manifest.json`, `split.json`. В `output/comparison.json` должны присутствовать ID и validation MAE/RMSE каждого запуска. Раскладка JSON не фиксирована тестом. Например, запись сравнения может содержать `{"run_id": "B", "validation_mae": 0.5, "validation_rmse": 0.6}`. Числа в реальном результате берутся из твоих файлов.

Без установленного SDK заготовка поднимает `RuntimeError` с командой установки. Пока функция не реализована, ожидается `NotImplementedError`. Ошибка обучения или передачи данных не должна превращаться в фиктивный успешный run. Быстрые тесты заменяют только границу MLflow и действительно вызывают твоё обучение на маленьких CSV. Поэтому незавершённый baseline/Pipeline/train остаётся причиной падения.

## Среда и зависимости

Базовая среда. MLflow SDK из labs/mlflow/requirements.txt в отдельном окружении, housing установлен --no-deps -e. CPU.

Зависит от train и 02-reproducibility. Для реальных запусков подними labs/mlflow/compose.yaml, URI <http://127.0.0.1:5001>, используй track_experiments из Python. Проверь runs в UI/API MLflow. Офлайн-тест выбора кандидата не проверяет запись на сервер.

## Запуск и результат

Из корня репозитория:

```bash
make task TASK=04-mlflow/01-experiments
```

Тесты функций работают offline на маленьких входах и временных файлах. До реализации ожидается `NotImplementedError`. Ошибка импорта означает проблему подготовки среды. Проверка функций не заменяет описанный опыт на данных или стенде.

Функции доступны через `course_tasks.load_task("04-mlflow/01-experiments")`. CLI `solution.py` также предоставлен. Он принимает `--data` (по умолчанию `work/housing.csv`), `--output` (`work/mlflow-runs`) и `--tracking-uri` (сначала переменная `MLFLOW_TRACKING_URI`, иначе `http://127.0.0.1:5001`). Явный аргумент выбирает конкретный сервер для данного запуска.

## Требования практического опыта

Реализуй `track_experiments` в `solution.py`: три разных конфигурации на одном split, параметры, MAE/RMSE, data_sha256, split и model bundle. Сопоставь validation-метрики в сохранённом `comparison.json`. Не подбирай по test.

```bash
MLFLOW_TRACKING_URI=http://127.0.0.1:5001 python modules/04-mlflow/tasks/01-experiments/solution.py
```

Ожидаются три завершённых run в experiment `housing-course`. Проверь реальные run IDs в UI/API и выбор кандидата по validation MAE.

## Приёмка и очистка

Запусти указанную выше команду `make task` после реализации и исправления ошибок. Проверяемые случаи перечислены в соседнем `test_task.py`.

После опыта останови стенд: `docker compose -f labs/mlflow/compose.yaml down`. Не удаляй volume без экспорта истории. Артефакты `work/` сохрани для следующих модулей.

## Пример корректного результата

Для сопоставимых runs с validation_mae 0.8/0.5/0.6 выбирается второй run. Изменение только test_mae не влияет на выбор. Разные data_sha256 или split вызывают ValueError, а не сравнение несопоставимых запусков.

## Локальная проверка SDK

После реализации задания и его предшественников можно проверить MLflow в локальных SQLite и каталоге артефактов. Установи зависимости модуля в его окружение, затем выполни из корня курса:

```bash
MLOPS_RUN_SDK=1 python scripts/run_task.py test 04-mlflow/01-experiments -- -m sdk
```

Используются только временные данные, внешний сервер не нужен. Без флага проверка пропускается. При включённом флаге отсутствие SDK считается ошибкой подготовки окружения. Этот запуск не заменяет практику работающего стенда. Подробнее — [режимы проверок](../../../../docs/task-structure.md#локальные-проверки-sdk).

## Проверка настоящего сервера

Параметр `experiment_name` позволяет использовать отдельный experiment, по умолчанию
`housing-course`. Не зашивай имя внутри реализации. В закреплённой SDK-среде:

```bash
MLOPS_RUN_INTEGRATION=1 MLOPS_RUN_WRITES=1 MLFLOW_TRACKING_URI=http://127.0.0.1:5001 python -m pytest modules/04-mlflow/tasks/01-experiments/test_task.py -m integration -q
```

Сервер должен уже работать. Тест создаёт уникальный experiment, вызывает твою
`track_experiments` на синтетическом CSV, затем новым серверным чтением проверяет
три FINISHED run, params, вычисленные metrics, скачанные bundle/split/manifest и
численную связь прогнозов с метриками. Синтетический CSV устраняет зависимость от
`work/housing.csv`, но не реализует за тебя baseline/Pipeline/train: незавершённое
обучение по-прежнему даёт `NotImplementedError`. Ни callback fake, ни локальная
SQLite-проверка SDK не подтверждают работу HTTP artifact proxy.

Тесты с записью требуют **оба** флага, имеют markers `integration`, `writes` и
удаляют только свои уникальные model/experiment/run. MLflow soft delete experiment
не гарантирует физическое удаление файлов artifact store. Не запускай глобальный
`mlflow gc` на общей среде. Очистку изолированного учебного volume выполняй отдельно
после сохранения нужной истории.
