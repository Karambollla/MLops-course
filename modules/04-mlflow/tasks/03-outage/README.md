# Отказ

[Модуль и подготовка](../../README.md#подготовка-к-заданиям) · [Все задания модуля](../../README.md#задания) · [SETUP](../../../../SETUP.md)

## Зачем сохранять незавершённую регистрацию

Обучение может завершиться успешно, а сервер реестра оказаться недоступным. Потерять связь с исходным run или автоматически повысить champion после такой ошибки опаснее, чем оставить результат ожидающим восстановления. Здесь проверяется переход `pending → registered` с сохранением происхождения. Граница локального состояния и внешнего побочного действия разобрана в [теории отказа регистрации](../../README.md#регистрация-после-сетевого-отказа).

## Что уже есть и что добавить

Из [Registry-темы](../02-registry/README.md) нужны существующий run ID, адрес его artifact и действующая версия champion. `pending` хранит эти значения и устойчивый run key. В offline-тестах callback подменяет сетевую регистрацию. На стенде он должен регистрировать тот же обученный результат, а не запускать обучение заново. Реализуй сохранение JSON и переход состояния. Сам статус ошибки не является сигналом продвижения модели.

Например, до отказа champion=`"4"`, pending относится к `run-1`. Callback с `ConnectionError` оставляет pending на диске и champion 4. После восстановления callback возвращает `"8"`: новое состояние registered содержит version 8 и прежний run-1, но champion по-прежнему 4. Повтор уже зарегистрированного состояния не вызывает callback. Это подтверждает локальную идемпотентность. Остановка сети после создания версии на сервере, но до ответа клиенту остаётся отдельным окном неопределённости.

## Где работать и контракт функции

Редактируй [solution.py](solution.py). Сценарии проверяются в [test_task.py](test_task.py).

```python
def recover_registration(pending: dict, register, local_path: Path) -> dict:
    ...
```

| Параметр | Тип | Формат и смысл | Откуда берётся | Пример |
|---|---|---|---|---|
| `pending` | `dict` | Состояние регистрации с исходными идентификаторами. Принимается также уже `registered` состояние | Создаётся после обучения. При повторе читается из сохранённого JSON | Объект ниже |
| `register` | Вызываемый объект | `register(payload) -> str` регистрирует переданный исходный артефакт и возвращает точную версию. При недоступности поднимает `ConnectionError` | Адаптер твоей SDK-регистрации. В unit-тестах подменяется | Callback, возвращающий `"8"` |
| `local_path` | `Path` | Путь устойчивого локального JSON. Родительские каталоги могут ещё не существовать | Выбирает вызывающий код | `Path("work/registration/pending.json")` |

Пример `pending`:

```json
{"run_key": "key-1", "run_id": "run-7", "artifact_uri": "runs:/run-7/model", "status": "pending", "champion_version": "4"}
```

`run_key` связывает повторы одного смыслового обучения. `run_id` указывает исходный run. `artifact_uri` берётся из результата логирования MLflow Model и должен оставаться пригодным для регистрации. URI в примере показывает форму ссылки, а настоящий SDK может вернуть другой поддерживаемый model URI. `champion_version` — версия, которая была активной до сбоя. Её нельзя подменять версией восстановленного кандидата.

Для `status="pending"` вызывается `register` с исходным состоянием. При `ConnectionError` атомарно сохрани pending в `local_path` и верни то же содержимое. Атомарная запись означает, что читатель не увидит половину JSON. Обеспечь создание родительских каталогов. Исходный словарь не меняется.

После успешного ответа `"8"` возвращается и сохраняется:

```json
{"run_key": "key-1", "run_id": "run-7", "artifact_uri": "runs:/run-7/model", "status": "registered", "champion_version": "4", "version": "8"}
```

Повтор уже `registered` состояния возвращает прежний результат и не вызывает callback. `ValueError` и другие неожиданные ошибки пробрасываются. Они не означают сетевой отказ. Функция не обучает модель заново и не меняет alias champion. Она подтверждает локальную идемпотентность, но не exactly once между клиентом и сервером при потере ответа после создания remote version.

## Среда и зависимости

Для быстрых проверок используй основную среду Python с pytest из [SETUP](../../../../SETUP.md#основная-среда). Функции работают на CPU под Linux/macOS.

Зависит от 04-mlflow/02-registry. Реальный outage выполняй на учебном Compose, не удаляя volume. Ожидаемое поведение на стенде: исходный run и bundle доступны после восстановления, champion не поменялся из-за ошибки.

## Запуск и результат

Из корня репозитория:

```bash
make task TASK=04-mlflow/03-outage
```

Тесты функций работают offline на маленьких входах и временных файлах. До реализации ожидается `NotImplementedError`. Ошибка импорта означает проблему подготовки среды. Проверка функций не заменяет описанный опыт на данных или стенде.

Это задание использует функции. Импортируй заготовку через `course_tasks.load_task("04-mlflow/03-outage")` из Python. CLI не требуется.

## Требования практического опыта

Останови сервер и запусти регистрацию ещё раз. Проверь исключение и сохранённое локальное состояние. Запусти сервер обратно и восстанови регистрацию без потери связи с исходным запуском. Не продвигай кандидата автоматически после ошибки.

## Остановка и восстановление реального сервера

Сначала при работающем MLflow сохрани исходные `run_id`, `artifact_uri` и `champion_version`. Подготовь pending для собственного артефакта. Файл `local_path` находится у клиента, а backend/artifacts — в серверном volume. Останови только сервис, сохранив его данные:

```bash
docker compose -f labs/mlflow/compose.yaml stop mlflow
```

Вызови `recover_registration` с callback настоящей регистрации. SDK может оборачивать сетевой отказ в собственное исключение. Контракт учебной функции обрабатывает именно `ConnectionError`: callback должен перевести в него распознанную недоступность сети. Не превращай любую ошибку MLflow в `ConnectionError`, иначе неверная модель окажется ложным pending.

Проверь локальный JSON: исходные идентификаторы и champion сохранены, status остался pending. Затем восстанови тот же сервер:

```bash
docker compose -f labs/mlflow/compose.yaml start mlflow
curl --fail --max-time 10 http://127.0.0.1:5001/health
```

Повтори регистрацию с сохранённым pending. Проверь конкретную version и связь с прежним run через Registry, а также скачивание исходного артефакта. Ещё один вызов с уже registered результатом не должен создавать новую версию. Alias champion сравни с исходным: восстановление кандидата его не продвигает.

## Приёмка и очистка

Запусти указанную выше команду `make task` после реализации и исправления ошибок. Проверяемые случаи перечислены в соседнем `test_task.py`.

После опыта останови стенд: `docker compose -f labs/mlflow/compose.yaml down`. Не удаляй volume без экспорта истории. Артефакты `work/` сохрани для следующих модулей.

## Пример корректного результата

При ConnectionError состояние остаётся pending, исходный run_id сохраняется, champion не продвигается. Успешный повтор меняет status на registered и сохраняет точную version. Повтор уже registered не вызывает регистрацию снова.

## Серверная интеграционная проверка

При работающем стенде и установленном `labs/mlflow/requirements.txt`:

```bash
MLOPS_RUN_INTEGRATION=1 MLOPS_RUN_WRITES=1 MLFLOW_TRACKING_URI=http://127.0.0.1:5001 python -m pytest modules/04-mlflow/tasks/03-outage/test_task.py -m integration -q
```

Тест создаёт собственные уникальные experiment/model, использует маленький
синтетический Pipeline и удаляет только свои записи в finally. Не требуется
существующая обученная housing-модель. Обязательны оба флага записи.
markers — `integration`, `writes`. Ограничение soft delete файлов описано в
[теме экспериментов](../01-experiments/README.md#проверка-настоящего-сервера).
Проверяется student `recover_registration`: отказ до запроса, durable pending,
реальная регистрация исходного SDK artifact, повтор registered без второго вызова
и без новой версии, неизменный champion. Отказ перед запросом **инъецирован**:
этот тест не выключает сервер и не доказывает обработку потери ответа после commit.
Описанный выше ручной опыт остановки/восстановления стенда остаётся обязательным.
