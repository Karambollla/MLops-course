# Сравнение inference latency

[Теория](../../README.md) · [Практика модуля](../../practice.md) · [Подсказки](../../hints.md)

## Какой вопрос решает измерение

Triton добавляет scheduler и batching, но маленький Pipeline может не стать быстрее FastAPI. Нужно измерить одинаковые запросы, а не сравнить конфигурации. [Latency и throughput](../../README.md#как-сравнивать-latency-и-throughput) объясняют wall time, concurrency и линейный percentile.

Предоставлены `solution.py` и CSV `benchmark.csv` с заголовком `request_id,engine,hardware,batch,concurrency,latency_ms,status`. Для функции нужны только строки измерений; она работает на локальном CPU в [основном окружении](../../../../SETUP.md). Полное сравнение требует работающих FastAPI и Triton с одной моделью на совместимом Linux x86_64 стенде. Это сравнение CPU-serving из данного config, не GPU-benchmark.

## Контракт функции

Реализуй `latency_summary(rows,elapsed_seconds,min_requests=200) -> dict`. Возвращаются `p50_ms`, `p95_ms`, `throughput_rps`, `error_ratio`.

В rows задержки `latency_ms` конечные и неотрицательные, status — HTTP-статус. Должно быть не меньше min_requests строк и положительное конечное elapsed_seconds. Неверные данные вызывают ValueError. p50/p95 вычисляются линейной интерполяцией по задержкам всех строк; error_ratio — доля status>=400. Throughput равен len(rows)/elapsed_seconds, где elapsed_seconds — общая длительность измеряемой серии. Не используй сумму индивидуальных latency вместо времени серии.

Для задержек 10/20/30 ms за 1 s и одного status=500 при min_requests=3 правильны p50=20 ms, p95=29 ms, throughput=3 rps и error_ratio=1/3. Здесь 29 получается интерполяцией на 90% пути от 20 к 30. Это вычисляемая фикстура; она не доказывает скорость сервера.

## Выполнить сравнение

Сначала убедись, что оба сервиса дают численно эквивалентный прогноз на одних строках. Прогрей модель, затем собери минимум 200 запросов отдельно для concurrency 1 и 4. Используй одинаковые input/batch и сопоставимые условия CPU/нагрузки. Сохраняй каждую строку, полное wall time, версии/настройки и сведения о ресурсах. Не смешивай warmup с измерениями; batch внутри запроса и число параллельных запросов — разные параметры.

Вывод оценивается по нескольким величинам: рост throughput при ухудшении p95 может быть разумным компромиссом, а рост доли ошибок требует отдельного объяснения. Метрики 8002 показывают внутреннюю сторону Triton и не заменяют клиентский интервал.

```bash
make task TASK=15-triton/03-benchmark
```

CLI нет; тесты проверяют только функцию агрегации. Без совместимого Triton можно выполнить CPU-часть с фикстурами, но не объявлять её сравнением реальных серверов. Сохрани исходные данные в `work/` и останови Triton командой `docker compose -f labs/triton/compose.yaml down`. План или письменный отчёт не требуются.
