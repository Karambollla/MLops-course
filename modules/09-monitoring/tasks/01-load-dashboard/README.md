# Нагрузка и dashboard

[Модуль](../../README.md) · [Задания](../../README.md#задания) · [Общая подготовка](../../README.md#подготовка-к-заданиям)

## Что уже подготовлено

HTTP-инструментация housing API считает ответы и длительности. Compose запускает API, Prometheus и Grafana. В [solution.py](solution.py) оставлены две учебные функции с импортами HTTP-клиента, `perf_counter`, `ThreadPoolExecutor` и NumPy. [scenario.json](scenario.json) содержит фиксированные измерения для теста расчётов. Он не является результатом обращения к твоему API. [dashboard.json](dashboard.json) содержит заголовок и пустой список панелей.

Увеличение concurrency, числа одновременно выполняемых запросов, может поднять throughput и ухудшить хвост задержек. Ты сначала рассчитываешь сводку готовых измерений, затем создаёшь настоящую нагрузку и сравниваешь её с dashboard. Прочти [путь метрики](../../README.md#путь-запроса-и-путь-метрики) и [формулы PromQL](../../README.md#счётчики-длительность-и-запросы).

## Расчёт сводки: `summarize_run`

Точная сигнатура заготовки:

```python
def summarize_run(run):
    ...
```

| Аргумент | Тип и формат | Откуда берётся | Пример |
|---|---|---|---|
| `run` | `dict` с полями серии из таблицы ниже | Элемент `runs` из scenario или результат `measure_load` | `{"concurrency": 1, "requests": 20, "seconds": 4, "status_counts": {"200": 18, "503": 2}, "p95_seconds": 0.2}` |

| Поле `run` | Тип и формат | Смысл и пример |
|---|---|---|
| `concurrency` | Положительное целое | Число одновременных запросов, например `4` |
| `requests` | Неотрицательное целое | Число ответов во всей серии, например `200` |
| `seconds` | Конечное число строго больше нуля | Общая длительность серии в секундах, например `10.0` |
| `status_counts` | Словарь `str → int` с неотрицательными counts | Строковые HTTP-коды, например `{"200": 190, "503": 10}`. Сумма counts равна `requests` |
| `p95_seconds` | Конечное неотрицательное число при трафике, `None` без запросов | Уже измеренная p95, например `0.08` секунды. По counts статусов её восстановить нельзя |

Верни словарь ровно с тремя полями:

| Поле результата | Расчёт | Пример для 20 ответов за 4 секунды, из них два 503 |
|---|---|---|
| `rps` | `requests / seconds` | `5.0` |
| `error_ratio` | Число ответов 500–599, делённое на `requests` | `0.1` |
| `p95_seconds` | Входная p95 без изменения | `0.2` |

4xx не входят в серверные ошибки 5xx. При нулевом трафике верни `{"rps": 0, "error_ratio": None, "p95_seconds": None}`. Ноль ошибок при отсутствии запросов не доказывает работоспособность. Неверные counts, несовпадение их суммы с requests, недопустимые seconds/concurrency/p95 и неконечные измерения должны вызывать `ValueError`.

Для первого run в scenario ожидается `{"rps": 20, "error_ratio": 0.05, "p95_seconds": 0.08}`. Для второго — `{"rps": 50, "error_ratio": 0, "p95_seconds": 0.1}`. Это примеры результата, а не реализация.

## Реальные измерения: `measure_load`

```python
def measure_load(
    url: str, payload: dict, requests: int = 200, concurrency: int = 1
) -> dict:
    ...
```

| Аргумент | Тип и формат | Откуда берётся и зачем нужен | Пример |
|---|---|---|---|
| `url` | `str`, полный HTTP URL маршрута `/predict` | Выбирается для запущенного API. Это адрес запроса, без дополнительного дописывания `/predict` внутри клиента | `"http://127.0.0.1:8000/predict"` |
| `payload` | `dict`, JSON-совместимое тело с `instances` | Загружается из `labs/housing/request.json`. Один HTTP-запрос может содержать несколько районов | `json.loads(Path("labs/housing/request.json").read_text())` |
| `requests` | Положительное целое, default `200` | Число настоящих POST-запросов всей серии, а не количество строк в instances | `24` |
| `concurrency` | Положительное целое, default `1` | Число запросов, которые могут выполняться одновременно | `2` |

Выполни заданное количество POST с JSON и `Content-Type: application/json`. Измерь длительность каждого запроса через `perf_counter`, а также общее время серии. При параллельном выполнении общее время не равно сумме длительностей. Не включай warmup и `/metrics` в эту серию. Сохраняй HTTP 4xx/5xx как полученные статусы, в том числе когда клиент представляет их исключением HTTPError. Сетевая ошибка не является HTTP-ответом: не превращай её в успешный 200. Фиксированная схема специального кода для сетевого отказа заданием не установлена.

Верни dict с полями `concurrency`, `requests`, `seconds`, `status_counts`, `p95_seconds` в формате `summarize_run` и дополнительным `durations_seconds`: список по одной конечной неотрицательной длительности в секундах на каждый ответ. p95 рассчитывается по исходным длительностям как 95-й процентиль с линейной интерполяцией. Например, для длительностей `[0.1, 0.2]` p95 равна `0.195`.

Форма результата двух успешных ответов может быть такой:

```json
{
  "concurrency": 1,
  "requests": 2,
  "seconds": 0.31,
  "status_counts": {"200": 2},
  "p95_seconds": 0.195,
  "durations_seconds": [0.1, 0.2]
}
```

Реальные числа зависят от стенда. Передай результат в `summarize_run`. Исходные длительности сохрани отдельно от сводки, чтобы можно было перепроверить квантиль.

## Проверка функций

Основное Python-окружение достаточно для фиксированных тестов. Docker, модель и сервер не нужны:

```bash
make task TASK=09-monitoring/01-load-dashboard
```

[test_task.py](test_task.py) проверяет расчёт сводок и ошибочные входы. До реализации `summarize_run` ожидается `NotImplementedError`. Проверка реального `measure_load` без специальных флагов пропускается.

## Нагрузка живого API и Prometheus

Подготовь [Compose-стенд](../../README.md#подготовка-к-заданиям) со своим bundle. Проверь `/ready` до измерения. Образ монтирует `work/artifacts` как `/models:ro`. Без модели API может отдавать метрики, но predict даст 503.

```bash
docker compose -f labs/monitoring/compose.yaml up -d --build
curl --fail http://127.0.0.1:8000/ready
MLOPS_RUN_INTEGRATION=1 MLOPS_RUN_WRITES=1 HOUSING_URL=http://127.0.0.1:8000 PROMETHEUS_URL=http://127.0.0.1:9090 python scripts/run_task.py test 09-monitoring/01-load-dashboard -- -m writes
```

`HOUSING_URL` — базовый адрес API без `/predict`, его добавляет сам live-тест. `PROMETHEUS_URL` — базовый адрес Prometheus на компьютере. [test_live.py](test_live.py) вызывает твою функцию с `requests=24, concurrency=2`, проверяет 24 статуса 200, p95 по длительностям и увеличение `http_requests_total{route="/predict"}` после scrape. Тест создаёт реальный трафик и требует оба флага. Не запускай его одновременно с другими нагрузочными опытами.

Затем измерь по 200 запросов с concurrency 1 и 4 своей функцией. Например, 200 ответов за 10 секунд дают 20 RPS. Сохрани длительности, counts и сводки. Это полезные исходные измерения, не отдельный письменный отчёт.

## Dashboard

Редактируй `dashboard.json`: добавь панели latency и error ratio и импортируй JSON в Grafana на порту 3000. Поле `title` задаёт имя dashboard, `panels` — описания панелей с PromQL-запросами. В Grafana выбери provisioned datasource Prometheus (`http://prometheus:9090` внутри сети Compose). Локальный вход — `student` / `local-course-only`.

Для RPS используй rate счётчика `/predict`. Для 5xx/all — отношение rates за одинаковое окно. Для p95 — `histogram_quantile` по объединённым buckets с сохранением `le`. Полные запросы разобраны в [теории](../../README.md#счётчики-длительность-и-запросы). Не усредняй p95 экземпляров и исключи `/metrics` из бизнес-RPS.

Подожди несколько scrape intervals: rate требует нескольких samples. Клиент измеряет конкретную серию, Prometheus оценивает скользящее окно, а histogram даёт приближение по buckets. Поэтому числа могут различаться. Тест нагрузки не проверяет настройку панелей. Экспортируй свой dashboard JSON перед удалением Grafana volume.

## Остановка

```bash
docker compose -f labs/monitoring/compose.yaml down
```

Compose down сохраняет named volumes. Собственный bundle и JSON dashboard пригодятся для следующих опытов.
