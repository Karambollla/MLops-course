## Зачем объединять выдачи

Keyword search может найти точный термин, а vector search — перефразировку. Требуется общий порядок документов, хотя scores имеют разные шкалы. [Разобранный RRF](../../README.md#гибридное-ранжирование-через-rrf) объединяет позиции и не зависит от доступности server-side hybrid API.

В соседнем [solution.py](solution.py) реализуй одну функцию объединения. Для применения уже есть lexical/vector выдачи предыдущих заданий и qrels из модуля 13. Для чистой функции достаточно маленьких списков IDs в [основном CPU-окружении](../../../../SETUP.md). Сервер не нужен. Заготовка `solution.py` не содержит транспорт или benchmark CLI.

## Вход и результат объединения

Сначала разберём условный каталог с документами A, B, C. Первый поисковый сигнал поставил A перед B, второй — B перед C. Для численного теста этим документам назначены IDs 1, 2, 3: вход `[[1,2],[2,3]]`. Это отдельный пример формулы. IDs не обозначают измеренные места документов основного корпуса.

```python
def reciprocal_rank_fusion(rankings: list[list], constant: int = 60) -> list[dict]:
    ...
```

| Параметр | Тип | Формат и смысл | Откуда взять | Пример |
|---|---|---|---|---|
| `rankings` | `list[list]` | Несколько выдач IDs. В каждой порядок от лучшего результата к худшему | IDs результатов lexical_search и vector_search | `[[1,2],[2,3]]` |
| `constant` | `int` | Неотрицательное сглаживание рангов. Это не число кандидатов | Выбранная настройка RRF | `60` |

Не передавай hits со score целиком: нужны именно IDs одинакового типа. Для примера ожидается порядок `[2,1,3]` и элементы вида `{"id":2,"score":0.032522...}`. Score здесь вычислен правилом RRF и не является cosine или вероятностью. Функция не обращается к SDK и не меняет исходные ранги.

## Контракт функции

Реализуй `reciprocal_rank_fusion(rankings,constant=60) -> list[dict]`. Каждый элемент результата содержит `id` и `score`. Score — сумма `1/(constant+rank)` по входным выдачам, rank начинается с 1. Один ID учитывается только на первом вхождении внутри одного списка. Позиции других элементов не сдвигаются. Результат сортируется по убыванию score, при равенстве сохраняется порядок первого появления в исходных списках. Пустой набор выдач даёт пустой список. Отрицательная constant — ValueError.

Для `[[1,2],[2,1]]` оба документа получают `1/61+1/62`, результат IDs — `[1,2]` по правилу равенства. Для `[[1,1,2],[2]]` ID1 получает `1/61`, ID2 — `1/63+1/61`: третья позиция не превращается во вторую после удаления дубля. Это примеры ожидаемого поведения, а не реализация функции.

## Проверка формулы и применение к выдачам

```bash
make task TASK=14-elasticsearch-opensearch/03-comparison
```

Тесты вызывают функцию напрямую. До реализации ожидается NotImplementedError. Затем примени RRF с c=60 к реальным lexical/vector спискам. Сравни keyword/vector/hybrid по Recall@2 и среднему reciprocal rank на одних qrels. Зафиксируй глубину каждой исходной выдачи — candidate pool — и конечный k, иначе меняется ещё и число доступных кандидатов.

Если CPU embeddings из модуля 13 уже подготовлены, повтори то же сравнение на них. Создай новые индексы с фактической размерностью и одинаковыми векторами в обоих движках. Сохрани model revision, qrels, исходные выдачи и параметры. Хороший результат на ручных векторах не доказывает качество encoder. Правильная формула RRF не гарантирует рост релевантности.

Функция сама не управляет сервисами. Если они запускались для измерений, останови соответствующий Compose-стенд с сохранением volume.

## Связь с SDK-практикой

После реализации функций соседних заданий запусти их integration/writes тесты по командам README. Они загружают корпус студенческим ingest, вызывают студенческие lexical_search/vector_search и передают реальные списки int IDs в твою reciprocal_rank_fusion. Результат проверяется по множеству кандидатов и Recall@2 через ranking_metrics модуля 13. Чистые unit-тесты RRF остаются отдельной проверкой формулы. Фиксированные списки сами по себе не подтверждают взаимодействие с движком.
