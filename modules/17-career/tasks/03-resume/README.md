## От выполненной работы к пункту резюме

Читатель резюме не видел курс и не знает, какие сервисы были реально запущены. Полезно дать действие, результат и условия, чтобы отличить собственный вклад от перечисления материалов. Основа — [формула пункта](../../README.md#резюме-как-проверяемое-описание-вклада) и [границы доказательств](../../README.md#от-утверждения-к-доказательству).

Исходные сведения — собственный код, реальные метрики и сценарии восстановления. Ниже только рекомендации: обязательного резюме, списка вакансий, отчёта, теста и публикации нет. Образцы не являются готовыми достижениями. Квадратные скобки заменяются проверенными данными или удаляются вместе с неподтверждённой частью.

## Примеры для разного фактического опыта

- «Разработал учебный локальный pipeline и API для [задача]. MAE на фиксированном test изменилась с [baseline] до [candidate]. Данные и модель связаны через [реальный hash/manifest]».
- «Добавил проверку контракта признаков и readiness модели. Проверил [реальные ошибочные запросы] и восстановление версии [реальный ID]».
- «Сравнил [реально запущенные engines] на [hardware], batch [N], concurrency [N], одном корпусе и [число] запросах после warmup. P95 [до] → [после] ms, error_ratio [значение]».

Слова «реализовал», «проверил на локальном стенде» и «изучил» означают разные объёмы опыта. Для ClearML offline подходит «сохранял параметры, метрики и артефакты обучения в offline-сессии», если это выполнялось. Отдельно можно назвать изучение очереди, не приписывая запуск Agent.

Если GPU не было: «Реализовал CPU-оценку памяти весов/KV cache и разбор SSE. Изучил протокол измерения TTFT, практического NVIDIA-serving пока нет». Локальный учебный кластер не следует описывать как многопользовательскую production-платформу или проверенный SLA.

## Как проверить числовой пункт

Относительное снижение MAE считается `(baseline-candidate)/baseline*100%` при baseline>0. Условные 100→90 дают 10%. 100→80 — 20%. Нужны один test и единицы ошибки. Если test менялся, разницу нельзя уверенно приписать модели.

Для скорости различай «latency уменьшилась в 2 раза» и «throughput вырос в 2 раза». При concurrent запросах это не одно следствие. Например, p95=100→50 ms на одинаковой нагрузке означает уменьшение этой percentile вдвое, но без wall time нельзя вывести requests/s. Если доля ошибок выросла, успешность также входит в интерпретацию. Эти числа — примеры арифметики, не результаты проекта.

Рядом с формулировкой полезно уметь открыть исходный CSV/JSON измерений и конфигурацию. Скриншот среднего без batch, hardware и числа запросов не позволяет восстановить условия. Файл с пустым benchmark-массивом не является измерением.

## Как выбрать содержание под роль

Для инфраструктурной роли выдели поставку, права, диагностику и восстановление. Для ML-роли — данные, split, baseline и качество. В обоих случаях нужен собственный вклад. Go полезен для gateways, API и эксплуатации. Python/NumPy нужны для чтения реального ML-кода. Необязательно перечислять каждый продукт курса.

Пример сопоставления опыта:

| Навык | Возможное подтверждение | Корректная граница |
|---|---|---|
| Python Pipeline | Обучение и проверка входа/прогнозов | Не равнозначен разработке новой ML-архитектуры |
| Kubernetes | Развёрнутый учебный Deployment и readiness | Не означает администрирование общего кластера |
| Поиск | Корпус, qrels и сравнение lexical/vector | Ручные 4D-векторы не проверяют encoder |
| GPU-serving | Реальный engine, запрос и исходные измерения | Теория/CPU fixtures остаются отдельным опытом |

Конкретные вакансии зависят от рынка. Можно посмотреть реальные объявления, выделить повторяющиеся требования и сравнить с такими подтверждениями. Следующий шаг выбирается по существенному пробелу интересующей роли, а не по длине списка технологий. Подробная логика — в [выборе следующего шага](../../README.md#как-выбрать-следующий-шаг).
