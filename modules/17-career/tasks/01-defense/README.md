## От набора инструментов к понятной истории

Собеседник видит репозиторий впервые. Полезно сначала объяснить, что предсказывается и зачем, а затем показать движение конкретного входа до наблюдаемого результата. Описание ролей компонентов — в [пути данных](../../README.md#предметный-сценарий-и-путь-данных), правила доказательства — в [таблице утверждений](../../README.md#от-утверждения-к-доказательству).

Исходный материал — собственный код обучения/API, реальные метрики, manifest и доступный локальный стенд. Если часть ещё не выполнена, рассказ ограничивается проверенными шагами. Это рекомендации: нет обязательного выступления, записи, отчёта или теста. Результат для себя — связное объяснение и воспроизводимые примеры, а не заполненный шаблон.

## Пример связного рассказа

«Я построил учебный локальный сервис оценки стоимости жилья. Одна строка — район, модель получает восемь числовых признаков и прогнозирует стоимость в единицах 100000 USD. До выбора модели отделил test; preprocessing и регрессор сохранил одним Pipeline. Baseline дал MAE [baseline], кандидат — [candidate] на тех же строках. Это оценка на конкретных данных, не обещание качества для любого города.

Для каждого выпуска связываю hash CSV, split, версию кода и файл модели. API проверяет схему признаков, readiness — загрузку артефакта. В демонстрации показываю корректный запрос, нарушение схемы и [реально выполненный возврат версии].

В учебном инциденте [что сломалось] я увидел [сигнал], проверил [гипотезу] и восстановил [компонент]. Технические latency и ошибки доступны без target. MAE на новых данных появится после получения фактических ответов и соединения с prediction IDs/версиями. Production-трафик и общий SLA я не проверял».

Квадратные скобки означают собственные сведения. Если rollback не выполнялся, подойдёт «предусмотрел путь возврата, практическую проверку ещё не сделал». Числовой расчёт MAE и единиц разобран в [теории](../../README.md#от-утверждения-к-доказательству).

## Небольшая демонстрация взаимодействий

Можно выбрать одну строку валидных признаков из своего test и проследить её без смены модели:

| Действие | Что удобно показать | Какой вывод допустим |
|---|---|---|
| Прочитать readiness | Статус и model_version загруженного bundle | API знает нужную модель |
| Отправить корректный запрос | Количество predictions равно числу instances, числа конечные | Данный вход вычислен |
| Убрать обязательный признак | Ошибка клиентского контракта, а не тихая подстановка | Проверка схемы реагирует на этот случай |
| Вернуть прежнюю модель | Версия и прогноз после переключения | Возврат действительно затронул артефакт |

Точные endpoint и JSON бери из [сервиса курса](../../../../labs/housing/README.md) или своего задокументированного API. Один HTTP 200 не подтверждает качество, а отсутствие падения после rollback не доказывает загрузку нужной версии. Больше о проверяемых границах — в [демонстрации](../../README.md#как-построить-демонстрацию).

На вопрос «зачем Airflow?» пример рассуждения: «Для нескольких зависимых шагов нужны история и повторы. Для одной независимой команды сначала рассмотрел бы cron. При повторе публикации проверяю устойчивый ключ выпуска». Это объясняет роль инструмента и границу более простого решения.

## Если демонстрация пошла иначе

Если API не ready, можно показать диагностику: путь модели, доступность файла, проверка bundle и logs. Не стоит объяснять сетевой отказ плохим качеством модели: это разные уровни. Если прогноз отличается, сначала сравни версию, порядок признаков и вход, затем численные библиотеки. Подготовленные исходные измерения помогают обсуждать результат, даже когда дополнительный GPU-стенд недоступен.

Другой инженер может попробовать README с чистого окружения. Скрытые пути и зависимости полезно исправить в документации. Публикация проекта и доступ к внешним аккаунтам остаются отдельным решением автора.
