# Показать проект через один рабочий сценарий

[Модуль](../../README.md) · [Все темы](../../README.md#задания)

## Что показать собеседнику

Представь, что другой разработчик впервые открывает твой репозиторий. Он видит много конфигураций, но ещё не понимает, какую задачу решает система и что в ней сделал ты. Начни с одного входа и проведи его до наблюдаемого результата. Основной порядок разобран в [главе о демонстрации](../../README.md#как-построить-демонстрацию).

Используй собственный код, артефакты и доступный стенд. Это рекомендации по рассказу, обязательного выступления, записи и письменной сдачи нет.

## Пример связного рассказа

Для учебного Housing-проекта начало могло бы выглядеть так:

> Я построил локальный сервис прогнозирования стоимости жилья. На входе характеристики района, на выходе прогноз в единицах исторического датасета. Сначала сравнил модель с постоянным ответом, затем сохранил выбранный Pipeline вместе с данными о его происхождении.
>
> На фиксированном test baseline дал MAE [своё значение], кандидат — [своё значение]. Конфигурацию выбирал по validation. API загружает этот же Pipeline и возвращает идентификатор модели. В демонстрации покажу запрос, ошибку входной схемы и [реально выполненный сценарий восстановления].

Квадратные скобки обозначают собственные результаты. Если восстановление не выполнялось, можно описать подготовленный механизм и его границу. Для текстового классификатора начало было бы о письме и его классе, для поиска — о запросе и подходящих документах. В обоих случаях сначала появляется понятная задача, затем инструменты.

## Небольшая демонстрация взаимодействий

Выбери действия, которые ты действительно проверял:

1. Открой исходный run или локальный комплект артефактов. Покажи хеш данных, split и конфигурацию, из которых получена модель.
2. Загрузи сервис с выбранным bundle и выполни корректный запрос из своего README.
3. Сопоставь версию и прогноз с ожидаемым артефактом. Отправь запрос без обязательного признака и покажи отказ схемы.
4. Если есть проверенный откат, переключи согласованную версию образа и модели, затем прочитай версию в новом ответе.
5. Покажи одну связанную метрику или сигнал отказа, если это входит в твою реализацию.

Конкретные команды сервиса находятся в [модуле 03](../../../03-service-ci/README.md). Загрузка модели, код HTTP 200 и качество прогноза подтверждают разные вещи. Объясни, какую из них показывает каждое действие.

## Если демонстрация пошла иначе

Допустим, `/live` отвечает, а `/ready` возвращает 503. Это повод проверить путь и загрузку модели. Если HTTP 200 есть, но числа отличаются от Pipeline, проверь паритет, порядок признаков и выбранную версию. Так ты показываешь последовательность проверки гипотез, а не угадывание команды.

Не запускай неиспробованные сценарии отказа ради эффектности. Для рассказа достаточно фактического симптома, команды различающей проверки и наблюдаемого восстановления. Если новый читатель не может повторить доступную часть по README, уточнение инструкции полезнее добавления ещё одного названия инструмента.
