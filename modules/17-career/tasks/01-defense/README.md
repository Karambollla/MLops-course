# Как представить собственный проект

[Теория](../../README.md) · [Практика модуля](../../practice.md) · [Подсказки](../../hints.md)

Это рекомендации и пример рассказа. Здесь нет обязательных отчётов, записи выступления или тестов. Подставляй только факты своего проекта.

## Пример связного рассказа

«Я построил учебный локальный сервис оценки стоимости жилья. До обучения отделил test; preprocessing и регрессор сохранил одним Pipeline. DummyRegressor дал MAE [baseline], кандидат — [candidate] на том же test. Это оценка на конкретном наборе, а не обещание качества для другого города.

Для каждого выпуска связываю hash данных, версию зависимостей и модель. API проверяет схему признаков; отсутствие обязательного поля возвращает ошибку клиента. Readiness проверяет загрузку модели. В демонстрации выполняю один корректный запрос, один с нарушением контракта и запрос после возврата предыдущей версии.

В учебном инциденте [что действительно сломалось] я увидел [сигнал], проверил [гипотезу] и восстановил [что]. Мониторинг latency и ошибок работает без target. MAE на новых данных появится только после получения разметки и соединения с сохранёнными prediction IDs. Многопользовательскую эксплуатацию и SLA я не проверял».

Квадратные скобки обозначают собственные данные, а не готовые достижения. Если rollback ещё не выполнялся, говори «планирую проверить возврат версии», не «проверил».

## Что удобно показать

Открой README запуска, реальный запрос к API, версию модели и исходные измерения сравнения. Объясни, откуда взялся test и почему он не использовался при выборе параметров. Для rollback покажи версию и прогноз после переключения: один статус 200 не доказывает возврат нужного артефакта.

На вопрос «зачем Airflow?» пример ответа: «Для нескольких зависимых шагов нужны история, повторы и наблюдаемость. Для одного небольшого ежедневного скрипта я сначала рассмотрел бы cron. При повторе публикации использую устойчивый ID выпуска, чтобы не создавать второй результат».

Другой инженер может попробовать инструкции с чистого окружения. Любое место, где приходится угадывать путь или версию, полезно исправить в README. Это способ улучшить проект, а не обязательная процедура сдачи.
