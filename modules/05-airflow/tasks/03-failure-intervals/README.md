# Сбой и интервалы

[Модуль и подготовка](../../README.md#подготовка-к-заданиям) · [Все задания модуля](../../README.md#задания) · [SETUP](../../../../SETUP.md)

## Зачем повтору нужен прежний интервал

Повтор упавшей публикации должен использовать сохранённые артефакты и тот же временной вход. Если вычислить дату через `now()`, повтор вчерашней работы завтра станет обработкой другой части данных. Здесь интервал становится явной частью состояния, а восстановление не создаёт новую смысловую публикацию. Перед работой прочти [раздел об интервале и восстановлении](../../README.md#интервал-данных-и-восстановление-шага).

## Исходное состояние

Нужны DAG [первой темы](../01-pipeline/README.md), идемпотентный [publish](../02-gate-retry/README.md) и готовый отдельный output. `interval_manifest` нормализует переданные моменты, `resume_publish` управляет переходом evaluated/published, не меняя исходный state. На стенде добавляется ежедневное UTC-расписание и небольшой опыт на двух прошлых интервалах. Housing остаётся одним статическим CSV: задание проверяет идентичность интервала, а не появление новых ежедневных наблюдений.

Для ежедневного интервала выбери явный `CronDataIntervalTimetable`, как объясняется в [разделе о расписании](../../README.md#интервал-данных-и-восстановление-шага): cron-строка с настройками Airflow 3.1.0 по умолчанию может выбрать trigger-семантику с нулевой длиной интервала. Проверка `interval_manifest` должна выявлять такую ошибку настройки, а не достраивать сутки из `now()`.

Вход `2025-01-01T03:00:00+03:00` → `2025-01-02T03:00:00+03:00` должен дать UTC-полуночи и partition `2025-01-01`. После исключения перед publish состояние остаётся evaluated с тем же interval и artifact_path. Повтор вызывает publish, возвращает published и release. Ещё один повтор уже не вызывает callback. Offline-тест доказывает переход функции, а очередность retry и чтение интервала из контекста подтверждаются в реальном DAG по логам конкретной task instance.

## `interval_manifest`: нормализовать границы интервала

```python
def interval_manifest(start: str, end: str) -> dict:
    ...
```

| Параметр | Тип | Формат и смысл | Откуда берётся | Пример |
|---|---|---|---|---|
| `start` | `str` | ISO 8601 datetime с часовым поясом, начало интервала включительно | `data_interval_start` контекста Airflow, преобразованный в строку | `"2025-01-01T03:00:00+03:00"` |
| `end` | `str` | ISO 8601 datetime с часовым поясом, конец интервала не включается | `data_interval_end` того же контекста | `"2025-01-02T03:00:00+03:00"` |

Нужны `end > start` и ровно 24 часа после преобразования в UTC. Строки с `Z` допустимы. Дата без времени/зоны, строка с неверным форматом, одинаковые или обратные границы и другая длительность дают `ValueError`. Не вычисляй интервал из `now()`.

Для двух строк из таблицы возвращается:

```json
{"data_interval_start": "2025-01-01T00:00:00+00:00", "data_interval_end": "2025-01-02T00:00:00+00:00", "partition": "2025-01-01"}
```

Границы выводятся в UTC с `+00:00`. `partition` — дата UTC-начала. Она может отличаться от даты во входной строке: `2025-02-01T01:00:00+02:00` соответствует UTC-дате `2025-01-31`. Чистая функция требует длительность, но не требует начала в полночь. Ежедневный DAG и его интеграционная проверка дополнительно требуют UTC-полуночи для двух выбранных запусков.

## `resume_publish`: повторить незавершённый шаг

```python
def resume_publish(state: dict, publish_fn) -> dict:
    ...
```

| Параметр | Тип | Формат и смысл | Откуда берётся | Пример |
|---|---|---|---|---|
| `state` | `dict` | `run_key`, `artifact_path`, `status`, `interval`. Для опубликованного состояния также `release` | Сохранённый результат оценки и интервал того же DAG run | Объект ниже |
| `publish_fn` | Вызываемый объект | `publish_fn(state) -> dict` публикует исходный результат и возвращает release | Адаптер идемпотентного `publish` предыдущей темы | Callback с результатом `{"version": "7"}` |

Пример входа:

```python
{
    "run_key": "key-1",
    "artifact_path": "/work/runs/key-1",
    "status": "evaluated",
    "interval": {"partition": "2025-01-01"},
}
```

`artifact_path` — каталог готового результата, а не заново выбранный путь при retry. `interval` переносится как есть. В unit-тесте ему достаточно `partition`, в DAG сохраняй также обе действительные границы из `interval_manifest`.

Для `evaluated` вызови callback с исходным контекстом. После успеха верни копию состояния со `status="published"` и полем `release`. В примере callback, вернувший `{"version": "7"}`, добавит именно такой `release`. Остальные поля останутся прежними. Если callback поднимает исключение, оно пробрасывается, входной словарь и вложенный interval не меняются. Ещё одна попытка с тем же `evaluated` повторяет вызов с прежним контекстом. Для `published` callback не вызывается, возвращается прежнее содержимое.

Функция сама не пишет state в файл: аргумента пути у неё нет. Устойчивое сохранение состояния и вызов из task подключаются в DAG. Окно после внешнего side effect закрывается идемпотентным `publish`, а не одним флагом в памяти.

## Настройки ежедневного графа

В `schedule` используй явный `CronDataIntervalTimetable` с UTC. Передай `data_interval_start/end` из `get_current_context()` в манифест. Добавь интервал к версиям данных, кода и конфигурации в смысловом ключе. Сохрани этот ключ и путь артефакта при retry. Для опыта выбери только два прошлых суточных интервала. После проверки выключи расписание, чтобы следующий календарный день не расширил опыт.

Вызови временное исключение непосредственно перед publish. Повтори только упавший шаг, сохранив успешные upstream tasks. Сопоставь release, число результатов, DAG run ID, task ID, attempt, run_key и artifact path в реальных логах. Затем убери инъекцию. Это отдельная проверка настоящего исполнения, а не свойство одного unit-теста.

## Среда и зависимости

Для быстрых проверок используй основную среду Python с pytest из [SETUP](../../../../SETUP.md#основная-среда). Функции работают на CPU под Linux/macOS.

Зависит от 05-airflow/02-gate-retry. Offline доказывает преобразование интервала и переход состояния. scheduler retry/catchup проверяй в Airflow отдельно. Проверяй состояние конкретной task и созданные release-файлы, а не только общий статус DAG.

## Запуск и результат

Из корня репозитория:

```bash
make task TASK=05-airflow/03-failure-intervals
```

Тесты функций работают offline на маленьких входах и временных файлах. До реализации ожидается `NotImplementedError`. Ошибка импорта означает проблему подготовки среды. Проверка функций не заменяет описанный опыт на данных или стенде.

Это задание использует функции. Импортируй заготовку через `course_tasks.load_task("05-airflow/03-failure-intervals")` из Python. CLI не требуется.

## Требования практического опыта

Временно вызови исключение перед publish, повтори только упавший шаг и проверь отсутствие дубликата. Затем добавь ежедневное расписание, передавай интервал в манифест и проверь catchup/backfill на двух прошлых датах. Не запускай массовый backfill на ноутбуке.

## Приёмка и очистка

Запусти указанную выше команду `make task` после реализации и исправления ошибок. Проверяемые случаи перечислены в соседнем `test_task.py`.

После опыта останови стенд: `docker compose -f labs/airflow/compose.yaml down`. Не удаляй volume без экспорта истории. Артефакты `work/` сохрани для следующих модулей.

## Пример корректного результата

Интервал с началом 2026-01-01T00:00:00Z и концом 2026-01-02T00:00:00Z даёт partition=2026-01-01. Интервал без часового пояса или не равный 24 часам вызывает ValueError. Для уже published состояния callback не вызывается.

## Приёмка расписания настоящим SDK

В `housing_pipeline.py` уже доступны `get_current_context` и
`CronDataIntervalTimetable`. wiring интервала оставлен TODO. Реализуй его сам,
включая явное получение `data_interval_start/end` внутри task, сохранение в
manifest и устойчивость ключа при retry. Приёмка требует две реальные прошлые
суточные UTC task instances, разные partition и соответствующие сохранённые
границы. Повтор упавшего publish сохраняет прежние interval/run_key/artifact.

Проверяй эти значения в UI/logs/XCom и реальных файлах обоих результатов.
`interval_manifest` на двух строках и успешная загрузка DagBag не демонстрируют
catchup/backfill. Ограничь опыт ровно двумя датами, выключи расписание после
проверки. Новый календарный день не должен незаметно расширять backfill.

## Проверка реальных интервалов

После двух успешных ежедневных запусков:

```bash
MLOPS_RUN_INTEGRATION=1 AIRFLOW_INTERVAL_RUN_IDS='["свой-run-1", "свой-run-2"]' python scripts/run_task.py test 05-airflow/03-failure-intervals -- -m integration
```

Проверка читает две записи DagRun из metadata DB работающего контейнера и требует разные суточные UTC-интервалы. Она не создаёт backfill, не меняет scheduler и не подменяет интервалы текущим временем. Метаданные файлов и XCom сопоставь с этими run ID по описанной выше процедуре.
