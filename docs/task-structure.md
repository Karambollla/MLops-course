# Как работать с заданиями

## Папки

В `modules/<module>/tasks/<task>/` находится README темы. Для технических заданий рядом есть код или конфигурация и test_task.py; для руководств — разобранные примеры без фиктивных тестов. Fixtures используются как входы для вычислений, а не как шаблоны доказательства выполненной работы. Полный перечень — `make task-list` и [реестр](../modules/tasks.json).

Файл practice.md модуля содержит оглавление, общую подготовку и завершение стенда. Теория и hints.md доступны на уровне модуля; README конкретной задачи задаёт точные входы, выходы и критерии.

## Команды

Из корня курса после [SETUP](../SETUP.md):

```bash
make task-list
make task TASK=00-python/02-jsonl-cli
python scripts/run_task.py test 00-python/02-jsonl-cli -- -q
python scripts/run_task.py run 00-python/02-jsonl-cli -- modules/00-python/tasks/02-jsonl-cli/fixtures/valid.jsonl
```

У задач без CLI runner пояснит, что нужно запустить тесты функций или стенда. Для руководств он покажет README и прямо сообщит, что автоматических проверок нет. Параметры CLI всегда передаются после `--`.

`make test` проверяет готовую инфраструктуру тестирования и HTTP-обвязку. `make tasks-collect` собирает учебные тесты без выполнения. `make tasks` проверяет технические задания, исключая руководства. Незавершённые функции дают ошибки, интеграционные тесты без включения пропускаются. Успех общих проверок и пропуск стенда не означают выполнение практики.

## Результаты и перенос

Генерируемые результаты сохраняй в `output/` внутри задания, если его README не задаёт другой путь. Эти папки исключены из Git. Код, тесты и редактируемые конфигурации остаются рядом с условием. JSON/CSV с данными, манифестами или измерениями являются техническими входами и результатами; пересказ действий в отчёте не требуется.

Для двух переиспользуемых комплектов уже есть готовые экспортёры:

```bash
python modules/01-ml/tasks/02-candidate/export.py
python modules/15-triton/tasks/01-onnx/export.py
```

Первый переносит модель и три JSON-файла в `work/artifacts/`, второй — ONNX и config в `work/triton/model_repository/housing/`. Они не запускают решения или тесты; результат сначала создаёшь и проверяешь самостоятельно. Одинаковые файлы не меняются, отличающиеся заменяются только с `--replace`. Перенос атомарен для каждого файла, но не для всего комплекта. После замены модели перезапусти соответствующий сервис.

Скрипты вычисляют пути относительно задания и корня курса, поэтому могут запускаться из любой директории. Базовое окружение и пакет housing должны быть установлены по SETUP. Данные и модели в `work/` используются следующими модулями; Python-функции подключаются напрямую и копирования не требуют. Результаты Airflow/Ansible и хранилища сервисов сохраняются по их собственным инструкциям.

## Общий код

Пакет housing и Compose/Helm/Terraform-стенды находятся в labs. Канонические реализации упражнений — в tasks. Например, `python -m housing.train` вызывает функции из [кандидата](../modules/01-ml/tasks/02-candidate/README.md), а housing.evaluate — из [baseline](../modules/01-ml/tasks/01-baseline/README.md). CLI-файлы вызывают эти реализации через адаптеры. Реализацию упражнения редактируй в папке задания.

`course_tasks.load_task("00-python/01-records")` позволяет использовать функцию предыдущего задания. `load_solution(__file__)` используется тестами для загрузки соседней заготовки. Разные solution.py загружаются с разными именами, поэтому не перетирают друг друга.

При сборке housing-образа нужен корень репозитория:

```bash
docker build -t housing:course -f labs/housing/Dockerfile .
```

Dockerfile копирует необходимые задания в /course/modules. MLOPS_COURSE_ROOT задаёт корень поиска внутри образа; на ноутбуке он определяется из расположения установленного editable-пакета. После изменения Python-заготовки контейнерный образ нужно пересобрать.

## Импорты

Стандартная библиотека и обязательные зависимости находятся в начале файла. Необязательные SDK (ClearML, MLflow, ONNX, Qdrant client) могут импортироваться внутри функции, выполняющей реальное подключение/экспорт. Это позволяет собрать тесты всего курса без установки всех платформ сразу; такой импорт сопровождается пояснением. TYPE_CHECKING — блок на уровне модуля для аннотаций без загрузки необязательной библиотеки.

## Пределы проверки

Поведенческие тесты проверяют функции на небольших фиксированных данных, ошибки входа и конкретные результаты. Интеграционные тесты читают уже поднятый стенд только при `MLOPS_RUN_INTEGRATION=1`; тесты не разворачивают и не удаляют инфраструктуру.

Для действий, которые неудобно надёжно автоматизировать, README содержит команды и пример ожидаемого вывода или инвариантов. Примеры показывают форму результата и не выдают вымышленные измерения за реальный запуск. Материалы интервью и резюме — рекомендации без обязательных ответов и формальных тестов.
