# Как работать с заданиями

## Папки

В `modules/<module>/tasks/<task>/` находится README темы. Для технических заданий рядом есть код или конфигурация и test_task.py; для руководств — разобранные примеры без фиктивных тестов. Fixtures используются как входы для вычислений, а не как шаблоны доказательства выполненной работы. Полный перечень — `make task-list` и [реестр](../modules/tasks.json).

Файл practice.md модуля содержит оглавление, общую подготовку и завершение стенда. Теория и hints.md доступны на уровне модуля; README конкретной задачи задаёт точные входы, выходы и критерии.

## ML-notebook

Исключение из структуры папок — [01-ml/housing.ipynb](../modules/01-ml/housing.ipynb). Его три раздела, учебные функции и все тесты находятся внутри одного notebook. Зависимости устанавливаются первой ячейкой в текущее ядро; проверочные ячейки запускаются вручную и используют текущие определения функций. Отдельных solution.py, test_task.py и экспортёра у этого модуля нет.

Общие команды пропускают этот модуль. Их успешное завершение не означает прохождение проверок notebook. После изменения функции выполни её ячейку повторно, затем проверку. После перезапуска ядра снова выполни необходимые определения.

## Команды

Из корня курса после [SETUP](../SETUP.md):

```bash
make task-list
make task TASK=00-python/02-jsonl-cli
python scripts/run_task.py test 00-python/02-jsonl-cli -- -q
python scripts/run_task.py run 00-python/02-jsonl-cli -- modules/00-python/tasks/02-jsonl-cli/fixtures/valid.jsonl
```

У задач без CLI runner пояснит, что нужно запустить тесты функций или стенда. Для руководств он покажет README и прямо сообщит, что автоматических проверок нет. Параметры CLI всегда передаются после `--`.

`make test` проверяет готовую инфраструктуру тестирования и HTTP-обвязку. `make tasks-collect` собирает учебные тесты без выполнения. `make task` собирает все `test_*.py` внутри выбранной темы, включая отдельные SDK/server-проверки. `make tasks` проверяет технические задания, исключая руководства. Незавершённые функции дают ошибки, интеграционные тесты без включения пропускаются. Успех общих проверок и пропуск стенда не означают выполнение практики.

## Результаты и перенос

Генерируемые результаты сохраняй в `output/` внутри задания, если его README не задаёт другой путь. Эти папки исключены из Git. Код, тесты и редактируемые конфигурации остаются рядом с условием. JSON/CSV с данными, манифестами или измерениями являются техническими входами и результатами; пересказ действий в отчёте не требуется.

Модель и три JSON-файла сохраняются последней ячейкой [ML-notebook](../modules/01-ml/housing.ipynb) прямо в `work/artifacts/`. Готовая функция `save_artifacts` не запускает обучение и разрешает замену отличающихся файлов только при `replace=True`.

Для ONNX есть отдельный экспортёр:

```bash
python modules/15-triton/tasks/01-onnx/export.py
```

Он переносит ONNX и config в `work/triton/model_repository/housing/`, не запускает решение или тесты; отличающиеся результаты заменяются с `--replace`. Оба способа используют общий помощник: сначала проверяется комплект и конфликты, затем каждый файл заменяется атомарно, модель — последней. Весь комплект не является единой транзакцией. После замены модели перезапусти соответствующий сервис.

Данные и модели в `work/` используются следующими модулями. Python-функции подключаются напрямую и копирования не требуют. Результаты Airflow/Ansible и хранилища сервисов сохраняются по их собственным инструкциям.

## Общий код

Пакет housing и Compose/Helm/Terraform-стенды находятся в labs. Учебные реализации находятся в tasks, а для ML — в [notebook](../modules/01-ml/housing.ipynb). `python -m housing.train` и `housing.evaluate` загружают только отмеченные ячейки с импортами и функциями из сохранённого notebook. Установка пакетов, чтение данных, графики и проверки при импорте не выполняются. В функциях обучения используй явные аргументы: состояния интерактивного ядра в CLI нет.

`course_tasks.load_task("00-python/01-records")` позволяет использовать функцию предыдущего задания. `load_solution(__file__)` используется тестами для загрузки соседней заготовки. Разные solution.py загружаются с разными именами, поэтому не перетирают друг друга.

При сборке housing-образа нужен корень репозитория:

```bash
docker build -t housing:course -f labs/housing/Dockerfile .
```

Dockerfile копирует необходимые задания в /course/modules. MLOPS_COURSE_ROOT задаёт корень поиска внутри образа; на ноутбуке он определяется из расположения установленного editable-пакета. После изменения Python-заготовки или notebook контейнерный образ нужно пересобрать.

## Импорты

Импорты для описанного в условии подхода уже подготовлены в Python-заготовках: стандартная библиотека, вычисления, доступ к функциям предыдущих заданий и нужные SDK. Реализуй логику с этими зависимостями. Неиспользуемые импорты в незавершённой заготовке ожидаемы; комментарий `ruff: noqa: F401` учитывает это при проверке кода. В заданиях с CLI и конфигурациями используются соответствующие команды и файлы, Python SDK для каждого инструмента не требуется.

Импорты находятся в начале файла, на уровне модуля. Так зависимости видны до чтения функций. Это относится и к необязательным SDK, например ClearML, MLflow и ONNX.

Чтобы базовые тесты собирались без всего дополнительного стека, отсутствие необязательного пакета обрабатывается при импорте:

```python
try:
    import mlflow
except ModuleNotFoundError as exc:
    if exc.name != "mlflow":
        raise
    mlflow = None
```

Перед реальным обращением к SDK функция проверяет `mlflow is None` и сообщает, какой файл зависимостей установить. Проверка `exc.name` важна: отсутствие самого MLflow допустимо для базовых тестов, а сломанная зависимость уже установленного SDK должна оставаться видимой ошибкой. Импорт не должен подключаться к серверу, запускать обучение или создавать артефакты.

`TYPE_CHECKING` — блок на уровне модуля для импортов, нужных только статическому анализатору типов. Он не заменяет настоящий импорт библиотеки, которая нужна при исполнении.

## Пределы проверки

### Локальные проверки SDK

Часть заданий DVC, MLflow, ClearML, Vault, Qdrant, ONNX и Triton содержит тесты с marker `sdk`. Они проверяют настоящие форматы и библиотеки без внешнего сервера: MLflow использует временные SQLite и каталог артефактов, Qdrant — in-memory коллекцию, ONNX Runtime — синтетическую модель. Эти тесты не скачивают модели и датасеты и не используют твой каталог `work/`.

По умолчанию SDK-проверки пропускаются. После реализации задания и его предшественников установи зависимости соответствующего модуля и включи проверки явно:

```bash
MLOPS_RUN_SDK=1 python scripts/run_task.py test 02-reproducibility/01-data-version -- -m sdk
MLOPS_RUN_SDK=1 python scripts/run_task.py test 04-mlflow/01-experiments -- -m sdk
MLOPS_RUN_SDK=1 python scripts/run_task.py test 04-mlflow/02-registry -- -m sdk
MLOPS_RUN_SDK=1 python scripts/run_task.py test 06-clearml/01-offline -- -m sdk
MLOPS_RUN_SDK=1 python scripts/run_task.py test 10-vault/01-policy -- -m sdk
MLOPS_RUN_SDK=1 python scripts/run_task.py test 13-qdrant/01-plumbing -- -m sdk
MLOPS_RUN_SDK=1 python scripts/run_task.py test 15-triton/01-onnx -- -m sdk
MLOPS_RUN_SDK=1 python scripts/run_task.py test 15-triton/02-server -- -m sdk
```

Выполняй команды в соответствующих окружениях модулей. При включённом флаге отсутствие SDK приводит к понятной ошибке с инструкцией установки, а не к успешному результату или молчаливому пропуску. Незавершённая учебная функция остаётся ошибкой `NotImplementedError`.

Быстрые тесты используют подставные зависимости на границах SDK, subprocess и файловых операций. Они проверяют передачу настоящих результатов и ошибки взаимодействия, но не подтверждают работу внешнего сервера.

### Проверки стендов

Поведенческие тесты проверяют функции на небольших фиксированных данных, ошибки входа и конкретные результаты. Проверки чтения используют уже поднятый стенд при `MLOPS_RUN_INTEGRATION=1`; они не разворачивают и не удаляют инфраструктуру. Отдельные тесты с marker `writes` вызывают реализацию учащегося и создают только собственные учебные индексы, коллекции, runs или child tokens. Для них одновременно нужны `MLOPS_RUN_INTEGRATION=1` и `MLOPS_RUN_WRITES=1`. Уникальные имена отделяют их от результатов твоих ручных опытов; cleanup относится только к созданным ресурсам. Нагрузка housing также требует writes-флаг, поскольку изменяет счётчики настоящими запросами.

Флаги `MLOPS_RUN_SDK` и `MLOPS_RUN_INTEGRATION` независимы: локальная SDK-проверка не подтверждает запуск Docker, Kubernetes или GPU-serving.

Для действий, которые неудобно надёжно автоматизировать, README содержит команды и пример ожидаемого вывода или инвариантов. Примеры показывают форму результата и не выдают вымышленные измерения за реальный запуск. Материалы интервью и резюме — рекомендации без обязательных ответов и формальных тестов.

## Приёмка практики инструментов

[Матрица всех тем](practice-map.md) указывает самостоятельные изменения, интерфейс инструмента, входы/выходы и проверку. Формирование JSON или успешный mock не заменяет создание ресурса и чтение результата SDK.

Примеры после ручного запуска соответствующего сервиса и установки зависимостей его модуля:

```bash
MLOPS_RUN_INTEGRATION=1 MLOPS_RUN_WRITES=1 MLFLOW_TRACKING_URI=http://127.0.0.1:5001 python scripts/run_task.py test 04-mlflow/01-experiments -- -m writes
MLOPS_RUN_INTEGRATION=1 MLOPS_RUN_WRITES=1 QDRANT_URL=http://127.0.0.1:6333 python scripts/run_task.py test 13-qdrant/01-plumbing -- -m writes
MLOPS_RUN_INTEGRATION=1 MLOPS_RUN_WRITES=1 ELASTICSEARCH_URL=http://127.0.0.1:9200 python scripts/run_task.py test 14-elasticsearch-opensearch/01-elasticsearch -- -m writes
MLOPS_RUN_INTEGRATION=1 MLOPS_RUN_WRITES=1 OPENSEARCH_URL=http://127.0.0.1:9200 python scripts/run_task.py test 14-elasticsearch-opensearch/02-opensearch -- -m writes
```

Elasticsearch и OpenSearch запускаются по очереди. Установка SDK в окружение не делает сервер доступным. Для Vault, Airflow и Triton используй точные переменные и команды страницы задания; не подставляй production endpoints или чужие токены.

Выполнение LLM API-сценариев исключено: vLLM/SGLang generation/streaming/benchmark и генерация TensorRT-LLM/Triton backend не вызываются и не имитируются. Локальные формулы и подготовленные SSE остаются вычислительными упражнениями, а не интеграцией.
